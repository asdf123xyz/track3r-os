# ADR 0014 — App host API v2: read, MIDI in, audio tap and undoable edits for SD app modules

Status: **Accepted** (maintainer, 2026-10-14) including **amendment A (export writes), accepted the same day** · maintainer's answers: edit API typed; first-launch confirm for edit tools; tier-2 scripts discarded; import UI stays with OS-FILES · Amends ADR 0002 (app modules; tier 2 scripts) and builds on ADR 0009 (actions, Editor, descriptors) · Panel: one design panel with three design lenses · Maintainer direction, 2026-10-14: the app modules below; **apps may not write to the SD card, save or touch files**; every edit undoable.

## Context

Today an app module (ABI 1.2, `module/sdk/o3module.h`) runs in the main loop, owns a page body, draws through a budgeted draw API (96 calls, 256 points, 384 characters, 4 ms a frame), gets button, pad and encoder events, keeps at most 32 runtime parameters, and its host table has only log, math and draw. It cannot hear audio, receive MIDI, read or edit the project, or touch files. The maintainer wants these as app modules:

- **TAP / CALC** (needs nothing new).
- **Level 2, read-only**: TUNER, SCOPE / SPECTRUM, LOUDNESS / VU with history, MIDI MONITOR.
- **Level 3, edits**: RHYTHM GEN (polyrhythm, probability, variations), CHORDS (a progression into a track), HUMANIZE (microtiming and volume jitter on a block), MUTATE / MORPH (instrument parameters), MOD RECIPES (modulation-matrix routes, OS-MODMX). Tool apps also appear in Pattern F7 TOOLS (`docs/ui/ui-map.md`).
- SMF export was dropped (it needs SD writes).

Facts checked in the tree: `o3m_host` carries its own `size`, so additive growth is the convention; the file header has `reserved2[2]`, zero today (`o3module.h:368,390`); `core::ActionArg` is one `int32_t` and most of the about 180 registered actions are cursor- or focus-relative (`app/src/actions.cpp`); `model::Editor` has nesting `begin_group()` / `end_group()` undo units (`editor.h:66-67`); the SD-writing actions are named (`file.save`, `file.save_as`, `sedit.save_wav`, ...: `actions.cpp:68-74`).

## Panel views (one line each)

- **Real-time and resources**: one mono tap ring plus peak / RMS is enough for TUNER (≈ 2048 frames at 11 kHz via decimation), SCOPE / SPECTRUM (512–1024) and VU; never call module code from the render or the MIDI parser; bench SDRAM jitter, fall back to a 4-block SRAM_U ring if it passes 20 µs.
- **Musician and compatibility**: a typed edit table, because generators think in steps and parameters, not in cursor moves; copy-out reads keep the model free to change; a confirm only for tools that edit.
- **Extensibility and verification**: the typed read / edit tables are exactly what a future script host would wrap, so scripts are deferred, not superseded; verify with a property test (any app edit sequence then undo restores the snapshot), a fuzz of every host entry (no file action reachable, no mutator outside a group) and a loader test that a 1.2 `.tmod` loads under 1.3.

## Recommendation

**ABI 1.3 (claimed by slice H1, the first to merge; amendment D), additive**: the capability mask in `reserved2[0]`, three host tables appended to `o3m_host` (read, edit, io), the launch context through a read call (not on `init`). Edits through a small **typed** API, one undo group per apply, hard size and rate limits. **File, save, format, update and WAV-save are absent by construction**: the edit table has no such entry, and the only actions reachable by id are a static `constexpr` whitelist (undo / redo, transport play / stop); there is no generic `run_action(id)`. Audio tap: one selectable mono block ring plus peak / RMS. MIDI in: an SPSC ring drained in the app's frame. Tier-2 scripts: the panel proposed deferring them; **the maintainer discarded them** (2026-10-14): ADR 0002's tier 2 is closed, SD extensions are native modules only.

## Consequences

- Unlocks every app the maintainer listed except SMF export; tool apps in Pattern F7 TOOLS with the selection as context.
- Apps never write the card: a project changed by an app is saved by the user (File SAVE), as any edit.
- The ABI grows (read, edit, io tables, `o3m_step` POD) and must stay stable: versioned PODs with `size`, static_asserts on `o3m_host` growth.
- 1.2 apps keep working (capability word 0). ADR 0002's tier 2 (scripts) is closed (maintainer).

## Validation

- Host: the undo property test and the host-entry fuzz above; a 1.2 fixture loads under 1.3; capability gating (a table is NULL without its bit).
- `hw-session` / `rt-optimize`: SDRAM jitter of the tap ring (< 20 µs or fall back), `diag cpu` before and after the tap, MIDI ring overflow counter under a dense controller stream.

## Amendment A — export writes (Accepted, maintainer 2026-10-14: apps may save to the SD for exporters)

The maintainer first ruled out SD writes, then raised exporters and accepted this design. Apps write nothing else:
- A fifth capability bit, **export_files**, and three io-table calls `export_open(name, ext) / export_write(buf, n) / export_close()`.
- **Create-only, in a sandbox**: the file goes to `AppExport/<app name>/` only; the name is sanitised (no path components, the module-name character rules) and an existing name gets a numeric suffix, so nothing is ever overwritten, renamed or deleted. No reads of any card file, no access to the project folder, `/modules`, `Firmware/` or anything else.
- Written through the core's atomic save (`app/atomic_save.h`), with the same gates as a core save (the card gate: a mounted, writable FAT card), a size cap (4 MiB a file [default]) and a count cap per app.
- The first-launch confirm names it: "This tool writes files to AppExport/<app>."
- Unlocks **SMF EXPORT** again (dropped for lack of writes; back on the maintainer's app list, slice H4) and lets other exporters (XM / IT export, reports) be apps instead of core code.
- Verification: host fuzz of the export calls (no path escape, no overwrite), a card test on a card.

Path amended 2026-10-15 (OS-H4): `AppExport/<app>/` instead of `/exports/<app>/`. On a computer `Export/` (the WAV export) and `exports/` read as the same folder, and `AppExport` cannot collide with a project name. The details (ABI 1.7, the non-blocking calls, the extension allowlist, the abort rule) are in `docs/specs/OS-H4.md`.

## Amendment B: H1 carries the clock and the tempo (2026-10-14)

OS-TAPCALC showed that an app with no clock counts taps in UI frames (about 33 ms), and that a tap tempo cannot apply its result without an edit entry. The design is unchanged; only the order of the slices moves:
- **H1 adds `now_ms()`** to the io table: a monotonic millisecond clock, read-only. It needs no capability bit.
- **H1 adds `get_tempo`** to the read table.
- **H1 brings forward `set_tempo`**, the first entry of the typed edit table. It sits behind the edit_project capability and the first-launch confirm, and each call is one undo unit through `edit_begin` / `edit_end`. The rest of the edit table stays in H3.
- **OS-TAPCALC is held on its branch** until H1 lands, then rebased onto these calls and merged with H1. That way the frame-count BPM, and the calibration it would need, never ships.

## Amendment C: MIDI out and SysEx for apps (maintainer, 2026-10-14: additional work, at the end of the queue)

Purpose: custom integrations with outboard gear. Examples: hardware-synth editors, setlist scenes (program change and CC per song), MIDI Tuning Standard retuning, Identity Request auto-detection, Launchpad/APC LED feedback, MMC/MTC transport, and later Sample Dump Standard and patch librarians. Not started; it sits at the end of the queue (BACKLOG OS-APPMIDI).

- **C1 (S/M):**
  - A sixth capability bit, **midi_out**, with the first-launch confirm: "This tool sends MIDI, including SysEx, to your devices."
  - io calls `midi_send(port, bytes, n)` for DIN, USB or both. Short messages and complete SysEx frames go through the OS MidiOut queue, rate-limited per frame so the sequencer's timing always wins, with a per-app byte cap per second.
  - A SysEx-in buffer per app (default 4 KB), delivered in chunks with start, continue and end flags; overflow is counted, never blocking.
  - The core MIDI parser stays the only reader of the ports.
- **C2 (M), later:**
  - Read access to the app's own `AppExport/<app>/` folder (read and list only; still no access outside the sandbox), for librarians and SDS.
  - A send-at-tick queue for timed output, scheduled by the render-side MidiOut, never by app code.
- **Limits:**
  - Apps run in the main loop (16–33 ms jitter), so C1 is for configuration and editing, not for playing in time.
  - Storing gear patches inside the project would be a persistent-format change: Level C, a separate decision.
- **Verification:**
  - Host fuzz of `midi_send`: malformed SysEx, oversize, flood.
  - A test that sequencer note timing does not move under an app flood.
  - On the unit: a MIDI loopback check.

## Amendment D: how slice H1 resolved the open points (OS-H1, 2026-10-14)

Implementation decisions inside the accepted design. They are additive and reversible (nothing here touches a persistent format); the maintainer is told in the report of OS-H1.

1. **Launch context: an additive read call, not a new `init()` signature.** `init(state, host)` keeps its ABI 1.2 shape, so a 1.2 module's `init` is called exactly as before. The context is `o3m_read_api.launch_ctx(o3m_launch_ctx* out)`: `{size, flags, pattern, track, instrument, block_start, block_length}`; `flags` bit 0 is `O3M_LAUNCH_FROM_TOOLS`. Opened from the MODULES list every field is zero and the call returns 0. The caller sets `out->size` to its own struct size and the OS copies at most that much (a later field is added at the end). Pattern F7 TOOLS (slice H3) fills it through `ModuleUi::launch_app(entry, project, ctx)`, which already takes it. Decision 7's text is amended: the context is *returned by a read call*, not passed to `init`.
2. **ABI minors go in merge order; H1 takes 1.3.** H1, OS-INSTUI S10 (page names, enum labels) and the cpu-budget M5 idea (`set_mod`) each wanted 1.3. The first to merge owns it (this slice); the next takes 1.4, and so on. `O3M_ABI_MINOR` is 3; `docs/specs/OS-INSTUI.md`, `docs/architecture/cpu-budget.md` and `docs/ui/ui-map.md` no longer claim 1.3. (INST 1.3 in OS-INSTUI is a different thing: the instrument file's minor.)
3. **Capability word and bits** (superseded in part by the conditions below: C4). `reserved2[0]` of the file header. Bits: `midi_in` 1, `read_project` 2, `audio_tap` 4, `edit_project` 8, `export_files` 16, `midi_out` 32 (all six assigned now; an OS of ABI 1.3 accepts only 1, 2 and 8, so a later slice's bit is refused as a reserved field until its minor). Only an **app of ABI 1.3** may set the word; a 1.2 file, or an instrument or effect, with a value there is `BadReserved` and quarantined. Set by `o3m_pack.py --caps midi_in,read_project,edit_project` (CMake `o3m_add_module(... CAPS ...)`); `module.json` `"capabilities": [...]` makes the generator write ABI minor 3 and the verify test compares the file with the manifest.
4. **Tables.** `o3m_host` grows `read`, `edit`, `io` at its end (`O3M_HOST_HAS(host, member)` checks `size`). `read` needs read_project, `edit` needs edit_project. The **io table is lent to every app that declares ABI 1.3** (it carries `now_ms`, which needs no capability bit); its `midi_read` / `midi_lost` members are NULL without `midi_in`, or in a build with no MIDI ring. An app that declares ABI 1.2 gets none of the three (NULL), whatever the OS could give: that is the back-compat rule, tested with a real 1.2 `.tmod` (the Pads example stays ABI 1.2 on purpose).
5. **Read table (H1) = `get_tempo` + `launch_ctx`.** `get_tempo` returns the project's tempo in **BPM x 100** (the model's `tempo_x100`, 4000..80000; 0 with no project); if a `set_tempo` of the same app is still queued it returns that value (read your write). Transport, steps, parameters and routes are added at the end of the table by later slices; each is a size-gated member.
6. **`set_tempo` (edit table, H1) is one undo unit of its own.** The grouped `edit_begin` / `edit_end` arrive with H3 and `set_tempo` will join an open group. The call only validates (range, project present: `O3M_EDIT_RANGE`, `O3M_EDIT_NO_PROJECT`) and **queues** one value; the App applies it at its next pass as the undoable action `module.app_tempo` (so dirty flag, undo, macro recording and the sequencer follow the usual path). Several calls in a frame coalesce into the last (at most one apply a frame). A request still queued when the app closes is applied; one queued when a project load clears the modules is dropped.
7. **The first-launch confirm** for edit_project is a two-step F1 on MODULES: the first launch shows "EDITS THE PROJECT (UNDOABLE): F1 AGAIN" and does not start the app; launching the same app straight after starts it. It is remembered **for the boot** (the last four confirmed stems, in RAM), not stored: a persistent record would be a settings-format decision. Reversible: a stored acknowledgement can replace it later without touching the ABI. **The memory is a ring of four stems** (review R4): a fifth editing app confirmed in one boot evicts the oldest, which is asked again. **Known (review R5, left as is):** the app is told its launch went through, and `set_tempo` returns OK, before the edit applies (it is queued and applied at the next pass); OK means "queued".
8. **`now_ms`** is the low 32 bits of the device's millisecond uptime (`hal::Clock::uptime_ms`). It wraps every 49.7 days: an app subtracts. No capability bit.
9. **MIDI in.** A 64-entry SPSC ring of 4-byte events in the render's control-change object (`midi/monitor.h`, inside `midi::CcInput`, SDRAM; about 300 bytes taken from the sample arena's tail). The render's existing byte walk feeds it; the **core parser stays the only reader of the ports**. It is switched on only while an app with `midi_in` runs (one relaxed load per byte otherwise). Events are whole **channel messages** (`port, status, data1, data2`; port 0 DIN, 1 USB), oldest first; real-time bytes and system common are not delivered; **SysEx is dropped and counted** once per message; a full ring drops the new message and counts it. The app drains it from its own frame (`view_draw`), 64 per call at most.
10. **The exit chord (F7 + F8).** Checked in the code (`App::pass`, `feed_module_app`, `bindings.cpp`): the app is handed the raw events first, then the OS's gesture layer recognises the chord and closes the page. So the **app sees the two presses (F7, F8) as ordinary button events, never their releases**, and the page closes in the same pass. `o3module.h` was right; the SDK README and the app guide that said the app does not hear it were wrong and are fixed. The chord stays the OS's: an app cannot swallow it. **Chord window (OS-CHORDEXIT, 2026-10-14):** the exit chord keeps the global 40 ms chord window (`kGestureTimings.chord_ms`, `core/include/o3os/core/gesture.h`); the maintainer's hand test on 0.4.16 exits every time. Fallback if a missed exit is ever reported: a 120 ms window for the exit chord only (not for the other chords). The HIL runner sends the chord as a `"burst": true` keys step so that it lands inside the 40 ms window (`o3hil.py`).
11. **`diag mod load` and apps.** The loader's search order already includes `modules/apps/` (`loader.cpp`, after instruments and effects), so `diag mod load <name>` loads and checks an app file; `mod bind` refuses it (not an instrument). It never launches an app: **MODULES, F1 is the way** (documented). The old text in the guide and in the console comment was stale; no code change.

### Conditions on amendment D (confirmed on points 1-5, 2026-10-14), folded into slice H1

- **C1. A table is NULL without its bit.** Any io / read / edit entry that needs a capability bit (`midi_read`, `midi_lost` today; the `export_*` calls in H4 with export_files, `midi_send` in C1 with midi_out) is NULL in the lent table unless the app's file asked for the bit and the OS grants it. The rule is stated in `o3module.h`; a test pins NULL for every gated entry, for every subset of read_project, edit_project and midi_in (`module_host_api_test`).
- **C2. `set_tempo` is rate-limited.** At most one tempo is queued per app frame, the last valid write wins (a refused, out-of-range call does not replace it), and each apply is one undo unit. Tested over several frames.
- **C3. The confirm memory is per boot and nothing is stored** (decision 7).
- **C4. The six capability bit values are frozen as published ABI** (midi_in 1, read_project 2, audio_tap 4, edit_project 8, export_files 16, midi_out 32), written in `docs/guides/app-modules.md` section 3.1 and the SDK README. Decision 3 changes in one point: an app that asks for a published bit this OS does not grant (4, 16 or 32 on ABI 1.3) is **refused at load** with its own loader status (`CapUnsupported`, not quarantined: the file is good, the OS is old) and a launch message that names the capability ("NEEDS AUDIO TAP (NEWER OS)", "NEEDS EXPORT FILES (NEWER OS)", "NEEDS MIDI OUT (NEWER OS)", all within the 48-character notification strip). It never runs with half its tables. A bit above the six is still a reserved field. Tested per bit at the image, the loader and the launch.
- **C5. Tap Calc declares edit_project** (with read_project) and so gets the two-step confirm; QA-MOD-008 says so; the packed file's word is pinned in `o3m_tapcalc_test` and the confirm for that word in `module_host_api_test`.

Review fixes folded in the same slice (OS-H1 review, approve with minors): the MIDI-in render parser is reset on every enable edge (a new midi_in app never completes the half message or running status of the last one); an app of ABI 1.2 is lent the real 1.2 host table (`size` ends at `draw`, `abi_minor` 2) and not a full-size table with NULLs; Tap Calc's default window is the widest (8 intervals) and its comment, the guide and the QA rows state the real accuracy (only the end taps count and keep the main loop's jitter: one end tap 33 ms off is about 2 BPM over 4 intervals, about 1 BPM over 8, at 120 BPM).

## Amendment E: how slice H2a built the audio tap (OS-H2a, ABI 1.4, 2026-10-14)

Implementation decisions inside decision 3(b); additive, reversible, no persistent format touched. Level C for the render write (a block's tap work in `Graph::run_taps`), B for the rest. TUNER and SCOPE / SPECTRUM are H2b; the API below was shaped for them (TUNER: `tap_stream`, decimated by the app; SCOPE / SPECTRUM: `tap_latest`).

1. **ABI 1.4 and the capability.** `O3M_ABI_MINOR` is 4 (the next minor after H1's 1.3, in merge order). `O3M_CAP_AUDIO_TAP` (4) is granted: `O3M_CAPS_ABI_1_4` = 1 | 2 | 4 | 8. The bit is valid in a file of **ABI 1.4** (`module.json` `"capabilities": ["audio_tap"]` makes the generator write minor 4; the packer refuses it on a lower minor). In a file of 1.3 or below it is a reserved field (`BadReserved`, quarantined: the file is wrong, not the OS old). C4 stands for the two bits still not granted: an app that asks for `export_files` (16) or `midi_out` (32) is refused at load (`CapUnsupported`, "NEEDS EXPORT FILES / MIDI OUT (NEWER OS)"). A **build with no tap** (a simulator without the object) refuses an app that asks for audio_tap with "NEEDS AUDIO TAP (NEWER OS)" and never runs it with half its tables. 1.2 and 1.3 apps run unchanged: their tables are the ones they had, the io table is the same one with four members appended at its end (NULL for them), and the back-compat tests are the H1 ones plus `module_host_api_test` "audio tap (H2a)" (a 1.3 app sees the 1.3 members at their offsets and the tap members NULL), `module_image_test` and `module_view_test` (the bit per ABI minor).
2. **The io table grows four members** (`o3module.h`, all NULL without the bit, rule C1): `tap_select(source)` (OFF / INPUT / MASTER), `tap_latest(out, frames)` (the newest window, 2..2048 frames), `tap_stream(out, max_frames, lost)` (everything new since the last call, up to 4032 frames; if more is waiting the oldest are dropped and counted) and `tap_levels(out)` (peak, RMS, clip blocks and the frames measured since the last call). The tap is off until the app selects, and off again when the app stops (`release_host`); a select starts the app's cursors two blocks after "now" so that nothing of the previous point is returned.
3. **Where the tap is.** One mono int16 stream, `kernel::mono_mix` of the INPUT bus as the render holds it at the end of the block (after the input strip's level: the Mixer's input meter sees the same; raw while that strip is closed) or of the MASTER output pair (what is heard: USB return included, the metronome click not; the same mono sum the spectrum ring takes, computed once when both are on). Written at the end of `Graph::run_taps`, after the meters, so a muted or silent render still keeps the sequence counter moving.
4. **The ring is 64 blocks, not 16.** ADR 0014 said 16 × 64 frames (23 ms). The main loop's frame is 16..33 ms and a reader that runs once a frame needs the ring to hold more than one frame of audio; 16 blocks are lapped by every 33 ms frame. 64 blocks are 93 ms, so a 30 Hz reader never loses a block, and the SDRAM is plentiful: **8 KiB** as the 32-bit atomic words of the existing `SampleRing<4096, 64>` (reused, not a new ring), plus **768 B** of per-block stats, about 9 KB at the sample arena's tail (`app_main.cpp`, `kAppTapSamples`), SRAM only the 4-byte pointer in the `Graph`. `max_window` is 63 blocks (4032 frames): the block the writer is in is the slack.
5. **Peak / RMS are per block, in a stats ring, not 16 B of SRAM.** A meter on a 33 ms frame must not miss the peak of a block between two reads, and a single "latest block" word would. So each block writes `{peak, sum of squares (64 bit)}` into a slot of a 64-slot ring beside the samples, with the same index and the same lap rule; `tap_levels` folds every block since the reader's last call (peak = max, sum of squares added, clip blocks counted) and the host takes the square root in the main loop. Three SDRAM words a block, none read back.
6. **Protocol (documented in `app_tap.h`).** Single writer (the render), single reader (the main loop), no read-modify-write anywhere (the SDRAM alias rule of `sdram_view.h`: no LDREX / STREX), plain 32-bit loads and stores. Writer: stats slot first, then the samples; the last store publishes the sequence counter (`head`, frames ever written, a multiple of 64) with release. Reader: `head` (acquire), copy, `head` again: a slot at position p is intact iff `h2 - p <= 4032`; three bounded tries; a reader that was lapped drops the OLDEST data and counts it (`lost`), never the render's time. Cursors are free-running u32 frame counts used only as differences (wrap-safe). A thread test (`audio taps thread:`, also under TSan) checks that whole windows are whole blocks and that a block's peak and sum of squares belong together.
7. **Cost and placement (Level C).** Off: one relaxed load of the source per block. On: `mono_mix` of 64 frames, `kernel::meter` (SMLALD, 64 frames), 32 word stores for the samples and 3 for the stats; the render times the whole tap work with its cycle counter and keeps min/mean/max (published every 16 blocks), shown by `diag cpu` as `tap: master, <n> blocks, write cycles last <a> mean <b> max <c> (max <x> us)` (`cpu reset` zeroes it through a request counter the render obeys: the render stays the only writer). **Host estimate** from the instruction counts: the two kernels are about 150 to 250 cycles each (`diag bench k_mono_mix`, `k_meter` give the unit's numbers), the 35 SDRAM stores 10 to 28 cycles each (cached ICode alias or system bus) so **600 to 1,400 cycles, 3 to 8 µs, worst case; 0.4 to 0.9 µs if the stores pipeline**: the ADR's 2 µs target is NOT yet shown, it is a **unit measurement** (QA-MOD-023). The ADR's fallback stands: if the max passes 20 µs (3,600 cycles) the ring moves to 4 blocks in SRAM_U (the API does not change, only the gapless guarantee of `tap_stream`). `AppTap::push` has to be in `.ramfunc_l` (a hot caller may not call flash, `check_ramfunc.py`; `O3OS_AUDIO_COLD` is for per-event code): see the commit's delta for the bytes, the budget is 27,648 B.
8. **LOUDNESS VU** (`modules/apps/loudness/`, new Community OS behaviour): the first app on the tap. It uses `tap_select` and `tap_levels` only: SOURCE (1 INPUT, 2 MASTER, a parameter), PEAK with a 24 dB/s fall and a hold marker (HOLD 1..10 s), RMS over 300 ms (a one-pole average of the mean square), a clip lamp for 2 s and a CLIPS counter, HOLD and MAX readouts, and a 24 s history line of the RMS (96 points); Delete clears. All dBFS, from the host's `log2_f` / `exp2_f`; a hostile answer (NaN, a negative, an absurd level) counts as silence. 3,000 B file, no hot code, 460 B of state.
9. **Not in H2a.** The TUNER and SCOPE / SPECTRUM apps (H2b); a decimation helper in the host (apps decimate themselves, with their own low-pass: a host-side decimator would fix a filter in the ABI); tap points other than input and master; a stereo tap.
10. **To verify on the unit** (`qa_modules.json`, QA-MOD-017..023): the VU follows a playing song; the INPUT point; the clip lamp; the tap line of `diag cpu` (the write time against 2 µs and the 20 µs fallback rule); `underrun 0` with the tap on during a dense song.
11. **H2b as built (OS-H2b, 2026-10-14): TUNER and SCOPE SPECTRUM.** Two SD apps (`modules/apps/tuner/`, `modules/apps/scope/`; ABI 1.4, capability audio_tap, new Community OS behaviour) on the API above, with **no change to the host, the tap or the ABI**. Written from scratch (no third-party code, no licence question), single precision, main loop only, no libc. They share an FFT and text helpers in `modules/apps/common/` (headers; CMake `INCLUDE`).
    - **TUNER** (`tap_stream`): its own 33-tap FIR low-pass (4.2 kHz) and decimation by 4 (11,025 Hz), a 2,048-frame ring, a normalised-autocorrelation pitch detector (Hann window, autocorrelation by two 2,048-point FFTs, Boersma's window correction, first peak at 0.9 of the highest and at least 0.6, refinement on the peaks at 2, 4, 8 ... periods), 30 Hz to 2.1 kHz (a period at the edge of the longest lag searched, 30.0 Hz, is refused: 27 and 29 Hz are NO SIGNAL), a median of 5 readings and an 8-cent note hysteresis, parameters A4 415..466 and SOURCE (INPUT default). A `lost` gap, a source change or 500 ms without samples restart the window. A window whose strongest line is above 3.6 kHz is NO SIGNAL (a tone near a quarter of the rate has its correlation peaks on the wrong lags at 11 kHz).
    - **SCOPE SPECTRUM** (`tap_latest`): VIEW, SOURCE (MASTER default), TIMEBASE (128 to 1,536 frames). Scope: rising zero-crossing trigger with hysteresis and a free-run fallback. Spectrum: 1,024-point FFT with a Hann window, 48 log bars 40 Hz to 20 kHz, 60 dB, bar fall 60 dB/s and peak-hold fall 12 dB/s.
    - **The 4 ms rule drives the structure**: `view_draw` may take 4 ms, and a 2,048-point transform is about 3 ms of CPU by the compiled loop (about 45 cycles a butterfly), so the FFT runs one stage at a time (`o3fft::step`), and the app's state is in SDRAM, which the core does not cache (about 28 cycles a load), so the estimate can be several times short. The work is therefore split into chunks (256 butterflies or 512 array elements; the tuner's filter 32 outputs, filtering from the stack), bounded by a chunk count AND by the host clock, which is checked BEFORE every chunk, the first one too; what the filter has no time for waits for the next frame (the stream stays gapless; more than 46 ms behind is a gap), and the last result stays on screen. If the estimate is wrong the guard slows the readings down instead of quarantining the app (`ViewStatus::Time`). Nominal figures, ESTIMATES owed to the unit (QA-MOD-033): Tuner a reading every 6 frames (about 200 ms), about 1.3 ms a frame; Spectrum a transform every 3 frames. Host tests drive the guard with a fake clock that advances while the app works.
    - **Size and state**: tuner.tmod 5,740 B (state 38.6 KB), scope.tmod 4,832 B (state 17.1 KB), no hot code; firmware flash delta 0 (SD files).
    - **Verified on the host only**: `o3m_tuner_test`, `o3m_scope_test` (FFT against a direct DFT, trigger, bars, tuner within 2 cents on sines). **To verify on the unit** (`qa_modules.json`, QA-MOD-024..033): the notes from MIDI, the A4 reference, NO SIGNAL on noise, the scope trigger and timebases, the spectrum bars and falls, and above all the per-frame cost (the estimates above are not measurements; no console command shows an app's `view_draw` time yet).

## Amendment G: how slice H3a built the edit table (OS-H3A, ABI 1.5, 2026-10-15)

Implementation decisions inside decisions 1(b), 5 and 7 and amendment D.6; additive, reversible, no persistent format touched. Level C for the published ABI, B for the rest. H3b (instrument parameters, routes, CHORDS, HUMANIZE, MUTATE / MORPH, MOD RECIPES) is not here.

1. **ABI 1.5** (`O3M_ABI_MINOR` 5, the next minor after H2a's 1.4). Everything is appended after the existing members; no capability bit changes (read_project 2, edit_project 8) and the file header is untouched. Read table: `pattern_info`, `get_steps`. Edit table: `edit_begin`, `edit_end`, `set_step`, `set_steps` (after `set_tempo`). Launch context: `block_tracks` (a `uint8_t` and 3 reserved bytes, 32 bytes in all; the 28-byte struct of 1.3 and 1.4 is its prefix). New codes beside `OK 0`, `RANGE 1`, `NO_PROJECT 2`: `NO_GROUP 3`, `GROUP_OPEN 4`, `LIMIT 5`, `RATE 6`. **The layout is proved twice.** `o3module.h` ends with compile-time assertions of the byte offset of every member of the host tables and the size of every table and POD for the 32-bit target, so every module build (the cross compiler builds all of them) fails if a published member moves; `tests/module_edit_test.cpp` keeps literal copies of the 1.2, 1.3 and 1.4 layouts and checks that an app declaring 1.3 or 1.4 finds each member where it was, that the launch context an app built for 28 bytes asks for is filled to 28 bytes and not one more, and that a 1.2 app is still lent nothing. The loader's minor rule is unchanged (a file above the OS's minor is refused); the launch now says `NEEDS NEWER OS` for it (and again on a second try, though the loader has quarantined the file for the boot), tested with a file of minor 6.
2. **The step POD** is the spec's `o3m_step` (8 bytes, the model's encodings, constants named `O3M_NOTE_*`, `O3M_VOL_*`, `O3M_FX_*`) and a **field mask** on every write (NOTE 1, INSTR 2, VOL 4, FX1 8, FX2 16). Values the Pattern cannot show are refused with RANGE (a note 129..252, an instrument above 64, a volume 128..254, an FX type 43..127; only the masked fields are looked at). `pattern_info` returns `{size, length, tracks}` as specified **plus `track_length[16]`**: rows are valid only inside the track's own length (the rule the pattern editor keeps, D7), so an app has to know it, and a polymetric pattern would otherwise make every lane write RANGE. Pattern ids are 1..255; a pattern that does not exist is RANGE for reads and writes alike (an app cannot create one; H3b may add that, a fresh pattern in a project is created by the first hand edit).
3. **A group is buffered, checked at the call, applied at `edit_end` by an ordinary undoable action.** The spec had `edit_begin` open an Editor group directly. The App's Editor is private to `dispatch()` (session.h: every project edit is an undo unit named by an action), so the group is kept in a fixed buffer of the module system (2,048 steps of 8 bytes and 2,048 five-byte ops, about 26 KB) and `edit_end` hands it to the App through a sink (`ModuleUi::set_edit_sink`, set by `App::attach_modules`), which runs the action **`module.app_group`** with the app's catalog entry as its argument. The handler writes the ops through the Editor inside the unit `dispatch()` opened, so the unit is named by the action and the app, the dirty flag (the project's generation), the sequencer and the undo history follow exactly as for a hand edit, and the action is not recorded in a user's macro. Each op is merged field by field with the step the project holds at that moment (the mask) and written with `set_steps`; the whole group is validated against the project before the first write. Consequences, all documented in the guide: a write is checked when called but the project changes at `edit_end` (a read inside the group sees the old project); `edit_end` returning OK means **applied** (it is synchronous, unlike `set_tempo` outside a group, where OK means queued); there is no `Editor::abort_group()` and no change to the journal, because the rollback of a group that went over a limit is that **nothing was ever written**: the project is byte-identical (same generation, no unit, and the redo history is still there). The cost is the 26 KB: the module system's host block at the start of the module region (SDRAM) grew from 32 to 64 KiB (`kModuleHostBytes`, `app_main.cpp`), taken from the modules' arena (768 KiB).
4. **Limits and rate.** At most **4,096 write calls** (`set_step`, `set_steps`, `set_tempo` in a group; refused calls count) and **2,048 steps** per group. The write that crosses either limit and every later write answers LIMIT and stores nothing; `edit_end` answers LIMIT and drops the group. A bad argument answers RANGE, writes nothing and **does not poison** the group (the spec: "that call writes nothing"; only LIMIT drops a group). **One group per call into the app, and only from `input()`**: a second `edit_begin` in the same call, or one from `enter`, `exit`, `set_param` or `view_draw`, answers RATE (an app edits on the user's key press; draw may run many times a frame and sits inside the renderer's pass).
5. **A group left open.** Every call into the app is bracketed (`begin_call` / `end_call`); when it returns with a group open the OS closes it (`end_call` -> `close_group`): the changes are **kept and applied** as one unit the user can UNDO (an app that forgot `edit_end` after a long generation must not lose or half-apply it), counted (`groups_abandoned`) and the first one of a launch is logged (`app: edit group left open, closed by the OS`). A group that had gone over a limit is dropped as at `edit_end`. The same bracket runs when the OS stops an app for a budget overrun (the verdict is read after `end_call`: the group is applied first, then the app is quarantined: the unit stands, as the ADR planned) and when the page closes (`exit` and `shutdown` are calls too). The Editor never has a group open across a frame, so UNDO is never Busy because of an app. `reset()` (a project load clears the modules) forgets a group; there cannot be one open then. Not handled: a hard fault inside the app's code (the device resets, as for any module).
6. **The host's time is not the app's.** `edit_end` applies the group inside the app's `input()` call, and a call may use 4 ms; the time spent in the sink is credited back to the call (`ViewHost::credit_host_us`), so a legitimate 2,048-step group cannot get its app quarantined. The cost on the unit is an open measure (QA-MOD-071): the host work of one APPLY of 4 lanes x 16 rows is a handful of 7-byte copies and four journal records.
7. **`set_tempo` joins an open group** (D.6): inside a group it is validated, counted and applied with the group at `edit_end` (`get_tempo` returns it meanwhile), part of the same unit; outside a group it is queued and its own unit `module.app_tempo`, as in H1 (C2 unchanged).
8. **UNDO names the app.** The unit's argument is the app's catalog entry; `edit.undo` / `edit.redo` read the unit before the walk and, for `module.app_group`, post `UNDO <APP NAME>` / `REDO <APP NAME>` (the module's own name, upper case). The name is looked up in the catalog of the moment, so a rescan that reorders the apps between the edit and the undo can name another app; the project is restored all the same.
9. **Pattern F7 TOOLS** (`tools_list.h`, `tools_actions.cpp`, `screens/tools_overlay.cpp`): a modal list overlay (context `tools`, OverlayId::Tools) with the engine picker's grammar. `ModuleUi::scan_tools()` rescans the card and keeps, in catalog order, the apps whose file asks for edit_project (`app_caps`: the loaded module's header, else the first 64 bytes of the file; at most 16 small reads, at the key press). F1 launches the app (`launch_app(entry, project, ctx)`, its second caller) with the Pattern's block: pattern in view, the block's first track and track count, rows, the 0-based instrument, `O3M_LAUNCH_FROM_TOOLS`; with no block `block_length` and `block_tracks` are 0 and `track` / `block_start` are the cursor's. A refused launch (the first-launch question, quarantine) is said inside the list (the strip waits behind a modal overlay) and keeps it up. The exit chord returns to Pattern with the cursor and the block untouched (`ModulesView::from_tools`; the project-change path of `poll_modules` too); an app opened from MODULES still returns there. F7 is refused silently while the view follows the play line (LIVE, or WATCH while playing), like selecting a block. The item list is one function (`tools_item`) with a count of fixed entries above the apps (0 today): OS-WAVEXP adds EXPORT PATTERN / EXPORT SELECTION by raising `kToolsFixed`, adding a Kind and a case in `tools_run`. The Pattern's F7 key row label is now `TOOLS` (it read `-`), which changes the Pattern goldens of the simulator.
10. **RHYTHM GEN** (`modules/apps/rhythmgen/`, 4.6 KB file, 136 B of state, no hot code, ABI 1.5, read_project + edit_project): up to four lanes (one per track of the block), HITS / LENGTH 1..64 / ROTATE / NOTE / PROB per lane, INSTR / VOL / MODE / SEED shared; the Euclid rule of the Fill dialog (`(i x hits) mod length < hits`, checked against `model::fill::euclid_hit` for every hits and length up to 64), rotation later by `rotate`, one xorshift32 draw per hit seeded from SEED and the lane through a hash, so a higher PROB only adds hits; F1 APPLY is one group (one `get_steps` + `set_steps` per lane, mask NOTE | INSTR | VOL, so FX are never touched), F2 VARY is SEED + 1 and an APPLY. **Decisions inside the spec:** (a) **the pages are the app's own, not OS parameters**: the app page lists at most eight parameter rows and has no paging, so 24 parameters would have been unreachable; the app declares none and draws pages 1-4 (lanes) and 5 (shared) itself, 5 rows or fewer each, navigated with Left / Right, Up / Down and the encoder (the OS keeps the Shift layer). The price is that its values are not remembered between launches and have no Learn; the defaults come from the block each time. (b) **The default NOTE is the step byte 49, "C-4" as the Pattern names it** (the model counts note 1 as C-0; the model's own default 60 shows as C-5). (c) The default HITS is a quarter of LENGTH (at least 1). (d) With no block the lane is 16 rows from the cursor, cut at the track's end.
11. **Tests** (`tests/module_edit_test.cpp`, `modules/apps/rhythmgen/tests/rhythmgen_test.cpp`): the layouts above; the capability gate for every subset; the codes of every entry for bad patterns, tracks, rows, counts, NULLs, masks and values; the group (one unit, the mask, UNDO / REDO byte for byte, empty group, order of calls, rate, from outside `input()`); the limits with exactly 2,048 accepted, the 2,049th LIMIT and the project byte-identical with no new generation, unit or redo loss; 4,096 calls; `set_tempo` in and out of a group; a group left open, a group left open by an app stopped for time, host time not charged; the **undo property** (24 seeds of random groups, then the same number of UNDOs gives every earlier snapshot, then REDO re-applies); a **fuzz** of every entry (600 frames of random calls, in and out of `input()`, with random undo and redo, under ASan and UBSan); TOOLS (the list, the follow refusal, the empty list, the context with and without a block, the way back, the item list); RHYTHM GEN through the whole stack and against the Fill dialog's Euclid.
12. **Cost** (`ci.sh mk66`, against the previous build): flash image +4,756 bytes (680,096 to 684,852), `.data` and SRAM `.bss` +0, `.ramfunc_l` unchanged at 27,512 (nothing hot was added), the module system's block in SDRAM 32 to 64 KiB (see 3). The simulator's Pattern goldens changed with the F7 label (192, regenerated).
13. **To verify on the unit** (`qa_tools.json`, QA-PAT-160..167, QA-MOD-070..079): F7 on the real key row, the list and the first-launch question, the block as context, one APPLY and one UNDO on a real project, the time of an APPLY of 4 lanes (`diag cpu`: the app's 4 ms budget does not include it, but the main loop stalls for it), the page's legibility at 800 x 330, and `diag mod` after leaving an app with a group open (never done by RHYTHM GEN).

## Amendment H: how slice H3b built the instrument parameters and four editing apps (OS-H3B, ABI 1.6, 2026-10-15)

Implementation decisions inside decisions 1(b), 5 and 7, amendment D.6 and amendment G; additive, reversible, no persistent format touched. Level C for the published ABI, B for the apps. The scope rule of the spec held: **no ABI entry goes in without a client in the same slice**. The route entries wait for H3c (no route type exists in the model), so 1.6 holds exactly what MUTATE and MORPH use.

1. **ABI 1.6** (`O3M_ABI_MINOR` 6). Appended after the 1.5 members; no capability bit, the header and the older tables untouched. Read table: `instrument_info(instrument, &info)`, `get_param_desc(instrument, index, &desc)`, `get_instrument_param(instrument, id, &value)`. Edit table: `set_instrument_param(instrument, id, value)` after `set_steps`. PODs: `o3m_instrument_info {size, kind, engine, param_count}` (16 bytes) and `o3m_param_desc {size, min, max, def, id, flags, group, reserved[3], name[16]}` (40 bytes). `instrument` is the number the Pattern shows (1..64, the step numbering). **The layout is proved three times:** compile-time assertions of every offset and size for the 32-bit target at the end of `o3module.h` (every module build checks them), the host-pointer offsets of **every member of the host, read, edit and io tables of 1.2 through 1.6** in `module_edit_test` ("abi 1.6: the published offsets ..."), and literal copies of the 1.5 tables (`ReadV15`, `EditV15`) through which an app reads steps and edits a group on a 1.6 OS. The loader's minor rule is unchanged (a file of minor 7 is refused, NEEDS NEWER OS). A new macro `O3M_TABLE_HAS(table, member)` is the way to ask whether the member you call exists; an app must **not** compare a table's `size` with `sizeof` of the whole struct, or an app of 1.5 rebuilt with the 1.6 header would refuse a 1.5 OS. RHYTHM GEN did exactly that and now uses the macro (the one edit outside the new apps). The OS lends the same newest table to every app of 1.3 or later, whatever minor it declares, so an app may use an entry of a later minor *if present* (CHORDS does, see 7).
2. **What the entries say.** `instrument_info.kind` is EMPTY (the slot holds nothing: OK, not RANGE), SAMPLE, MIDI or MODULE. `engine` is a sample's play engine (the project's byte: 0 auto, 1 modern, 2 Amiga, 3 12-bit, 4 8-bit), or for a module the **FNV-1a hash of the module's stem** (the name in the project's module table), equal for every instrument of the module and not for another module; two instruments **match** when kind and engine are equal (the rule MORPH uses; no engine id is published for modules, which have none). `param_count` is 83 for a sample (the model's table), the module's own number for a module that is loaded and bound (0 otherwise: the listing is the descriptor the Params page would draw), 0 for MIDI and EMPTY. A descriptor is the model's own (`core::ParamDesc`, `model/params.h`) or, for a module, `describe_module_param`'s: `min`, `max`, `def` in the parameter's unit, `name` upper case and cut to the page's 12 characters (**the field holds 16 bytes, the spec's 12 had no room for the NUL of a 12-character name such as GRAIN LENGTH**), `id` the project's field id (a sample's 0..13, 0x14..0x1C, `0x20 + 8e + f`, `0x60 + 4s + f`; a module's `0x100 + i`: they were already persisted in the project's MIDI Learn bindings and are never renumbered), `group` the model's page (VOICE 0, FILTER 1, ENV 2, SENDS 3, SOURCE 4) with the LFO rows of the modulation slots moved to **MOD 5** (as the MOD page shows them), or `i / 8` for a module (the pages of eight; S10 may name them later). Flags: **ENUM** (the value picks a name: every `choice` row, a module BOOL), **STEPPED** (not an enum, stored in a whole-number field, at most 64 apart: TUNE, BIT DEPTH, SLICE, a small module INT; an app that blends two values should switch between such values), **APP_WRITABLE**. Reads show the project as it is (an open group's writes are not seen), as `get_steps` does; a module parameter that the blob does not reach yet reads as the module's default (as the Params page shows it).
3. **APP_WRITABLE, conservative, and where it lives.** The set is one predicate, `model::instrument_field_app_writable(field)` (`model/params.h`), not a flag on every row of the table: a flag would have meant editing 40 rows of a table the whole OS shares for something only the module host reads, and the flag byte of `core::ParamDesc` is full of the UI's meanings (**deviation from the spec's "mark the descriptor table"**; the descriptor an app sees carries the flag, the model's rows do not). **Writable (61 of 83):** VOLUME, PANNING, TUNE, FINE TUNE, GLIDE, FILTER, FILTER TYPE, CUTOFF, RESONANCE, DELAY SEND, REVERB SEND, OVERDRIVE, BIT DEPTH (13); each of the six envelopes' AMOUNT, ATTACK, DECAY, SUSTAIN, RELEASE (30); each of the six modulation slots' LFO SHAPE, LFO SPEED, LFO AMOUNT (18). **Clear (22), for review:** PLAY ENGINE (the engine action rebinds the slot and refuses an Amiga the sample cannot play); the nine rows of the source page (PLAY MODE, WT POS, WT SIZE, GRAIN POS / LENGTH / SHAPE / LOOP, SLICES, SLICE: they go through validating actions that look at the sample, and GRAIN LENGTH and WT SIZE clamp against it); each envelope's ENABLE (6) and each modulation slot's SOURCE (6) (they change the voice's kind: an LFO is chosen when the descriptor is built, and ENABLE and SOURCE write the same two bytes). Not reachable at all: the sample, its points, the slices, the module binding, a MIDI instrument's channel (MIDI fields are S8b's and come later if an app needs them). **Every parameter of a module instrument is writable**: the module declared it, and the host (`write_module_param`) holds it to the module's own range. LFO rows are written although they only matter when the slot's SOURCE is LFO, because the user can set that on the MOD page and the value is then what the app wrote.
4. **`set_instrument_param` joins the group and takes the Params page's path.** A call is checked when made (a group open, not over a limit, a SAMPLE or a loaded MODULE instrument, a known id, APP_WRITABLE, finite and inside `min`..`max`; **nothing is clamped for the app**, a value one ulp past the range is RANGE, and NaN is RANGE because it fails the comparison) and **stored** as an op of its own in the H3a buffer (`EditOp::pattern` 0 marks it; the slot in `track`; the id and the float in one pool slot, a `ParamOp` of 8 bytes, the size of a step, so no memory was added). It therefore counts as **one write call and one of the 2,048 slots**, and a group may hold at most **`O3M_EDIT_MAX_PARAM_WRITES` = 64 accepted parameter writes** (review fold: `write_param` pushes each into the engine's 256-entry ring or a module's 64-entry one, which drop a change silently when full; the 65th is LIMIT and drops the group; a sample has 61 writable parameters, a module at most 32); the H3a limits (4,096 calls, 2,048 steps, whole-group rollback as "never applied") are unchanged and a group may mix steps, the tempo and parameters. At `edit_end` the action `module.app_group` writes the steps and the tempo through the Editor (`ModuleUi::apply_group`, which re-checks the parameter ops too, so a bad group writes nothing) and then each parameter through `write_param`, **the same function the Params page uses**: `Editor::set_param`'s own range and rounding (a whole-number field stores the value rounded), the module path (`write_module_param`) for a module, and `send_param_change`, so the engine, or a module's running instance, hears it as it hears a hand edit, and the journal records each change inside the group's one unit. UNDO restores the **exact float bits** (the journal holds old and new value) and `edit.undo` already sends the restored values to a module instance and rebinds a sample slot (more than 16 changes make the unit `applied_incomplete`, which the undo path handles). Rejected cases: a MIDI or empty instrument, an unloaded module, an unknown id and a non-writable parameter are RANGE and **do not poison** the group. The worst case, 64 parameter writes that all change something beside 2,000 steps, applies as one unit and undoes byte for byte (tested). **UNDO and REDO of a unit with more than 16 changes** (the Editor lists 16, `kAppliedMax`) resend every writable parameter of a changed sample instrument to the engine (`edit_actions.cpp`, beside the module blob's resend), so the engine matches the project at once, with the transport running (review fold).
5. **CHORDS** (`modules/apps/chords/`, ABI 1.5, 4.9 KB file, 140 B of state). The music is a header (`chords_math.h`): a progression is a list of scale degrees, the chord on a degree is the scale's diatonic one (major or natural minor; triads, or with SEVENTHS maj7 / min7 / dom7 / m7b5), the root is `12 x OCTAVE + pitch class + 1` folded into the octave (the Pattern's C-4 is 49), so I-V-vi-IV in C is C, G, Am, F and the same numbers in MINOR are Cm, Gm, A flat, Fm. Eight presets: I-V-vi-IV, I-vi-IV-V, ii-V-I, I-IV-V-IV, vi-IV-I-V, i-VI-III-VII, i-iv-v-i, the 12-bar blues (degrees 1 1 1 1 4 4 1 1 5 4 1 5). Both modes put a chord on rows 0, RATE, 2 x RATE ... of the target and **empty the note on the other rows**; **the progression plays once** (chords that do not fit are dropped; no loop, so a default RATE that does not divide the rows leaves the remainder empty instead of a one-row chord); the default RATE is the target rows divided by the number of chords (at least 1) and follows the progression until set by hand (Delete gives AUTO back). **CHORD FX** writes the root, the instrument and FX 14 Chord into FX2, FX1 when FX2 is taken, **in place when a Chord FX is already there**; a row whose two slots hold other FX gets the root without the Chord FX and is counted (`N WITHOUT FX: NO FREE SLOT`). The Chord value is the index of the chord's mask in `seq/fx.h kChordMask` (`docs/specs/OS-PFX.md`): major 5, minor 4, diminished 3, maj7 24, min7 20, dom7 23, m7b5 17 (every quality has its own entry, so SEVENTHS never falls back to the triad); **the app keeps its own copy of this map and `chords_test` checks each entry against the OS table** (the mask equals the chord's tones and no other entry is the same chord). **SPREAD** puts tone t on track t of the block, the first 3 tracks (4 with SEVENTHS), no FX; a block with fewer tracks writes fewer tones and says how many were left out; with no block CHORD FX and SPREAD use the cursor's track only (SPREAD writes one tone).
6. **The FX 14 finding (checked in the source).** `seq/src/sequencer.cpp` `pfx_note` (comment at 1596-1599, the branch at 1643-1648) builds the chord's other notes only `if (is_midi_slot(slot))`; **for every other instrument it does `++stats_.fx_ignored` and plays the root alone** (a sample or module voice is one a track: "no voice for the other notes"), and `seq/sequencer.h:52` says the same. So Chord FX is only worth writing for a MIDI instrument, and **the default MODE is CHORD FX for a MIDI instrument and SPREAD for any other**, as the spec had it.
7. **CHORDS decides that default from `instrument_info` while declaring 1.5.** The spec said CHORDS needs nothing new and declares 1.5, and also that the default depends on the instrument's kind, which only 1.6 can say. Both hold: CHORDS **asks `instrument_info` only if the table has it** (`O3M_TABLE_HAS`) and otherwise defaults to SPREAD, the mode that sounds on every instrument (an OS of 1.5 gets that; the test builds a 1.5 table and checks that `instrument_info` is not even called). MODE follows the instrument while it is `AUTO`; moving MODE by hand stops that (Delete gives AUTO back). Declared minimum stays 1.5: the file runs on an OS of 1.5.
8. **HUMANIZE** (`apps/humanize/`, ABI 1.5, 3.1 KB, 108 B of state). The target is the block (every track of it), or with no block the cursor's track for 16 rows from the cursor row; only steps with a note (1..128) are touched, and the write mask is VOL | FX1 | FX2 (notes and instruments are never in it). For each noted step two draws are always made (a delay, then a volume jitter), from xorshift32 seeded by SEED and the track's place in the target through a hash, **whatever the FX or volume of the other steps**, so a step's result depends only on its own place and the settings. The delay is uniform in 0..TIME (0..100, FX 2 Micro-move), the volume jitter uniform in -VOL..+VOL (0..64) around the volume of a step that already carries one, clamped to 0..127 (**review fold: a step with an unset volume is left unset**; the sequencer and the voices give it the instrument's own volume, `sequencer.cpp` `default_velocity`, and a written velocity would replace that, about doubling a volume-50 instrument; repeated APPLYs jitter the volume they find, so it random-walks); with VOL 0 no volume is written, with TIME 0 no delay. A step that already has Micro-move gets that slot's value replaced (also by 0); otherwise the delay goes into an empty slot, FX2 first; a step that drew a delay above 0 and has both slots taken keeps its timing and is counted (`N STEPS: NO FREE FX SLOT`). TIME 0 and VOL 0 make no group at all (nothing to undo). The result for a seed is **pinned** in the host test.
9. **MUTATE** (`apps/mutate/`, ABI 1.6, 3.3 KB, 1,060 B of state). On launch it reads `instrument_info` and every `get_param_desc` of the context instrument (it must be SAMPLE or MODULE: otherwise `SAMPLE OR MODULE INSTRUMENTS ONLY`) and keeps the writable ones (12 bytes each). `new = old + (r - 0.5) x AMOUNT x (max - min)`, clamped, with **r drawn from SEED and the parameter's id** (not its place in the list), so a parameter gets the same new value whichever GROUP is chosen and a GROUP is a subset of ALL; STEPPED and ENUM parameters move by the delta rounded (a two-value switch, whose delta is at most half a step, never flips). GROUP is ALL or one of the groups that hold a writable parameter (VOICE, FILTER, ENV, SENDS, MOD for a sample, no SOURCE page: nothing there is writable; PAGE 1.. for a module). AMOUNT steps by 5 % a detent; AMOUNT 0 makes no group. Only parameters whose new value differs are written.
10. **MORPH** (`apps/morph/`, ABI 1.6, 3.0 KB, 1,448 B of state). On launch it copies A's writable parameters into its state (A0, 332 bytes) and lists as SOURCE the other instruments with the **same kind and the same `engine`** (up to 63 `instrument_info` calls at launch; none gives `NO MATCHING INSTRUMENT`). APPLY writes `A0 + (B - A0) x POS` for continuous parameters; STEPPED and ENUM ones are A0 below POS 50 and B's from 50; **POS 0 and POS 100 are exact** (A0 and B to the last bit, special-cased so that float rounding of the blend cannot spoil RESET). A0 is the instrument as it was when the page opened, so APPLY is idempotent and a second APPLY blends from A0, not from the first result. F3 RESET sets POS 0 and applies it: A is A0 again, bit for bit. **No live sweep:** turning POS or SOURCE writes nothing; every F1 or F3 is one group, so one undo unit (the spec). PLAY ENGINE, the source page, ENABLEs and SOURCEs keep A's values.
11. **Every app** appears in Pattern F7 TOOLS below EXPORT and the rule, sorted by name (CHORDS, HUMANIZE, MORPH, MUTATE, RHYTHM GEN), is packed like RHYTHM GEN (`o3m_manifest` + `o3m_add_module` + `o3m_add_test`, version 1.0.0, caps `read_project,edit_project`), takes its target from the launch context, makes one group per F1 (or F2/F3), names the unit after itself (`UNDO MUTATE` ...), exits with F7+F8 and uses seeded xorshift32. They share `apps/common/o3m_edit.h` (text helpers, the seeded draw, the target block, the page layout). The pages are the apps' own (as RHYTHM GEN's), fixed layout from 480 x 288 up, checked by a test that no text leaves the canvas or overlaps another at 480 x 288 and 800 x 330; no OS parameters, so no Learn and nothing remembered between launches (as H3a). **Sizes:** humanize.tmod 3,148 B, chords.tmod 4,916 B, mutate.tmod 3,256 B, morph.tmod 2,956 B (the slab is 14 KiB); no hot code; nothing in the firmware image grew for them (they are SD files).
12. **Tests.** `tests/module_edit_test.cpp` (the 1.6 cases are at its end): the offsets of 1.2 .. 1.6 member by member; an app of 1.5 reading steps and editing a group through its own tables on a 1.6 OS; the gating of the four entries for every capability subset; `instrument_info` for all four kinds and bad slots; `get_param_desc` for the 83 rows of a sample against the model's own table (every min, max, def, name, flag and group) and the module's 11, `APP_WRITABLE` on exactly the 61; `get_instrument_param` against the project, the blob's short tail reading defaults; `set_instrument_param` outside a group, from a group, with every non-writable id, every unknown id (0..0x1FF), bad slots, the ends of the ranges, out of range, NaN, +/-inf; a group mixing steps, tempo, a sample's and a module's parameters being one unit with exact undo and redo and the module instance hearing both; the limits (2,048 parameter writes accepted, the next LIMIT; steps and parameters sharing the slots; 4,096 refused calls; the project byte-identical after a dropped group); a group left open; the worst case; a **fuzz** of the four entries with the others (600 frames, random instruments, ids, indices, sizes, NaN, NULL, in and out of `input()`, with random undo and redo, checking that the non-writable parameters never changed and every parameter stays inside its descriptor); the **undo property** over 16 seeds of random groups mixing steps, tempo and parameters of two samples and a module (every snapshot back by UNDO, forward by REDO, dropped groups no unit); the four apps through the whole stack (TOOLS list order, one unit named after the app, the Params values byte for byte, the module instance). Per app, `modules/apps/{chords,humanize,mutate,morph}/tests/` (15, 15, 11 and 11 cases) drive the host shared object on `o3m_test::FakeApi`, which gained instruments and `set_instrument_param` with the OS's rules, against oracles: the OS's chord table, an independent scale reckoning, a double-precision reckoning of the mutate and morph rules, the same SEED giving the same result with values pinned for HUMANIZE and MUTATE, the packed `.tmod` read back by the loader. The fake host is one at a time (its table functions have no context, like the real ones), so the tests that compare runs make them one after another.
13. **Not done, and why.** The route entries and MOD RECIPES (H3c, after OS-MODMX); creating a pattern from an app; MIDI-instrument fields (S8b's). The apps' values are not remembered between launches and have no Learn. The simulator goldens did not change (the simulator's card has no tool app, so no TOOLS list shot holds these apps).
14. **To verify on the unit** (`qa_tools.json`, QA-MOD-080..089, QA-PAT-210..213): the F7 list with the five apps, the first-launch question for each, CHORDS on a MIDI instrument (the external synth playing the whole chord) and on a sample instrument (SPREAD), HUMANIZE's delays by ear and in the shots, MUTATE and MORPH on a real sample and a TB-303, the Params page before / after / after UNDO, the module instance following (a sounding TB-303), the legibility of the pages at 800 x 330, and the main-loop stall of an APPLY of 61 parameters (`diag cpu`; the cost in the app's own 4 ms is credited back as in H3a).

## Amendment I: how slice H4 built the export writes and SMF EXPORT (OS-H4, ABI 1.7, 2026-10-15)

Implementation decisions inside amendment A and `docs/specs/OS-H4.md`; additive, no persistent format touched. Level C for the card writes and the published ABI, B for the app.

1. **ABI 1.7** (`O3M_ABI_MINOR` 7). `O3M_CAP_EXPORT_FILES` (16) is granted, only to a file of ABI 1.7 (in an older file the bit is a reserved field). The io table grows `export_open`, `export_write`, `export_close`, `export_status` at offsets 36..48 (size 52), NULL without the bit; `o3m_instrument_info` grows `midi_channel` (size 20, a 1.6 app's 16 bytes are filled as before). The offsets of every 1.2 .. 1.6 member are pinned by a literal copy of the 1.6 layout in `tests/module_edit_test.cpp`.
2. **Where it lives.** `app/app_export.h/.cpp` (a state machine and the ring, no path and no card call of its own); `SaveService::start_app_file` builds the names, applies the guard again and starts one NewOnly `AtomicSave` job whose `SaveSource` is the ring. A separate file keeps `module_ui.cpp` (already 1,700 lines) to the launch, the grant and the confirm.
3. **The guard** (`hal/save_guard.h`): `AppExport`, `AppExport/<app>` (folders), the Temp, and `AppExport/<app>/<stem>.<ext>` as a Target with the extension allowlist; no Backup form, so a finished file can be neither renamed nor removed. `kPathCap` 96 holds the longest path (78 bytes).
4. **A user's save wins (deviation from "waits its turn or NO_CARD at open").** The job of an app's file exists from `export_open` to its commit, so waiting would make the user's key wait for the app. The save layer already has one pattern for a job that must not hold the user up (the RECENT file, `yield_recent`); an app's file uses it, with two limits found in review: the cancel happens in `launch()` (and the plan and stems steps), that is, only once the user's request has passed its own gates and really starts, so a refused or no-op request never kills an export; and a file that has reached its read-back or rename (`AtomicSave::past_write`) is never cancelled, the user's request answers Busy for that moment. The app reads FAILED when it is cancelled. Tested (`app_export_test.cpp`).
4b. **An open file times out.** An open file holds the job slot, so `busy()` (loads, new, firmware update, put/rm, the settings and RECENT autosaves) is true while it is open. `AppExport::tick` (from `SaveService::poll`) aborts a file that is open with no write, no drain to the card and no close for **`kIdleMs` = 20,000 ms**: FAILED, Temp removed. A closed file is not timed (the job ends by itself). Known limit: the idle clock is the one `tick` last saw, so a file opened before the first poll tick would be timed from 0; `poll` runs every pass from boot, so this does not happen in practice.
4c. **The name probe is bounded.** `export_open` looks for a free `_001` .. `_999` inside the app's call, so a plain scan (999 directory lookups) could pass its time budget: 1..8 are probed one by one, then the step doubles and a binary search closes in (about 25 lookups at most). With the taken numbers in one run the lowest free number is chosen; with holes some free one; LIMIT when 999 and the probes before it are taken. Known limit (accepted): when `_999` is taken, LIMIT can come back although a lower number is free (a hole the probes did not visit); the probe never returns a taken name, and the commit never replaces a file.
4d. **The confirm is remembered with its bits.** The once-per-boot acknowledgement stores the confirm bits (edit_project, export_files) per stem; a file replaced by a version that asks for more asks again.
5. **The 31-byte rule, the caps, the abort and the heal** are as in the spec; a retry of the atomic save that would need `begin()` again fails the export (the drained bytes are gone). The ring is 16 KiB in SDRAM_STATIC.
6. **The confirm** is one line of at most 48 characters: `WRITES FILES TO APPEXPORT/<APP>: F1 AGAIN` (a long name is cut with `..`), and `EDITS (UNDOABLE) + WRITES FILES: F1 AGAIN` for an app with both bits (no room for the folder as well; the guide names it). `ModuleUi::launch_message` carries it to the MODULES strip and the TOOLS list.
7. **SMF EXPORT** (`modules/apps/smfexport/`, ABI 1.7, read_project + export_files, 5.2 KB file, 2,840 B of state). File `PAT<nnn>.mid` (`PAT<nnn>_SEL.mid` for a block) in `AppExport/smfexport/`. Type 1, PPQ 96, tempo and 4/4 in the first track, one track per track with a note. Micro-move uses `micromove_start(v) / 2` ticks (a copy of the core's formula, checked against it for every value). A note ends at the next note or at an Off, Cut or Fade step (v1 does not tell them apart) or the end of the range. The instrument a note with none plays is the last one the track names above the range, else the cursor's. The header counts the tracks before they are written, so the writer always writes that many (a track that lost its notes is written empty). Other FX are counted by number on the page; Chord FX 14 is not expanded.
8. **Sizes** (MK66 image, against dev 2368bb4): FLASH +2,856 B (724,336 to 727,192), SRAM_U +0, SDRAM_STATIC +16,384 B (82,880 to 99,264: the ring).
9. **To verify on the unit** (`qa_h4.json`, QA-MOD-090..098) on a card: the confirm, the F7 list, an export of a pattern and of a block, a second export that becomes `_001`, the `.mid` files on a computer, a pulled card (no stray final file, no Temp). Nothing of H4 has run on a Tracker.
10. **Not done.** Reading `AppExport` (C2), whole-song export, Chord expansion; the app page lists no capability badges (the OS shows none for any bit today).

## Amendment J: the tap's sample stores follow the readers (OS-BUG-TAPWRITE, Level C for the render write, 2026-10-18)

Implementation decision inside decision 3(b) and amendment E item 7; additive and reversible, no persistent format, no ABI member or offset touched and no ABI minor bump, but **one behaviour of ABI 1.4 an app can observe changes**: the first `tap_latest` / `tap_stream` call returns 0 (a return of 0 was already legal), there is no history before it, and a reader must poll every frame (the SDK header comments, `module/sdk/README.md`, `docs/guides/app-modules.md` and `docs/CHANGELOG.md` say so; the shipped TUNER and SCOPE SPECTRUM already read every frame and LOUDNESS VU reads no samples). New Community OS behaviour.

1. **The finding (unit, image int.6, transport stopped, Loudness VU open, QA-MOD-023).** The tap work of a block read mean 1,765 / max 6,077 cycles (9.8 / 33.7 µs; 0.7 % / 2.3 % of a 261,120-cycle block). Amendment E item 7 wanted mean below 360 and max below 3,600 (20 µs), and named the fallback of a 4-block ring in SRAM_U.
2. **The cause, from the code (the split below is an inference to confirm with the next unit run).** A block with the tap on is: `mono_mix` (SRAM_L loop), `meter` (SRAM_L loop), 3 stats stores, **32 sample stores** and one head store, the ring and the stats being in SDRAM behind the cached alias. The compiled store loop is 9 instructions an iteration, 32 times, each with a store to SDRAM (`AppTap::push`, `.ramfunc_l`); the host estimate took a store at 10 to 28 cycles and 600 to 1,400 cycles at worst, and the unit read 1,765 as a mean, so the stores and their bus waits (the loop alone is about 300 cycles before any wait) are probably the largest part, and the two kernels (estimated at 300 to 500 together, 150 to 250 each as in amendment E item 7; an estimate, not a measurement) and the counters the rest. It is **not paid with no reader**: with the source Off a block costs one relaxed load, and the tap is Off before an app selects a point and again when it stops (`release_host`). With Loudness VU open it is paid in full, although the VU calls only `tap_levels` and never reads a sample. The max is a wall-clock figure of a priority-128 render that the audio DMA, SysTick, MIDI UART, USB and completion interrupts preempt, so a long interrupt inside the window shows as max; the figure does not separate SDRAM jitter from preemption (open research question: `diag bench kernels` minimums against these means will).
3. **Why the ADR's numbers are not expected to be met by the fallback either.** `mono_mix` + `meter` alone are estimated at 300 to 500 cycles (150 to 250 each, amendment E item 7), so "mean below 360" is not expected to be met with a ring in SRAM_U either; to be confirmed with `diag bench kernels` on the unit; the 4-block ring would also cost 512 B of SRAM_U plus the stats (the margin is about 1.1 KB), end the 93 ms ring that lets a 33 ms frame read gaplessly, and not move the mean below the kernels. The mean target is therefore not judged any more; the max rule (3,600 cycles) stays for the levels-only run.
4. **As built.** `AppTap` has a `samples` flag (main loop writes, the render reads it once a block, relaxed, default set). While it is clear `push()` still computes the block's peak and sum of squares and publishes the stats slot and the head, but stores no sample (`SampleRing::skip`: the head moves on, the words keep the lap before: stale). `ModuleUi` clears it when an audio_tap app starts, sets it at the app's first `tap_latest` or `tap_stream` call (the flag first, a compiler fence, then the head: the freshness point `tap_fresh_` and the stream cursor move to head + 2 blocks, the rule a select already used, so no stale word is ever returned) and puts the default back when the app stops. `tap_levels` is unchanged and never needs the flag. Observable by an app: the first `tap_latest` / `tap_stream` call returns 0 and the real frames begin two blocks (2.9 ms) later; a stream no longer begins at the select but at its first call (the SDK comment and `docs/guides/app-modules.md` say so). TUNER and SCOPE SPECTRUM read samples and pay what int.6 measured; LOUDNESS VU pays the kernels, 4 stores and the counters.
5. **Sizes** (MK66 image, against dev a117093; the firmware code of dev equals the pre-change build): FLASH +100 B (812,184 to 812,284, after the review fold), SRAM_L +16 B (49,864 to 49,880: `AppTap::push` grew from 112 to 132 B), SRAM_U +0, SDRAM_STATIC +0 (the flag is one word of the AppTap in the sample arena, +4 B of the 10.8 MB arena). `ci.sh host` 199 of 199 and `ci.sh mk66` 19 of 19 on the folded branch; `ci.sh qemu` 57 of 57 ran before the fold (the fold changes comments, a compiler fence and one access specifier, 24 B of flash less, no behaviour).
6. **Tests.** `audio_app_tap_test.cpp` (samples off: exact stats, nothing stored, head moves; on again; the graph honours the flag), `module_host_api_test.cpp` (launch is levels-only, the first read of either call arms and withholds two blocks, a launch after an exit starts levels-only again, tap_levels never arms), `audio_taps_thread_test.cpp` (a smoke test: the flag toggled against a running writer, the ranges from the computed position are whole blocks of the writer; the proofs of freshness are the first two files).
7. **To verify on the unit.** QA-MOD-023 twice in one session (`qa_modules.json`): Loudness VU (levels only; the step is soft until the next image gives figures, because the max is a wall-clock figure and the run plays the song: a max of 3,600 cycles or more is reported) and Scope Spectrum (samples; reported), with `diag bench kernels` for `k_mono_mix` and `k_meter`. Expect the VU mean to be about the two kernels plus 150 cycles and the Scope mean to be near int.6's; the difference is the store cost.
8. **The sample readers.** **Decision: TUNER and SCOPE are accepted as measured (the max rule is waived for them), decided by the orchestrator under the maintainer's delegation, 2026-10-18.** Options (b) to (d) stay open, nothing built. (a) Accept: 0.7 % of a block at the mean and 2.3 % at the worst, inside the render's 60 % budget, only while TUNER or SCOPE is open. (b) Take the 32 stores out of the render: the render writes the mono block into a 2-block SRAM staging (256 B of SRAM_U) and a software interrupt below the render (priority 160, a new IRQ line and an irq-table row) drains it into the SDRAM ring; the total CPU is the same, but the stores leave the render's deadline. (c) One fused `mono_mix` + `meter` kernel (about 100 to 150 cycles less, for every tap user). (d) Move the render-private cost counters (20 B, about 8 SDRAM accesses a block, outside the timed region) from the AppTap in SDRAM to the Graph in SRAM_U, about 150 to 200 cycles a block that `diag cpu` does not show.

## Amendment K: how OS-APPUX S3 built ABI 1.10 (2026-10-19; the decisions are in `docs/specs/OS-APPUX.md`)

ABI 1.10 appends four members to the io table (`get_transport`, `set_own_param`, `play_note`, `stop_note`) and one capability bit, `O3M_CAP_PLAY_NOTES` (64, the first above the six frozen values, no confirm: it only makes sound). Nothing older moved; `o3m_ui`, the descriptor and the host table do not grow. `set_own_param` keeps a declared row with the project (`APPM` 1.1: up to twelve apps; the layout is that of 1.0, written as 1.0 while six or fewer are stored) and the launch hands the kept rows to `set_param` before `enter()`. `play_note` goes through the live-note path (source `kLiveSourceApp`): four held notes, eight calls a frame, every note ended when the app's host is released; a MIDI instrument is not routed for an app. A screen button on an app page leaves the app (an OS change, not an ABI one). An app built at 1.10 has no OS parameter column. Conditions C1 (a table entry is NULL without its bit) and C4 (the six frozen values) hold.
