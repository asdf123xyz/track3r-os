# OS-KEYROWDLG: the F-key row says what the keys do while a dialog or a question is up

Status: **decided, docs only** (spec session, 2026-10-17; revised the same day with the maintainer's decisions).  Amended 2026-10-18 (OS-APPUX amendment 3): S5 also carries the exit part of OS-APPUX S1 (F8 BACK, Play withheld, F7 + F8 kept). The maintainer said "go with recommendations" (2026-10-17); Fable answered the decision table of section 6, all (a), and its gap fixes are in the design. Line refs are `dev` 62dddbb. Trigger, the maintainer's request (2026-10-17): when NEW is hit in the File view, or at any other place that tells how the F-keys work, the actual F-keys should show the options, not only the dialog; detect all such places. Answer: **yes, possible, and small** (one table, no binding change, about +0.5 KB flash [est] for S1-S4). Everything proposed is **new Community OS behaviour**; no parity is claimed. **S1-S4 are Level B** (visible UI and goldens; no bindings, formats, ABI or audio path change; the boot-disk slice also needs one unit look) and are in the alpha. **S5 is Level C** (it changes the published module ABI, 1.9) and comes after the alpha.

## 1. The audit

### 1.1 How the key row is drawn and chosen today (verified in code)

- **Labels are the screen's.** `Screen::soft_keys()` gives eight labels, `soft_keys_shifted()` / `shift_row()` the Shift row (`app/include/o3os/app/screens/screen.h:126-134`). `key_row()` (`:148`) returns the Shift row while Shift is held and `follows_shift()` (`:143`: no overlay, not a capturing screen), else the plain row. Nine screens call `ui::soft_keys(r, f.keys, key_row(*this, view, plain), 8[, dim, hot])` (`app/src/screens/*.cpp`; 13 row sites in all); Pattern goes through `PatternView::Status::soft_keys` (`pattern_view.cpp:371`), Instrument through `params_key_row` (`params_screen.cpp:813`), File swaps the table by page (`file_screen.cpp:315-327`). The renderer is `ui::soft_keys` (`ui/src/components.cpp:51`): a `dim` mask (a key that answers and refuses) and a `hot` mask (inverted chip: the key in force). A label is at most 8 characters (`tests/shift_labels_test.cpp:108`). Blank (`""`) already means "nothing here" (OS-MODPAGEKEYS).
- **Three overlays own the row.** `ViewState::overlay_keys()` (`view_state.h:179`) is true for Navigator, Fill and ExportProgress only; the screens skip their row then (all 13 row sites guard on it) and the overlay paints its own on the frame band (`overlays.cpp:372-377`, `fill_overlay.cpp:115-117`, `export_overlay.cpp:73-75`; tables `overlay.h:77, 201, 215`). That is the OS-SMALL2 fix ("F1 GOTTERN": the screen's labels showed through the dialog's on the unit), so the screen must draw **no** row under an owner; a repaint over it is not trusted.
- **Every other dialog and question leaves the screen's row in place** and says its keys elsewhere: a dialog footer (`draw_key_hint`, `app/src/screens/dialog.cpp:38`) or the strip text. Seen in the simulator gallery: the Learn dialog says `F8 BACK` over `PATTERN LENGTH JUMP FILL PREVIEW INVERT TOOLS UNDO`; the engine picker says `F1 SELECT  F8 BACK` over `1-8 9-16 - - - <05 07> UNDO`.
- **What a key really does** is the binding. A modal overlay's context is first in the chain and captures: an unbound key is swallowed (`core/src/binding.cpp:57-78`). Shift+Fn in a modal context resolves to Fn through the unmodified retry (`:60-70`) unless the context binds the Shift key (the Navigator does, `bindings.cpp:784-791`). A strip question is **not** modal: the other keys run their own action and take the question back with `FileView::ask_clear()` (`file_view.h:52-77`, `file_actions.cpp:247-318`), and the question only counts while its text is the head of the strip (`new_question_open`, `file_actions.cpp:98-105`).
- `docs/ui/ui-map.md` item 13 ("labelled on its key row") and item 10 ("F8 BACK on every key row, which holds today") are true of the dialogs' footers, not of the F-key row. This item makes them true.

## 2. The rule and the smallest design

### 2.1 The rule

1. **A dialog that owns the F-keys owns the row**: the row shows that dialog's options, nothing else; a key it does not accept is **blank** (decided, row 2 of section 6). Blank, not dim: dim already means "answers and refuses with a reason on the strip" (`ui/src/components.cpp:51`), and a dead key does not answer. Applies to every modal overlay (A1-A10), the boot disk (D1) and the INPUT TEST screen (G1: a screen, not an overlay, with two chords), and, in S5, to the app pages (C4: the app declares the labels).
2. **A question on the strip** (the next press of a key answers it) puts its answer on the key: the answer keys show their word, inverted (`hot`), the other keys **keep their label**, because they still work and take the question back (today's behaviour, B1-B8; decided, row 3). "Press again" confirms keep the key's own word plus `?` (`OPEN?`, `APPLY?`), as Learn's `CLEAR ALL?` already does.
3. **Shift**: the row of a dialog does **not** follow Shift, **unless the dialog declares Shift options**, as the Navigator already does (`kNavigatorShiftKeys`, `overlays.cpp:377`; `owner_row(.., bool shift, ..)`). Under any other dialog Shift+Fn acts as Fn (`core/src/binding.cpp:60-70`), so the plain row is the truth. Under a dialog with Shift options (today only the Navigator: Shift+F7 CLOSE, Shift+F8 GO, Shift+F1..F6 bound to `ui.none` and shown `-`) the row shows that layer while Shift is held. A question answered on Shift+F7 (B3, B7) marks the Shift layer's key, as every screen's row does (decided, row 4).
4. **A label is at most 8 characters**; the long phrase (`KEEP INSTRUMENTS`) stays in the dialog line and on the strip, from the same table (decided, row 1: the hints stay in the dialogs too; the line carries the long words, the row the 8-character word).
5. **One table, three readers**: the key row, the dialog's hint line and the strip's question text are all made from one `KeyPrompt`; the bindings stay the truth about what a key does, and a test resolves them against the table. A **lint keeps the text, the row and the bindings in agreement for good** (S4, mandatory: section 5), so a later dialog cannot name a key outside the table.

### 2.2 The design: one table, one function, no new state

New `app/include/o3os/app/key_prompt.h`, `app/src/key_prompt.cpp`:

```cpp
struct KeyOption { std::uint8_t key;    // 0..7 = F1..F8, 8..15 = Shift+F1..F8
                   const char* label;   // <= 8 chars, upper case: the key row ("" never listed; "-" only for a Shift key bound to ui.none)
                   const char* words; };// the phrase of the dialog line and the strip text; null = label, "" = not in the line
enum class PromptKind : std::uint8_t { Owner, Question };
struct KeyPrompt { PromptKind kind; const KeyOption* options; std::uint8_t count; };
struct KeyRow    { const char* label[8]; std::uint8_t dim, hot; };      // 18 bytes on the stack
struct PromptState { const KeyPrompt* prompt; std::uint16_t live, hot; }; // bit per option
PromptState prompt_in_force(const Model&, const ViewState&) noexcept;    // pure: reads view.overlay, view.disk_keys (S3) and the existing question flags
bool owner_row(const PromptState&, bool shift, KeyRow&) noexcept;        // every key blank except the live options; the Shift layer only if the prompt declares one (rule 3)
void patch_row(const PromptState&, bool shifted, KeyRow&) noexcept;      // a question's answers over the screen's own row
int  draw_prompt_hints(ui::Renderer&, int x, int y, int h, const PromptState&) noexcept; // the dialog line, same options
```

- **Owners.** `overlay_keys()` becomes `overlay != OverlayId::None || disk_keys != DiskKeys::Off` (every modal overlay owns the row; Notify is never in `view.overlay`; `disk_keys` is S3's), and `follows_shift` (`screen.h:143`) tests `!view.overlay_keys() && !screen.captures()` instead of `view.overlay == None`, so the two cannot drift. `render_scene` (`app/src/screens/scene.cpp:10-21`) paints the owner's row once, on the frame band, after the overlay: `panel(f.keys)` then `ui::soft_keys(.., row.label, 8, row.dim, row.hot)`. All 13 row sites already skip on `overlay_keys()`, so **no screen changes**. The three hand-written row paints (Navigator, Fill, Export) and their three tables go; the seven footer chains of `draw_key_hint` become `draw_prompt_hints` (net code removal). The Navigator, Fill and Export rows must come out byte-identical, with one deliberate change (Shift+F6, next bullet).
- **The Navigator's Shift row (Fable's gap (f)).** Shift+F1..F6 are all bound to `ui.none` (`bindings.cpp:786-791`), yet `kNavigatorShiftKeys` (`overlay.h:78`) shows `-` on F1..F5 and blank on F6. In S2 the table lists six inert Shift options with label `-` and empty words (not in a dialog line): Shift+F6 reads `-` too, and `tests/overlay_test.cpp:522-527` changes `i < 5` to `i < 6`. A Navigator frame with Shift held changes by one glyph (`update_goldens` tells whether any golden holds one); every other Navigator frame is byte-identical. This is the one Shift layer a dialog declares; every other dialog's row stays plain under Shift (rule 3).
- **The boot disk (D1) and the one-guard decision (Fable's gap (c)).** On the boot disk `view.overlay` is `None` (the strip is a persistent notice on the app's own Pattern screen, `app_main.cpp:2429-2437`), so the 13 row sites would still draw the Pattern's labels. Two ways: (i) fold the new `ViewState::disk_keys` into `overlay_keys()`; (ii) leave `overlay_keys()` alone and add a second guard to the 13 sites and Pattern's status. **Chosen: (i).** OS-SMALL2 ("F1 GOTTERN") is the lesson that a site under an owning row must not depend on a guard of its own: with one predicate, read by the 13 sites, by `follows_shift` and by the scene painter, the next screen or the 14th site cannot forget it, and a test needs only the predicate. (ii) spreads one rule over 14 places and leaves a slip to be caught by a golden. The cost of (i) is that `overlay_keys()` is no longer a function of `overlay` alone: one more compare, inline, nothing else. `DiskKeys` is `Off | Restart | Confirm | Finishing`: `Restart` is eight `RESTART`; `Confirm` (the "computer may still be writing" warning) eight `AGAIN?`, hot; `Finishing` (the restart is waiting for the command in flight, `disk_restart.h`) eight blank, since no key acts any more.
- **INPUT TEST (G1, Fable's gap (e)).** A screen, not an overlay (its context captures, so `follows_shift` is already false and `overlay_keys()` is not involved). `kInputTestSoftKeys` (`input_test_screen.h:9`) becomes `"", "CLEAR", "CLEAR", "EXIT", "EXIT", "", "", ""`: F2/F3 `CLEAR` and F4/F5 `EXIT`, the same word on both keys of a chord, as the app page does for F7 + F8 (`modules_screen.h:11`); the other keys are blank (the screen sees them raw and they light their cell; nothing else happens). `render` draws `ui::soft_keys` on the footer band in place of the left text of `:140`. The footer's right-hand readout (AGE, MAX, EVENTS, `:141-150`) would share the band with the eight cells, so it moves; where (the strip, which already carries the health line, or the caption row) is the implementer's call, looked at on the three themes. The six goldens `gallery/inputtest_{typical,worst}_{amiga,black,white}` move. S2's test resolves the two chords through the INPUT TEST context (`bindings.cpp:876-877`) the way test (1) resolves taps.
- **Live masks** (the same function serves the dialog line and the row): Learn F1/F2 with a focus parameter, F3/F4 with bindings, F4 hot while `view.learn.confirm` (label `CLR ALL`, `CLR ALL?` while hot: `CLEAR ALL` is 9 characters; the words stay `CLEAR ALL`); Navigator F8 when the chosen cell is a built screen; choosers F1-F3 (the open one hot) and F8 BACK; picker, Tools, play mode `F1 SELECT|RUN|SELECT`, `F8 BACK`; text entry F1 TYPE, F2 CAPS, F6 AUTO for Save As only, F7 CANCEL, F8 SAVE|OK; step popup F8 CANCEL; Fill F1 FILL, F8 BACK; export F8 CANCEL.
- **Questions.** Only three screens can ask (File, Config, Modules), so only their three row sites (`file_screen.cpp:327`, `config_screen.cpp:336`, `modules_screen.cpp:132`) call `patch_row` after `key_row()`. Tables: `new_choice` F3 `ALL`, F1 `KEEP INS` (words `ALL`, `KEEP INSTRUMENTS`); `confirm_new` F1 `OPEN?` / `IMPORT?`; `confirm_purge` Shift+F7 `PURGE?`; `og_ask` F1 `EXPORT?`; Config `params.armed` F7 `APPLY?`, `params.defaults_armed` Shift+F7 `RESET?` (the Shift label `DEFAULTS` plus `?` is 9 characters); a pending launch confirm F1 `LAUNCH?` (Tools: `RUN?`, an Owner row there). **Liveness is one predicate**, `file_question_live(view)` = flag set and the question's text is the head of the strip: `new_question_open` and the row both call it, so a question queued behind another message marks nothing, as it answers nothing.
- **App pages (C4, S5, after the alpha; Fable's gap (a)).** This is the key-row part of OS-APPUX 3.1 **and the exit part of its old S1** (amended 2026-10-18, OS-APPUX amendment 3): F8 BACK, F7 + F8 kept as the escape hatch, Play withheld from the app; and nothing else of that spec (no app grammar 3.2, no 1.10 slice with `set_own_param` and `play_note`, no screen buttons leaving the app). **ABI 1.9**: `o3m_ui` grows one member at its end, `const o3m_keys* (*keys)(void* state)` (APPUX 3.1, option A: called once a frame before the page draws and after every `input()`; it returns 16 labels, `f[8]` and `shift_f[8]`, each up to 7 characters, NULL or `""` for a blank key). `o3m_ui.struct_size` carries the new member, so the descriptor does not grow and a 1.2-1.8 app (no `keys`) loads and runs exactly as today with the legacy row `-- -- -- -- -- -- EXIT EXIT`. The host copies the labels into the module host block (128 B, SDRAM, no SRAM), validates them (printable ASCII, cut to 7), and draws them with the same `ui::soft_keys` and the same blank rule; the Shift row while Shift is held (`follows_shift` gets one exception, an app that declares `keys`). **The exit changes (amended 2026-10-18, OS-APPUX amendment 3)**: F8 reads `BACK` and returns (one level: Pattern when launched from TOOLS, else MODULES), withheld from `input()`; Play is withheld too and drives the transport; the chord F7 + F8 stays the escape hatch. The legacy row reads `-- -- -- -- -- -- -- BACK`, so the row never reads `EXIT EXIT` between slices. The app labels F1-F7 and Shift+F1-F7 (F7 shows the app's label or `-`; an app that labels F7 gets it, the chord still wins), and its F8 slot is reserved and ignored (the OS draws BACK there). Pads and Rec still reach the app. Key events reach `input()` raw, as now: the OS only shows what the app says. The 12 shipped apps declare their labels in the same slice (labels only; their grammar is OS-APPUX S2 and S3), and the S4 lint grows a rule for `modules/apps`: an app whose body names `Fn` must label `Fn` in its `keys()`, checked by the per-app test. Cost [est] from APPUX 3.1: flash +1.4-2.2 KB (the key row +1.2-1.8, the exit part +0.2-0.4), SRAM 0, CPU nil, to be measured. Level C (published ABI): section 5, S5.
- **Text from the table.** The NEW strip text is built from its table (`NEW PROJECT` or `UNSAVED CHANGES`, then `F3 ALL, F1 KEEP INSTRUMENTS`; 44 characters, the strip holds 48) by `prompt_text()` into a `FixedString<48>`; `new_question_open` and `file_question_sync` compare with the same builder. A unit test pins the strings to today's, byte for byte.

### 2.3 Cost and constraints

- **No allocation, nothing real-time.** Constexpr tables; `KeyRow` is 18 bytes on the stack; the work is O(8) a frame, on the main loop's draw path, only while a prompt is live. No audio, ISR, render or SD code is touched; no `double`.
- **Flash** about +0.5 KB [est] net for S1-S4 (about 45 options at 12 bytes plus the composer, minus the three row paints and seven hint chains), and S5 adds +1.4-2.2 KB [est] (APPUX 3.1 and the exit part of its old S1, (amended 2026-10-18, OS-APPUX amendment 3)); SRAM 0 (stack 18 bytes; S5's 128 B are in the SDRAM host block); to be measured and recorded per slice. **Display list**: an owner's row replaces the screen's, so no state grows; `ctest budget` stays at or below 1792 words.
- **Unchanged**: bindings, actions, which keys cancel, every format; the module ABI until S5 (S1-S4 do not touch it). No new `ViewState` field except S3's `disk_keys`.
- **Hazard**: an 8-character inverted label is 2 px wider than a plain one: look at `KEEP INS` on the three themes; fallback `KEEP`.
