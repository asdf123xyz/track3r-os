# OS-BUG-PASTE24: an OG instrument at VOLUME 100 jumps from +0 dB to +24 dB at its first Params edit

BACKLOG row OS-BUG-PASTE24, reopened 2026-10-16; the maintainer chose **option C** the same day. **Level C** (instrument volume is a persistent field and the sound of every import; a sudden +24 dB is a hearing and speaker risk). This is phase 1: root cause as far as the source shows it, acceptance tests (expected-fail until the fix), the fix design. **No fix is in this phase.** Classification: the anchors of the level law are documented in the release notes (PAR-023; not verified; smoothing.h THE LEVEL LAWS) and the curve between them is this OS's model, an open research question (Q) with no capture in the repo; the import mapping and the Amiga reading below are `new Community OS behaviour`. **Phase 3 (spec fold, 2026-10-16): the maintainer answered Q1 and Q2 (decided by the maintainer, section 8); D2, D3 and D4 are no longer on hold and are specified below as slices (section 9). Implementation of D2, D3 and D4 starts only after the risk reviewer's verdict on this spec.** Risk review of 6cd231e: GO WITH CONDITIONS; its findings are folded in (findings 1..9, marked [RR1]..[RR9] below). Anything this fold chose that the maintainer did not state is marked "default, to confirm by the maintainer" (collected in section 14).

## 1. Symptom

Unit, v0.5.0, OG project `Projects/t-v16`, instrument 1 KICK, console `inst 1`: after the load `vol 100 gain +0.0 dB`; after a PLAY MODE change (any Params edit that rebuilds the descriptor) `vol 100 gain +24.0 dB`, and back to One shot it stays +24.0 dB. A VOLUME of 50 reads +0.0 dB. The host does not show it. (The tester's later log shows the report fits the boot demo project, whose instrument 1 is KICK at VOLUME 100, better than t-v16: R0.)

## 2. Root cause

**R0. The demo kit: the most likely root cause (found by the risk review, supported by the tester's log).** At boot, and for a project with no sample instrument (`demo_then_modules`), the platform installs the demo kit (`install_demo`, `platform/mk66/src/app_main.cpp`). It bound `kit.sample[i]` straight into the voices at the descriptor's default gain, unity (`SampleDesc::gain`, `voices.h:451`: +0.0 dB), while the four demo instruments it added said **VOLUME 100** (`model/src/demo.cpp:33`; KICK is slot 1, `demo.cpp:9`). The first rebuild of a descriptor (any Params edit: `rebind_now` -> `make_sample_desc`, `sample_bank.cpp:509`) reads 100 through the document's law (the 1.2+ law at boot) and gives **+24.0 dB**; VOLUME 50 gives +0.0 dB, the same law at unity. That is the reported behaviour to the digit: `inst 1` KICK, `vol 100 gain +0.0 dB` before, `+24.0 dB` after a PLAY MODE change, and it stays.
Evidence from the unit (tester, v0.6.0, console `log` and `load`): the only `the project has no sample instrument: demo kit` line is at boot (3598 ms), before any load, and loading `Projects/t-v16` prints none. t-v16 (OG v16, 12 patterns) has 16 real sample instruments (16 samples loaded, 0 missing, 7595 KB; beat slice, one shot, wavetable) and 16 MIDI instruments in 49..64; after a reload `inst 1` reads mode 5 (beat slice), `vol 50`, `gain +0.0 dB`, and the 50 comes from the file (`project.mt`, 2320 B). So the original repro fits the **boot demo project** (instrument 1 = KICK at VOLUME 100), not t-v16 (an earlier reading of this spec assumed t-v16 had no sample instrument; it has sixteen). The next unit run confirms it with D5: on the boot project `inst 1` reads `... law 12 demo` and, before the fix, steps by 24 dB at the first Params edit.

**R1. The law is not data (the class of bug, still real).** An instrument stores a bare level 0..100 (`SamplerParams::volume`). Which gain that is decides `audio::LevelLaw` (`level_gain_q16`, `audio/src/graph.cpp:30`): Og1114 puts 100 at 0 dB (65536), Og12 puts 50 at 0 dB and 100 at +24 dB (1038676). It was runtime state in three copies (the sample loader's `law_`, `SampleBank::law_`, `VoicePool::law_`), set by `begin_samples()` and nowhere derived from the document, so any descriptor written outside that path (R0) or any copy that drifted would be a +-24 dB step at the next rebuild. Phase 2 makes it the document's: `Project::volume_law()` (runtime only), read by every rebuild (D1 below).

**R2. Two more defects of the same shape, confirmed by the tests (they wait for the maintainer, section 3).**
- *OG below 7 saved native.* A native project plays at Og12 (`app_main.cpp` `begin_samples`); the native file carries no law. An OG project of version < 7 at VOLUME 100 (0 dB) saved as `.o3pj` and loaded again plays at +24 dB. Test: `og samples: an OG v6 project at VOLUME 100 saved native and reloaded ...` (expected-fail).
- *Imports are born at +24 dB.* MOD, S3M and MED map the tracker volume 0..64 to a linear percent (`formats/mod/src/map.cpp:420`, `formats/med/src/med_map.cpp:910`), so 64 becomes level 100, which Og12 plays at +24 dB. The tracker volume command has the same inverse (`voices.cpp:1576`).

**R3. Latent, recorded as a new item (not in this change).** The OG export writes version 16 for a project whose law was the 1.1.14 table (`docs/formats/og.md:105`, `:231`), with the levels unchanged, so under our 1.2+ law the exported file would read +24 dB (what an official unit plays is an open research question). Candidate row: *OS-OGEXPORT-LAW*.

## 4. Decision (maintainer, 2026-10-16, option C) and its reading

- An import maps tracker volume 64 to **level 50 = 0 dB on the log scale of the instrument law**; the volumes below keep their ratio in dB: level = 50 + round(20 log10(v/64) / 0.48), at least 1 for v >= 1, 0 for v = 0. Volumes 1 to 4 (under -24 dB) clamp to level 1 (-24 dB). The quantisation is the law's own, 0.48 dB a step: MOD 32 -> level 37 (-6.24 dB, 6.02 wanted).
- Option A (rewriting OG v<7 volumes at load) was not chosen. OG files are never rewritten, and no OG writer changes.

## 5. Fix design (Level C)

**D0 (done). The demo kit at unity under the document's law.** `install_demo` moved from the platform into `app::install_demo_kit` (`app/src/sample_bank.cpp`) so that the host can hold it to the rebuild invariant; it adds the four instruments at `unity_level(project_law)` (50 under the 1.2+ law, 100 under the 1.1.14 table; `model::demo::add_instruments(project, volume)`, default 50), so the kit's unity descriptors and a rebuild from the project agree. A native demo project saved by an older build stores 100 and plays +24 dB at the next load, as it was saved; nothing rewrites it. `SampleBank::demo_kit()` is true while the slots hold the kit and ends at `clear()`.

**D1 (done). One source of truth for the law.** `model::Project::volume_law()` (0 the 1.2+ law, 1 the 1.1.14 table; runtime in phase 2; from slice S1 it is also stored, as the `LAW` chunk when it is 1 (D3), and set when a native file with that chunk has loaded). Rules (finding 5 of the risk review): committed **only when a load has succeeded** (`app::commit_og_law_if_done` at the Done of an OG load; a failed load or a folder that is no project commits nothing; this holds for a failure before the project reader's `reset()`: a `project.mt` that fails to parse fails after it, leaving an empty document at the 1.2+ law); `Project::reset()` puts it back to 0 (a native project, an import and a new document are the 1.2+ law; a half-read document too); `reset(true)` (KEEP INSTRUMENTS) **keeps it** (deliberate departure from the review's "NEW, fresh and keep reset it": the kept instruments and the audio bound to them were built through that law, and resetting it would move their level by 24 dB at the first rebuild, the very bug; the ALL path and a fresh project reset it). `SampleBank::rebind_now` starts with `sync_law()`: the bank's copy and the voices' follow the document, written **only when they differ** (finding 7: no store into `VoicePool::law_` at every Params edit; a change happens at a load with the engine quiet, and the word is a single byte the render reads at a ParamChange). The loader's `law_` argument stays (it is the document's law at the time of the call). Files: `model/include/o3os/model/project.h`, `model/src/project.cpp`, `app/include/o3os/app/og_samples.h`, `app/src/sample_bank.cpp`, `app/include/o3os/app/sample_bank.h`, `audio/include/o3os/audio/voices.h` (getter), `platform/mk66/src/app_main.cpp`.

**D5 (done). `diag inst` says the law and the kit.** Every branch of the line ends ` law 12|1114 [demo]` (`describe_instrument`, `app/src/og_samples.cpp`): the document's law, ` BANK-LAW n` and ` VOICES-LAW n` when the bank's or the voices' copy differs from it (a drift is visible), and ` demo` while the slots hold the kit; the flag ends at `clear()` and with any new audio in a slot (`adopt`, `set_audio`), not at a rebuild.

**D6 (dropped).** Zeroing the descriptor's padding so that two builds compare as bytes cost a descriptor of flash (248 B) for a property only a test reads, and did not cover `rebind_now`; the tests compare the fields (`same_desc`). The e29fa17 case passed alone and failed in a group run when it compared bytes (padding bytes 26-27, 198-199, ... only).

**D2 (decided, slice S3). The import re-map.** One pure function `volume_level_of_tracker(v)` in `formats` (uses `core::log2_fast`, import time only) for `formats/mod/src/map.cpp:420` and `formats/med/src/med_map.cpp:910` **only** (finding 2: `med_map.cpp:823` is the MED **MIDI** instrument, whose `volume` is a velocity read linearly (`default_velocity * 127 / 100`), and `track_volume_percent` (`med_import.cpp:281`) is the track volumes: both stay linear; the plain case `med map: a MIDI instrument's volume stays the linear velocity percent` holds it before and after). Its numbers are those of `tests/support/volume_law.h`. Side effect to document as **new Community OS behaviour** (finding 8): the instrument volume is also the Roll's default velocity, so an import at level 50 gives velocity 63 where level 100 gave 127; the hearing of a plain note is the same (the voice's gain is the instrument's own), but the start velocity of a Roll (`seq/src/sequencer.cpp:1281`, `sampler.volume * 127 / 100`) goes from 127 to 63: a VolUp/VolDown Roll peaks about 6 dB lower, the Roll-to-note ratio goes from -24 dB to -6 dB, and a MIDI-out Roll sends half the velocity (QA-INS-212).

**D4 (decided by the maintainer through Q2, slice S4). The Amiga reading.** `amiga_vol = min(64, round(64 * gain / 65536))` and the tracker volume command at `vol / 64` of unity. **[RR2] This is not only an import matter: it changes every native instrument, on the Amiga engine (its default-volume reading) and, for the Cxx command, on the Modern engine only (the tracker effects act on its sampler voices).** Today `tracker_set` (`audio/src/voices.cpp:1584`) makes Cxx `level_gain_q16((vol * 100 + 32) / 64, law)`, i.e. **"level 100 through the law"** at C40, whatever the instrument's own level is: under the 1.2+ law that is +24 dB, an absolute level. After the fix it is **vol/64 of unity** (C40 = 0 dB, C20 = -6 dB). **The reference of Cxx changes from "level 100 through the law" to "unity".** Example: an instrument at level 80 (+14.4 dB on its own) with a C40 on its note jumped to +24 dB before and plays 0 dB after (a drop of 24 dB); at level 30 (-9.6 dB) a C40 also jumped to +24 dB before and plays 0 dB after (it is now 9.6 dB above the instrument's own level instead of 33.6). Every song that uses Cxx on a note that names no velocity changes by up to 24 dB, imported or not. The numbers the maintainer must see (finding 3): (a) every stored level from 50 to 100 now reads 64 on the Amiga engine, so a project **saved by an older build** (from an import, where the levels were the linear percent: half volume stored as 50, or any native project on the Amiga engine) becomes full volume there, and its Cxx commands change by up to 24 dB as above; (b) the quantisation: MOD 32 -> level 37 (-6.24 dB) reads 31, so the round trip import -> Amiga volume is within 1 of the source for every volume 0..64 except three, measured in S4: volume 59 (level 49) reads 61, and volumes 1 and 2 read 4 (level 1, the law's floor, is 4 / 64; volume 3 reads 4, within 1) (the plain case `an imported MOD volume reads on the Amiga engine within 1 of the volume it was written at` holds it before and after); volumes 1..4 clamp to level 1 (-24 dB), which the Amiga engine reads as 4 (S4 measurement; this text said 1); (c) the 1.1.14 table is read the same way (the expected-fail case `... through the 1.1.14 table as well`). An old saved project cannot be told from a new one (the level is the only datum), so there is no loader, and none is wanted: the maintainer accepted these numbers (Q2) on two conditions, both part of the slice: **a changelog entry** that says plainly what changes for a project saved by an older build, imported or native (section 13), and **a test fixture** of such projects (section 13) that pins the new reading, so that the change is a visible, deliberate line in the tests. S3 and S4 are one merge: with S3 alone an import (level 50) would read 32 on the Amiga engine (`(50 * 64 + 50) / 100`), half the volume it was written at. **[RR9]** S4 also rewrites the comments that state the old reading: `audio/include/o3os/audio/voices.h:471` (`amiga_vol`: "the loader derives it from the instrument's volume"), `voices.cpp:1290` ("a MED importer's svol 0..64 made volume * 100 / 64") and `voices.cpp:1584` ("the inverse of the loader's amiga_vol = (volume x 64 + 50) / 100").

**D3 (decided by the maintainer through Q1, slice S1 for the format and S2 for its use). The `LAW` chunk.** The volume law becomes data of the native file. Q1 chose the chunk over the conversion at save (which is up to 15 dB off for levels 1..39: finding 4). Design:

- **Chunk.** Id `LAW ` (four characters, the fourth a space, as `CRC `), version 1.0 (`0x0100`), payload exactly 3 bytes: `u16 version`, `u8 law` (0 the 1.2+ instrument law, 1 the 1.1.14 table; the numbers of `Project::volume_law()` and of `law_number` in `diag inst`). With its header and pad byte it is 12 bytes in the file. A newer minor only appends: read as far as 1.0 goes, the rest skipped, `newer_minor` set (the rule of every chunk).
- **The default is tied to the law, in two places.** (1) *In the file:* **a file without `LAW` is the 1.2+ law**, the law every native file written until now was played at (`begin_samples`: a native project, an import and a new project are the 1.2+ law; D1), so no file written today changes meaning: the "old law" a file without the chunk loads as is exactly the one it always played at. The writer writes `LAW` **only when the law is 1** (the rule of section 10 of the format: a new persistent part is a new chunk written only when the project has it), so every project that is not an OG project below version 7 is the same bytes as before: `empty` 186 B, `small` 2,648 B, `settings` 2,720 B, `state` 3,372 B and the other pinned fixtures keep their size and CRC-32. A file that holds `LAW` with law 0 is accepted and written back without the chunk. (2) *In the model:* the level of a new sample instrument is the law's unity, `unity_level(law)` (50 under the 1.2+ law, 100 under the table), as the demo kit already is (D0); `init_instrument` stays at 50 (no format, no model change), and the sites that create a sample instrument in a live project take the unity of the project's law, so that an instrument added to a project that plays the table is born at 0 dB and not below it. **[RR1] The sites are known, not to be guessed:** `app/src/record_actions.cpp:326` (the recorder, and the loop capture) and the IFF sample reader (`formats/src/iff_sample.cpp:740`, adopted by the app) both call `formats::wav::make_sample_instrument`, which sets no level (it leaves `init_instrument`'s 50), so in a law-1 project they are born at 50, which is far below 0 dB on the table (about -20 dB by the risk review); the wavetable reader (`formats/src/wt_surge.cpp:186`) calls the same function and is the third site (found by this fold). `formats` is below `app` and does not know the law, so **`make_sample_instrument` is not changed**: the app sets `inst.sampler.volume = unity_level(project_law(project))` right after the call at the recorder, and at the place the app adopts the IFF or wavetable reader's instrument (the engineer finds it with the grep `make_sample_instrument|set_instrument` in `app/`, and reports any further site). A load into a slot that already holds an instrument makes a fresh instrument too (the reader replaces the slot's), so it is set to the unity as well.
- **Order and presence.** `LAW` is the **last known chunk**, after `SNFX` and before the unknown chunks and `CRC ` (rank 18; `CRC ` moves to rank 19, in the C++ reader and in `tools/o3project.py`). Finding 6 of the risk review: an older build writes unknown chunks after SNFX, so a file the older build re-saved has `LAW` after `SNFX`, which the strict order accepts only because the chunk is last. There is **no presence flag**: `state_present_` (a `uint8_t` with all eight bits used) is not widened and gets no bit, because the chunk is present exactly when `volume_law() == 1` (default, to confirm by the maintainer; it saves the widening finding 6 asked for).
- **Reading.** Shape errors as always (version 0 or a newer major, a length other than 3 for 1.0 or less than 3 for a newer minor, a second `LAW`, a `LAW` before a chunk of higher rank). **A `law` byte above 1 is `Malformed`** (`LAW: unknown law`), not a default: a law this version does not know has levels this version would play up to 24 dB wrong, and the tolerant rule of `NOTE`/`SNFX` (value out of range reads as default) is chosen for state that has a safe default; this one has not (default, to confirm by the maintainer). The reader holds the value and applies it with `Project::set_volume_law` **at Done**, after the CRC has been checked, so a native load that fails after the chunk commits nothing (the rule of D1); a native file without the chunk leaves the law at the 0 that `reset()` gave. **[RR6]** The held value lives in the `Reader` and is **cleared in its `begin`/init** (not only by the constructor), so a `Reader` object used for two loads in a row cannot carry the first file's law into the second; the test below reads a law-1 file and then a file without the chunk (and a law-1 file that fails at the CRC and then a clean file) through the same `Reader`. A `law` byte above 1 is `Malformed` also in a chunk of a **newer minor** (the byte's meaning is fixed by 1.0; only appended bytes after offset 3 are skipped).
- **Version bump and loader rule. [RR3] The downgrade risk, and a decision PENDING MAINTAINER (Q5, section 8).** The loader rule is settled: absent chunk = the 1.2+ law; present = the stored law. The bump is not: the new chunk is version 1.0 and, as written so far, **no existing chunk is bumped and no field changes meaning**, so the container stays at major 1 and an **older build** (any build before S1+S2, and a build with S1 alone) opens a law-1 file, keeps `LAW` as one unknown chunk (3 payload bytes; the pool arithmetic of `PERSIST2` becomes 15,295 of 16,384 bytes and 12 of 16 chunks for a full OG import with every state chunk), writes it back byte for byte, **and plays the levels at the 1.2+ law: a native copy of an OG project below 7 sounds +24 dB louder at VOLUME 100 than it should. That is a hearing and speaker risk on a downgrade**, the very bug of this item for the files that carry the chunk. It does not worsen what such a copy does today (it plays +24 dB now), but a file written by the fixed build and opened on an older one is a new way to meet it. The changelog (section 13) and `docs/formats/o3-project.md` (the `LAW` section and section 10) must say this in plain words: do not open a project saved from an OG project below version 7 with a build older than the one that wrote the chunk, master low. The options:
  - **(a)** no major bump; accept the risk and document it (the repository's rule of section 10 of the format: a new chunk needs no bump). Cheapest; leaves the hazard.
  - **(b)** a major bump **only in files that carry `LAW`**: such a file writes `PHDR` at version 2.0 (a layout identical to 1.0; 2.0 means "this file has a `LAW` chunk and a reader must understand it"). An older build refuses it (`NewerMajor`, as the format promises), so it never plays a law-1 file at the wrong law; every law-0 file is written exactly as today (the pinned fixtures keep their bytes). The new reader accepts `PHDR` 1.x and 2.0, treats `PHDR` 2.0 without `LAW` as `Malformed`, and `LAW` under `PHDR` 1.x as legal (an older build re-saved it, or a hand-made file). Cost: about 40 B of flash and one more rule in `o3project.py` and in the format document; the price is that an older build cannot open those files at all, which is the intent.
  - **(c)** a major bump always (every file `PHDR` 2.0): older builds refuse every native project, including the ones that never had the problem.
  **Recommendation of this fold: (b) is feasible and is the only option that removes the hearing risk without breaking any law-0 file; (c) is not worth it (it strands every user of an older build for a risk that exists in one kind of file); (a) is the repository's convention but leaves the risk.** Whichever the maintainer picks, S1 must not be implemented before the answer (it changes `PHDR`'s accepted versions and the writer), and until S1+S2 are both in a build, no image carrying only S1 goes to a tester or a card (see S1+S2 as a pair, section 9).
- **Not in the file, deliberately:** the OG export's version (`OS-OGEXPORT-LAW`, Q4: still a separate item) and the module instruments.

**Not changed.** OG readers and writers; `.o3st`; the mixer and master levels (Og1114 for every project by design, `smoothing.h`; PAR-023); the module instruments (`module/`, `modules/`).

> **Instrument volume, imports and the Amiga engine (OS-BUG-PASTE24).** (1) An imported MOD, S3M or MED sample now has the instrument level that is 0 dB for the module's volume 64 (level 50), and the lower volumes follow the instrument law in dB (MOD 32 is level 37, -6.2 dB); it was level 100, which plays +24 dB louder than the module.
