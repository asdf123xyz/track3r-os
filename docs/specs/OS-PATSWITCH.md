# OS-PATSWITCH: change pattern while playing

Maintainer request, 2026-10-17: "when playing a pattern i want to change to another pattern without stopping. like if I hit f1, then the keypad has to lightup with the current pattern and allow to change and keep playing in the other pattern, same with the encoder when pressing f1, yeah?"

Maintainer decisions, 2026-10-17 (verbatim): "c->hold only, while we hold we can change to any pattern, 2. at current or next bar (whatevers easier), 3. changes the pattern instantly, 4. a, 5. no step mode ... it should be just simply change to the pattern being set at the current position, yeah?" Confirmed with the maintainer by the orchestrator the same day; the decisions are in section 13. **Section 14 is the as-built record (2026-10-17) and overrides this text where they differ**: the PATTERN chooser is the hold only (a tap opens nothing), the risk review's seven conditions, and the empty-pattern addition.

**Level C** (the sequencer's step-boundary rule and the audio-path timing; CLAUDE.md: "ISRs and the audio path"). Full process: this design, a risk review, one independent review, the QEMU and MK66 gates, hardware verification (sections 9 and 12). Behaviour: new Community OS behaviour. Parity with the original firmware is an open research question (section 0, last bullet). Section 0 was read in the code at dev 62dddbb and not run on the unit.

## 0. What exists today

- **F1 on Pattern, no Shift.** Tap = `chooser.toggle 0` (`app/src/bindings.cpp:375`), hold (400 ms, `core/include/o3os/core/gesture.h:77`) = `chooser.hold 0` (`:378`), closed by the release (`chooser.release`, `:750`; `chooser_held` in `app/include/o3os/app/pattern_edit.h:66`). A tap is delivered at the release, because F1 also has a hold binding (`gesture.h:16`). It opens the PATTERN chooser, a strip over the info line (`app/src/screens/overlays.cpp:387-421`). The same stopped and playing; nothing in it looks at the transport. With no document the key only says its label (`app/src/chooser_actions.cpp:85-87`).
- **F1 with Shift** is `pads.mode 0`, the NOTES pads (`bindings.cpp:391`); Shift+F6 is PATS (`:395`). Neither is a pattern key.
- **Inside the chooser** (a modal overlay: it captures, so the pads do not reach the note layer, `app/src/app.cpp:639-641`): encoder, Up, Down = `chooser.delta` (`bindings.cpp:740-744`), Shift+encoder = 8 places (`:745`), pad n = pattern n+1 (`:746`, `chooser_actions.cpp:158`). All of them end in `set_pattern` (`chooser_actions.cpp:60`): `view.edit.pattern`, clamped 1..255, view state, no undo unit (test `tests/pattern_edit_app_test.cpp:1051`), nothing sent to the sequencer. Left/Right do nothing in the pattern chooser.
- **Playing.** In WATCH and LIVE the view is pulled back to the playing pattern as soon as the position moves (`pattern_follow_play`, `app/src/screens/pattern_screen.cpp:166-185`, called from `app.cpp:486`), so a pick shows for at most a step and changes nothing. In STEP (the free cursor, `pattern_cursor_follows`, `app/include/o3os/app/screens/pattern_screen.h:47`) the view stays on the pick while the old pattern plays. **Net: today F1 cannot change what plays.**
- **Pad lights in the chooser: none.** With any overlay up except the step popup, `App::pad_lights` answers false (`app.cpp:2186-2195`).
- **PATS** (`PadMode::Patterns`, `app/include/o3os/app/pad_layer.h:25`): the pads are patterns 1..48, lit by `patterns_roles` (`app/src/pad_lights.cpp:113-127`: Back = the pattern has content, Front = the pattern that plays, stopped the one in view, a queued one blinks). A pad is `patterns_pad` (`app/src/pad_mode_actions.cpp:126-148`): stopped it selects the pattern for editing; playing it calls `TransportSink::queue_pattern(id)`, taken **at the end of the pattern** (`sequencer.cpp:1155-1161`), and remembers it in `PatternEdit::queued_pattern` (a second tap cancels). Test: `tests/pad_modes_test.cpp:877`. It has no encoder binding.
- **The sequencer has two ways to move the line, neither is a pattern switch at once.** (1) The live jump (`queue_jump`, the Song screen's; `sequencer.cpp:1129-1143`) and the queued pattern (`:1155-1161`) are read only in `pattern_end()`: at the end of the pattern. (2) The step-boundary jump of OS-PLAYCUR: `locate_row(row)` (`sequencer.cpp:580`, command `LocateRow`, `sequencer.h:142`) sets `located_*` and `locate_pending_`; `end_step()` (`:1034-1048`) takes it at the next step boundary: the pattern, order position and row are set, `load_tracks()` places every track, one `Pattern` event is emitted, nothing is cut, the grid is untouched (test `tests/seq_metro_test.cpp:524-553`). It stays inside the pattern now playing.
- **Song and loop.** In Pattern mode the pattern loops. A queued pattern taken in Song mode **leaves the song**: the mode becomes Pattern and the new pattern loops (`sequencer.cpp:1155-1161`); the Song screen's live jump goes back. A live jump beats a queued pattern and clears it (`:1131-1139`).
- **Latent issue (found by reading, no test yet).** When a live jump beats a queued PATS pad, the App's `queued_pattern` stays set (it is cleared only when playing stops or the pattern becomes the queued one, `app.cpp:468-470`), so the pad blinks until the transport stops. In scope: section 7.
- **Recording.** `pattern_loops` (`app/src/rec_actions.cpp:28-30`) counts a queued pattern as "does not loop". `rec_note` refuses a note while the playhead is in another pattern than the one in view, with `THE PLAYHEAD IS IN ANOTHER PATTERN` (`rec_actions.cpp:59`); a pattern change clears the held recorded notes without an OFF (`app.cpp:471-473`).
- **QA catalogue** (`docs/qa/catalogue/pattern.md`): no row for F1 tap or hold, none for a pick in the PATTERN chooser, none for PATS. The last ID is 253; new rows start at 254.
- **Original firmware.** The sequencer notes and `docs/specs/OS-005-audio-engine.md:145` describe `queue_pattern` as the official firmware's sequential switch (Fn1+Right); the repository holds no evidence for that. Nothing in this repository says when the official firmware makes the switch, or whether it has a switch at once. Open research question; no parity is claimed.

## 1. Behaviour (new Community OS behaviour)

One rule: **while F1 is held on Pattern (the chooser the 400 ms hold opened) and the transport plays, choosing a pattern switches the PLAYING pattern at once, and the playback goes on at the same row.** Stopped it is unchanged: it selects the pattern in view.

- **Hold F1** (400 ms, as today): the PATTERN chooser opens and the pads light with the patterns (section 4). **Release F1**: it closes. Playback is never touched by the opening or the closing.
- **While held:** pad n = pattern n+1 (1..48); encoder, Up, Down = +-1; Shift+encoder = 8 places (1..255, clamped). Each pick, each detent, switches the playing pattern (section 2). Pick as often as you like; the last wins.
- **A tap of F1 opens nothing** (maintainer, 2026-10-17: hold only; the tap-opened PATTERN chooser is removed). With no project the tap still says its label (`F1 PATTERN`), the one thing it did besides the chooser. F2 and F3 keep their tap toggle. (This replaces agent decision A2.)
- **The same rule in every editing mode: WATCH, LIVE, and the free-cursor mode the chip calls STEP.** No STEP-specific behaviour. (The STEP *pad mode*, Shift+F5, is off since OS-STEPPADOFF and not involved.)
- **Picking the pattern that already plays:** in Pattern mode, with no switch waiting, no switch starts (a queued pattern, a queued live jump, a requested mode and a locate that waits are still dropped, as by every pick). In Song mode it leaves the song and loops that pattern (decision 4; agent decision A5). A pick is compared with where the sequencer is going, the switch that waits or else the playing pattern (section 14, condition 1): the pattern that plays, picked while a switch waits, takes the switch back.
- **An empty or unused pattern** (one the project lacks, or one that holds nothing) is gone to like any other, and the transport never stops (section 14, A9).
- **Stopped, or during a count-in** (`view.play.count_in != 0`): the pick selects the pattern in view as today; nothing is sent. (Agent decision A6.)
- **No sink, or the sink refuses** (no sequencer, ring full): the pick is not applied and nothing changes.
- Left/Right stay unbound. F2, F3 (LENGTH, JUMP), F8 and the stopped chooser are unchanged.
- **PATS (Shift+F6) is not changed by this item:** its pads still queue at the end of the pattern. See open question Q1.

## 2. The switch in the sequencer (Level C)

**What the rule means.** At the next step boundary the playing pattern becomes the chosen one, the mode becomes Pattern, and every track continues at the same row of the new pattern. Nothing is cut, the grid is untouched, no step is played twice or skipped; what the skipped OFF rows of the old pattern would have ended is released at the landing (A8; section 14, condition 2). A step is the finest point at which the sequencer changes a row (rows are read once per step), so "instantly" is at most one step later (125 ms at 120 BPM, 16 steps a bar). The maintainer's "current or next bar, whatever is easier" is met by the easier and nearer of the two.

**The row.** The next row of the old pattern is the one the line would play at this boundary. Rule (agent decision A1): `row = next row`, **or 0 when the old pattern ends at this boundary** (its last step has just run, or a Break pattern / Order jump FX ends it); the new row is `row % L`, with `L` the new pattern's running length (`effective_len()` after `pattern_len_ = song_pattern_len(id)`: the longest track, or the Perform length when it is set). So 16 steps to 8 steps at row 12 plays row 4; 8 to 16 at row 5 plays row 5; equal lengths keep the row; a loop end starts the new pattern at row 0. Each track then sits at `row % its own length` (`load_tracks()`, polymetric tracks keep their phase rule); a track with a Perform source pattern keeps it.

**How the live jump is reused** (`sequencer.cpp:1131` is the template, `locate_row` is the base). The live jump is taken only in `pattern_end()`, so by itself it cannot switch at once. What is reused:
1. *Its command path:* a new `Command::Kind::SwitchPattern` (`a` = pattern id; `Command` stays 8 bytes) on the same `CommandRing`, drained in `drain_commands()` (`sequencer.cpp:308-345`) into `Sequencer::switch_pattern(id)`, as `QueueJump` is.
2. *Its precedence rule:* the newest intent wins. `switch_pattern` clears `queued_pattern_` (a PATS pad), `queued_jump_` (a Song live jump), `mode_request_` and a locate that waits; `queued_jump_` clears the published `queued` word at the next block, so the Song slot stops blinking.
3. *Its Song-to-Pattern change:* `mode_ = PlayMode::Pattern`, the pattern loops, as the queued-pattern arm does (`:1155-1161`).
4. *The step-boundary point of OS-PLAYCUR (`end_step`), with the switch's own members, not `located_`:* `switch_pattern` sets `switch_pending_` and `switch_id_`; one branch of `end_step()` takes them at the next step boundary: the row above, `mode_`, `pattern_id_`, `pattern_len_`, `song_step_`, `break_pending_` and `jump_pending_` cleared (agent decision A4), then `load_tracks()` and the `Pattern` event as for a locate. What clears the request (`begin_run`, `end_run`, `locate`, `locate_row`), the release step after the landing and the landing word: section 14, conditions 2, 3 and 7. Ignored (nothing set) when `!playing_`, during a count-in (`count_in_left_ != 0`), or for an id outside 1..255.

The engineer may shape the code differently if the observable rules above hold. A pattern the project lacks plays as empty at the default length (`sequencer.cpp:518-523`; the row counter `rows_missing` counts it): the pad is Off and the strip says EMPTY.

## 3. App side

- **New sink call** `TransportSink::switch_pattern(unsigned id)` (`app/include/o3os/app/actions.h`, default false, like `queue_pattern`). `SeqTransport` in `platform/mk66/src/app_main.cpp` pushes `SwitchPattern` with the guards of `queue_pattern` (sequencer present, outputs open, audio running, id <= 255). The main loop stays the ring's one producer.
- **One function** in `chooser_actions.cpp`, `pick_pattern`, used by `chooser_pad` and `chooser_delta` for the PATTERN chooser: if the chooser is held, `view.play.playing`, `count_in == 0` and a sink is attached, it compares the pick with the pending target (`switch_to`, else the playing pattern; skipping the view's `edit.pattern` early-out), asks the sink first and only then sets `view.edit.pattern`, clears `view.edit.queued_pattern` (the sequencer dropped the PATS queue) and sets `PatternEdit::switch_to`; otherwise it is today's `set_pattern`. The encoder and Up/Down count from `view.edit.pattern`, which holds the last pick, so a fast turn is not stuck on the old playing number.
- **`switch_to` (new, runtime only: `PatternEdit::switch_to` and `switch_age`).** Between the pick and the step boundary the published position still says the old pattern. `pattern_follow_play` must not pull the view back then: it skips the pull-back while `switch_to != 0`. `poll_play_position` clears it when the published pattern is the target, when the transport stops, when another pattern than the target starts, and after `kSwitchGuardSteps` (4) step changes without the landing (a guard, counted in `PatternEdit::switch_age`; a healthy ring never reaches it). STEP never pulls back, so it needs no special case.
- **No other App state.** What plays is read from the published position as today (`view.play.pattern`, `view.play.order`). The App reads nothing else about the switch; the sequencer publishes one word of landings for the console line only (section 14, condition 7).

## 4. Pad lights (held PatternChooser only)

`App::pad_lights` answers with `patterns_roles` (the PATS grammar, unchanged) when `overlay == PatternChooser && chooser_held`: **Front** = the pattern that plays (stopped: the pattern in view), **Back** = the pattern exists and has a step that is not empty, **Off** = absent or empty, a PATS-queued one blinks. Lit stopped as well as playing. After a pick the Front pad moves when the switch lands, at most one step later. `PatternContent` is polled while the held chooser is up (`app.cpp:217`), bounded as in PATS (two patterns a pass, `pad_lights.h:71`). Pads cover patterns 1..48; a pattern above 48 has no pad (the strip and the encoder reach it). There is no tap-opened PATTERN chooser; the LENGTH and JUMP choosers stay without lights.

## 5. What the screen shows

- **Chooser strip.** Held and playing: the hint is `pads, encoder: switch now   COPY: COPY   SHIFT+COPY: PASTE   release F1: close` (PAT-OPS-B, D11: it names the pads and the encoder only; the pads 1-48, Up and Down pick all the same, and a value too long for the line drops the pick words); in Song mode the value adds `LEAVES THE SONG`; a chosen pattern the project lacks adds `EMPTY`. Held and stopped: `pads, encoder: +-1   COPY: COPY ...   release F1: close`. (A chosen pattern the project lacks says `EMPTY` in both.)
- **The view.** WATCH and LIVE: the grid stays on the pick while `switch_to` is set and then follows the playing pattern (no one-step flicker). STEP: the view is on the pick and the cursor stays on its row.
- **No status chip, no queue marker for the F1 switch:** the old `NEXT nn` chip is gone with the queue design; a switch waits one step at most, which `switch_to` covers. PATS still blinks its queued pad (section 14, condition 5).

## 6. Song mode and recording

- **Song:** leave the song and loop the chosen pattern, as PATS does (decision 4). While the transport plays, Play is Stop (`pattern_actions.cpp:221`), so the song comes back with **two** presses: Play (stop), then Play on the Song screen (start); the Song screen's Rec-while-playing live jump goes back at the end of the pattern. A waiting live jump is dropped by the switch (newest wins).
- **Recording (LIVE).** The held chooser captures the pads, so no note is recorded while F1 is down. A take goes on across the switch, one undo unit (a song already crosses patterns inside a take). The held notes of the old pattern end without an OFF, the existing rule for a pattern change. After the pick and before the landing (at most one step) a note is refused with `THE PLAYHEAD IS IN ANOTHER PATTERN`; nothing is written to the wrong pattern. `pattern_loops` is untouched: no queue state exists for the switch, so the new pattern loops and the last step wraps.
- **STEP:** the free cursor edits the pattern in view, which is the playing one after the landing.

## 7. Fix inside this item (kept)

The PATS blink: the App clears `queued_pattern` whenever the published pattern changes while one is set (the queue was consumed or beaten), as well as on a stop and when this item's switch is sent, **except when the change is the landing of a switch** (the pattern that shows is `switch_to`): a queue made after the pick still waits for the new pattern's end, so its blink goes on (section 14, condition 5). Host test first: a live jump beats a queued pad and the pad stops blinking. Accepted miss: an Order jump FX that lets the queue wait for the next end also clears the App's memory (the blink goes, the queue still applies); rare, recorded, not fixed.

## 8. Persistence

None. `switch_to`, `queued_pattern`, the chooser, the lights and the pad mode are runtime state (`pad_layer.h:18`). No `.o3pj`, `.o3st`, OG file or journal entry changes. `Command::Kind` is not persisted. A pick is not an undo unit.

## 9. Real-time safety, CPU and size

- **Hand-off.** The main loop pushes one 8-byte `Command` on the existing `SpscRing<Command, 32>` (`sequencer.h:163`): wait-free, no lock, no allocation; a full ring returns false and the pick is dropped. The render (the one consumer) drains at the start of a block (`drain_commands`, at most 16 a block) and only writes the sequencer's private members (`switch_pending_`, `switch_id_`, `switch_release_`, the queues; section 14, condition 3). One word is shared with the main loop, `landing_pub_` (a relaxed `std::atomic<std::uint32_t>`, the render the one writer, the main loop the reader; section 14, condition 7); nothing else needs `volatile` or a critical section beyond the ring's own ordering.
- **Boundary work.** One extra flag test per step in `end_step()`. The switching step does what a pattern end does: `load_tracks()` (a loop of `kMaxTracks`, bounded), one `song_pattern_len`, one `Pattern` event, one relaxed store of the landing word; the step after it adds one flag test and the bounded track loop of `switch_release` (section 14, condition 2). No SD I/O, no blocking, no unbounded loop. Without a switch the event stream is bit-identical to today.
- **Project reads** (`pattern_length`, `read_step`) are the render-context reads the sequencer already makes at every pattern end and locate; a pattern edited at that moment is the generation-checked case (`rows_torn`).
- **Size.** Measured, section 14 (Size): FLASH +1096 B, SRAM_U +16 B (the first estimate, under 1 KiB and 4 bytes, left out the release step, the landing word and the strip texts). The Sequencer's size changes, so the QEMU target golden runs (`tools/ci.sh qemu`) before merge.
- **CPU.** Measure on the unit (`docs/architecture/cpu-budget.md`): the worst step cost of a switch with 16 active tracks against the natural pattern end, and the CPU strip while the encoder spins the chooser through patterns during playback. Gate: no underrun and no peak above the natural pattern-end peak.

## 10. Risks (input to the risk review)

| # | Risk | Handling |
|---|---|---|
| R1 | A step is played twice or skipped at the boundary | Exact-sample grid test as OS-PLAYCUR's (ring and direct); the row is taken from the boundary, never from the App |
| R2 | The row is beyond the new pattern, or tracks have other lengths, or the Perform length is set | `row % L` and `load_tracks`; tests for 16 to 8, 8 to 16, 64 to 16, polymetric tracks, Perform length |
| R3 | The switch meets a pending break, Order jump, queued pattern, live jump, mode request or locate | Defined in section 2 (newest wins, break and jump cleared); one test each |
| R4 | A switch outlives a stop, a count-in or a restart | Ignored when not playing or counting in; cleared by `begin_run` and `stop`; test stop then play |
| R5 | Song to Pattern at a boundary: published order, `song_step_index`, SongEnd | Test: order none, no SongEnd, the song does not come back by itself |
| R6 | The view sticks on a switch the sequencer never took | `switch_to` guard (section 3); host test with a sink that accepts and a position that never changes |
| R7 | A burst of detents fills the ring | One command per gesture, last wins; full ring drops the detent and changes nothing |
| R8 | CPU spike at the switch step | Section 9 gate; no per-block cost |
| R9 | Two surfaces disagree: PATS queues at the end, the F1 hold switches at once | Documented; open question Q1 |
| R10 | F1 held under 400 ms and a pad hit plays a note (the hold has not fired) | Existing gesture limit (`gesture.h`: pads have no hold binding); the lights are the cue; listed, not fixed |
| R11 | A LIVE note in the one-step window is refused | Existing message, nothing written (section 6) |

## 13. Decisions

**Maintainer, decided 2026-10-17** (the earlier options are dropped: the queue at the end of the pattern, the NEXT chip, the cancel logic, the tap-opened chooser that closes itself):

| # | Question | Decision | Date |
|---|---|---|---|
| 1 | F1 gesture | Hold only: while F1 is held the chooser is open, the pads light, any pattern can be chosen; release closes it. A tap keeps today's function | 2026-10-17 |
| 2 | When the switch happens | At once on the same row; the first answer was "current or next bar, whatever is easier": built as the next step boundary, the sequencer's finest point (section 2) | 2026-10-17 |
| 3 | The encoder | Each detent switches the playing pattern at once, while F1 is held | 2026-10-17 |
| 4 | Song mode | (a) Leave the song and loop the chosen pattern, as PATS does | 2026-10-17 |
| 5 | STEP (free cursor) | No STEP-specific behaviour: the same rule in WATCH, LIVE and STEP | 2026-10-17 |

**Agent decisions** (local, documented, reversible; recorded here):

| # | Decision | Why |
|---|---|---|
| A1 | The row is the next row, 0 when the old pattern ends at the boundary, then `row % L` of the new pattern's running length | Simplest safe rule, always inside the new pattern; the loop end starts a pattern from its top |
| A2 | A tap-opened chooser stays view-only and unlit; the lights and the switch need the hold (`chooser_held`) | Maintainer: hold only, a tap keeps today's function; lights that promise "this plays" must not appear where a pick does not play |
| A3 | No F1 + turn shortcut before the 400 ms hold fires | A turn that consumes F1 makes its release silent (`gesture.h:33-35`), so a chooser opened that way could not close on the release; a gesture-layer change is out of scope. Idea: a HoldEncoder that keeps the HoldEnd |
| A4 | The switch clears the queued pattern, the queued live jump, the mode request, and the old pattern's pending break and Order jump | The newest intent wins; a break from the pattern left must not end the new one a step in |
| A5 | In Song mode the playing pattern's own pad also sends the switch | It is the way to loop the pattern the song is on; one expression, no special case |
| A6 | Stopped and during a count-in a pick is a view pick | Rows are not played then; the sequencer ignores a switch there |
| A7 | PATS keeps its queue at the end of the pattern | Smallest change; the maintainer's answers are about the F1 hold |
| A8 | At the landing each track ends what the skipped OFF rows would have ended: a note off for every MIDI note still on, a release (not a cut) for the sampler notes of tracks that do not start a note on the landing row (risk review condition 2) | A mid-pattern switch skips the old pattern's OFF rows; without it a MIDI note hangs and a sampler note, a Roll or an arp rings on through the new pattern's empty rows |

## 14. As built (2026-10-17)

Implemented on `feat/OS-PATSWITCH` with the maintainer's decisions of 2026-10-17 and the seven conditions of the risk review (GO WITH CONDITIONS). Where this section and sections 0 to 13 differ, this section is the behaviour.

**Maintainer decisions.** (1) HOLD ONLY: the PATTERN chooser exists only while F1 is held, the release closes it, and a tap of F1 opens nothing (today's tap-opened chooser on Pattern is gone; the only other thing the tap did, saying `F1 PATTERN` with no project, stays). (2) Playing, the pads light as PATS lights them; a pad or each encoder detent switches the PLAYING pattern at once, at the next step boundary, by rule A1. (3) Stopped, holding F1 and picking selects the pattern to view and edit, as before (also in a count-in). (4) Song mode: the song is left and the chosen pattern loops, as PATS does. (5) The same rule in WATCH, LIVE and STEP. (6) PATS (Shift+F6) is unchanged: a tap queues for the end of the pattern. So PATS is the queued way and F1 held is the at-once way.

**Conditions of the risk review, and how each is met.**

1. *Lost pick.* `pick_pattern` (`app/src/chooser_actions.cpp`) compares a pick with the pending target (`switch_to`) or else `play.pattern`, never with the view's `edit.pattern`, so the early-out of `set_pattern` is skipped on this path. A pick of the pattern that plays, with a switch waiting, is sent: the sequencer takes the waiting switch back (`switch_pattern` of the pattern now playing in Pattern mode starts no switch and withdraws the one that waits; like every pick it also drops a queued pattern, a queued live jump, a requested mode and a locate that waits). Tests `tests/pattern_switch_app_test.cpp`: "a pick is compared with where the sequencer is going" (play 1, pick 3, pick 1 inside the window sends both and ends with nothing waiting; encoder +1 then -1 likewise), "a view parked on another pattern (STEP) still switches to it" (the view on 5 while 1 plays, F1 + pad 5 switches to 5); `tests/seq_patswitch_test.cpp`: "the pattern that plays withdraws a switch that waits" (same drain and across blocks: it plays 1).
2. *Hung notes.* A mid-pattern switch skips the old pattern's OFF rows (agent decision A8). On the first step after the landing, once per track and after its row is read and Chance and Micro-move are known (`Sequencer::switch_release`, called from `play_microstep` at microstep 1 while `switch_release_` is set), the track ends what an OFF row would have: a MIDI note still on gets its note off, whatever the new row is; a sampler note still open gets a NoteOff (a release, never a NoteCut or NoteFade) and its step closes, so a Roll, an arpeggio or a stutter of the old row does not run on through the new pattern's empty rows; a track whose new row starts a note on this microstep (a note, an Off, a Cut or a Fade, not cancelled by Chance, not delayed by Micro-move) is left to that row. The events are at the sample of the landing, before the new row's own. Tests `seq_patswitch_test`: "the notes the skipped OFF rows would have ended end at the landing" (MIDI out and the sampler: one off each at the landing sample, none for a track that starts a note, one for a track whose new row is an OFF, off then on for a MIDI note replaced by a MIDI note, no cut and no fade, no second off later) and "a Roll or an arpeggio of the pattern left ends with the release".
3. *Own members.* The switch uses `switch_pending_`, `switch_id_` and `switch_release_`, not `located_`: they are cleared in `begin_run`, in `end_run` (a stop, a restart and a resume alike) and by `locate()` and `locate_row()` (the later request wins), and `switch_pattern` clears a locate that waits. Tests: "nothing waits across a stop, a restart or a resume": [Stop, Switch] in one drain, [Switch, Play], [Switch, Resume] (the resume goes on where the run is, on the pattern it plays); "the newest intent wins" (queued pattern, live jump, requested mode, locate before and after).
4. *Phase.* The new row is `row % max(L, 1)`, with `L` the running length (`effective_len()`, the Perform length when set). An even-to-even switch keeps the swing pair: the swing flag toggles at every step start, counted from the start of the run and never reset by a pattern end or a landing, and `(next row) % L` keeps the parity of the next row when `L` is even (a loop-end 0 follows an even old length). Test "an even-to-even switch keeps the swing pair" (the Step events fall on the same samples as in a run without the switch, and the parity of the row equals the parity of the step, at swing 50 and 66). What odd lengths do: (a) Swing: the pairing is by step count, not by row. An odd length already slips the pairing at each loop of that pattern (a row that was the long step of its pair is the short one on the next loop); a switch to or from an odd length changes the parity of the row against the pair once, from the landing on. Nothing is lost or doubled; the long and short steps trade places. (b) Metronome: the beat (every 4th step) and the accent (every 16th) are counted from the row (`song_step_`), not from the start of the run. A new pattern whose length is a multiple of 4 keeps the beat phase, one whose length is not a multiple of 4 moves it; the accent falls on row 0 of the new pattern (and on every 16th row), so a pattern shorter than 16 accents at its own start. (c) Looper: the loop player counts Step events (`steps_` since its last restart, restart on the 16 N-th), not rows, so a running loop keeps its length in steps and its place on the transport across a landing: no step is added, skipped or repeated. Only the first start after a Stop waits for a Step event whose row is a multiple of 16, which after a switch is a row of the new pattern. The bar lines of the pattern (row % 16) and the loop's bars agree after a switch only when the row advance is a multiple of 16, as when the lengths are multiples of 16; from 16 to 8 at row 12 the loop's restart no longer falls on a pattern bar. A take armed for a Bar or for the Pattern waits for the new pattern's row 0 or row % 16 = 0, not the old one's.
5. *The blink fix (section 7) and a queue that coincides with a landing.* `App::poll_play_position` clears `queued_pattern` on a published pattern change that is not the queue's own start, except when the pattern that shows is the target of the switch (`switch_to`, the landing): a queue made after the pick still waits for the new pattern's end, and its pad keeps blinking. Test `pattern_switch_app_test`: "the PATS blink ends when a live jump beat the queue, not when a switch lands and the queue was made after it" (written first: with the old rule the blink stayed until the stop; the mutation without the new clause fails it).
6. *Play on Song.* While the transport plays, Play is Stop (`pattern_actions.cpp:221`): coming back to the song takes two presses, Play (stop) and Play on the Song screen (start). Section 6 and QA-PAT-259 say so.
7. *Console line.* Each landing logs `play: switched to pattern P row R` (row counted from 0), by `log_switch_landing()` in `platform/mk66/src/app_main.cpp`, once a pass, from one word the render publishes (`Sequencer::last_landing()`: landings (16 bits) << 16 | pattern << 8 | row; the render is the one writer, the main loop reads it). Two landings between two passes show the later one. Test `seq_patswitch_test`: "every landing is counted in the log word with its pattern and row".

**Real time.** The main loop stays the one producer of the existing `SpscRing<Command, 32>` (`SwitchPattern`, 8 bytes, wait-free, a full ring returns false and the pick is dropped). The render's added work: one flag test per step (`end_step`), at the landing `load_tracks` (bounded by `kMaxTracks`), one `song_pattern_len`, one `Pattern` event and one relaxed word store, and, on the one step after a landing, one flag test and a bounded track loop's worth of `switch_release` (no allocation, no I/O, no blocking). Without a switch the event stream is bit-identical to before (test: the hash of a run is the same across block sizes and `seq_determinism_test` is unchanged).

**Empty patterns (maintainer's addition, 2026-10-17; agent decision A9).** The request: in PATS a pad of a pattern that does not exist "just stops"; for both PATS (queued) and F1 held (at once), going to an empty or unused pattern must go to it and keep playing through its empty rows at the length a new pattern gets, never stop, create or save nothing the user did not edit. *Why it seemed to stop.* Not the queue (`QueuePattern` and the held pick accept any id 1..255, and the App never checks that the pattern exists), not the sequencer (a pattern the project lacks plays as empty at the project's default length: `song_pattern_len`, `read_step` answering an empty row, counted in `rows_missing`; a host test queues a missing pattern and checks that the transport runs on, the Step events stay on the grid and the row wraps at the default length), and not the model (`Project::pattern(id)` is null and `pattern_length` is 0, which the sequencer already turns into the default). It was the Pattern screen's follow rule: `pattern_follow_play` pulled the view only to a pattern the project has, so in WATCH and LIVE the grid stayed on the old pattern with no play bar and the sound went silent (empty rows): it looked stopped. *Fix, at that place:* the view follows any playing pattern 1..255; `PatternSource` already shows a missing pattern as an empty grid at the default length, the sequencer's own rule, so the play bar runs through it; nothing is created (no undo unit, the project file is unchanged until the user writes into that pattern, and a note recorded in LIVE into the pattern that plays creates it as any first edit does). Stopped, the pick selects it for editing as before. Consequences: a Song whose order names a missing pattern is now followed as well (the view used to stay; `play_position_test` changed); `rec_test`'s refusal case (`THE PLAYHEAD IS IN ANOTHER PATTERN`) is now the step between a held-F1 pick and its landing. Tests: `seq_patswitch_test` "a pattern the project lacks plays as empty at the default length and the transport runs on, for the switch and for the queue (PATS)"; `pattern_switch_app_test` "an empty or unused pattern is gone to, in PATS (queued) and with F1 held (at once)" (written first against the old follow rule, where it fails: the view stayed on pattern 1 and the bar was gone); QA-PAT-264.
