# OS-USBDISK: the Tracker as a USB disk

Status: **phase 1: spec and hazard list (2026-10-16), maintainer decisions folded 2026-10-16; code starts with S0/U1a (the pure engine, not wired); folded 2026-10-16 with the risk review (GO WITH CONDITIONS: findings F1..F10 below).** Written for a risk review before any implementation · **Level C** (storage, USB MSC, boot, hardware; a second writer on a FAT volume) · BACKLOG row `OS-USBDISK` (APPROVED, M-L): "(a) running: the card goes to the PC exclusively while the Tracker keeps playing, editing and mixing from RAM; only card operations (load, save, browse) are blocked, with a strip message; on eject, remount and rescan; in USB STANDARD mode USB audio is off meanwhile (ADR 0012, bandwidth); (b) boot: a separate MSC mode at start-up. Builds on OS-SDSWAP's unmount/remount. Never both sides writing at once (the FAT would corrupt)."

**Maintainer decisions (2026-10-16), folded in: these replace the matching defaults below.** (1) Mode (b), the boot disk, ships first, then (a), the running mode. (2) The boot chord is Shift + F1 + F7. (3) Read-only first: the disk is exported write-protected until the writable step. (4) The Disk device is composite: CDC + MIDI + MSC. (5) `bcdDevice` 0x0002 for Disk. (6) The USB VID/PID stay the ones this driver already uses (0x16D0 / 0x0E9F: the official firmware's pair, kept by the maintainer's decision (2026-10-16, confirmed 2026-10-18), publication included), **with the risks accepted by the maintainer**: the ID belongs to another vendor, and a host tool made for the official Tracker that matches on VID/PID could take the unit for one (section 3.1 states the consequences and how the OS stays distinguishable). The F10 gate "a released image that exposes a disk waits for the project's own PID" is therefore lifted by this decision; no pid.codes PID is planned (ADR 0012 amendment 3).

Evidence markers: **[code]** read in the tree at dev aafdcb8 (file:line), **[parity]** verified parity with the original firmware, **[new]** new Community OS behaviour, **[open]** open research question, **[est]** estimate to be measured, **[default]** a choice the row leaves open: default, **to confirm by the maintainer** (section 13).

Parity: documented in the release notes, not verified: official releases 1.4.0-1.9.2 ship **no USB file transfer** (PAR-022, PAR-086; ADR 0008 line 22; `docs/design/product-ux.md:196`; the default there is a card reader only). So the whole feature is **[new]**; no parity is claimed anywhere below.

## 3. The USB side

### 3.1 Layout [new]

A third mode `Mode::Disk`: the STANDARD function set (CDC `diag` + MIDI, interfaces 0..3, EP 1..3) **plus** one Mass Storage interface (class 08h, subclass 06h SCSI transparent, protocol 50h Bulk-Only) as interface 4 with a bulk pair on **EP 4 OUT (0x04) and EP 5 IN (0x85)**, 64-byte full-speed packets (F9: two endpoint numbers, so the K66's one-EPSTALL-per-number limit cannot halt one direction through the other, and the 13 BOT cases stay implementable). `endpoint_kind` returns Bulk for 0x04/0x85 in Disk, `last_endpoint(Disk) = 5`. Configuration descriptor grows by 23 bytes (interface + two endpoints); the validator and the golden-bytes test get a Disk case. `bcdDevice` 0x0002 (the cache rule of ADR 0012 amendment 3). **VID 0x16D0 / PID 0x0E9F are the ones this driver already uses (decision 2026-10-16, risks accepted by the maintainer, see "Identity and its risks" below).** **[decided 2026-10-16]** composite: CDC and MIDI stay alive in Disk mode (the console, `diag`, and the HIL tools keep working; MIDI to the DAW while the card is open); a pure single-function layout stays the fallback if a host stack mis-binds the composite (Windows `usbccgp`).

**Identity and its risks (decision 2026-10-16).** The Disk descriptor uses the driver's VID/PID, 0x16D0 / 0x0E9F, as the STANDARD and AUDIO modes already do (`identity.h`): the official firmware's pair, kept by the maintainer's decision (2026-10-16, confirmed 2026-10-18), publication included; the maintainer's statement is the evidence. The maintainer accepts two risks: **(i)** the VID belongs to another vendor (not allocated to this project; a collision with that vendor's own devices is possible and nothing in the OS can prevent it); **(ii)** a host tool made for the official Tracker (an updater or companion software) that matches on VID/PID could take this unit for an official Tracker and try to talk to it. The OS stays distinguishable by what a host can read, never by the VID/PID: **`bcdDevice` 0x0002** in Disk mode (STANDARD 0x0001, AUDIO 0x0101, all three different, `static_assert`ed), the **product string `Track3r`** and manufacturer string `track3r-os` (never an official string), the interface strings (`Track3r diag`, `Track3r MIDI`, `Track3r Disk`) and the SCSI INQUIRY vendor `Track3r` / product `SD CARD`. A tool that must tell the OS from the original firmware reads `bcdDevice` and the strings. The OS itself never claims to be the original firmware: no string, serial or class code of it is copied, and no official tool is supported or tested. The risk and the string/`bcdDevice` rule are repeated in the README of the USB driver when U1c wires the disk, and the release notes of the first image that exposes a disk name it.

AUDIO to Disk is a soft re-enumeration to Disk (audio streams stop: **"USB audio off meanwhile"** [code: bandwidth, ADR 0012:46]), and the eject goes back to the previous mode and profile with a second re-enumeration. **[default]**

### 3.2 Bulk-Only Transport

CBW (31 bytes) on OUT, data stage, CSW (13 bytes) on IN; all 13 cases of the BOT specification (Hi/Hn/Ho, Hi/Dn, Hn/Di..) answered with the right residue and stall; GET MAX LUN returns 0 (one LUN) and Bulk-Only Reset (0xFF) is implemented; HALT of a bulk endpoint is cleared by CLEAR_FEATURE(ENDPOINT_HALT) with a data-toggle reset. K66 limit: one EPSTALL per endpoint number [code: README]: with the pair on two numbers (3.1) each direction halts and clears on its own; all 13 BOT cases are kept and tested, including the reset recovery (reset, then clear both halts). **The flow control is the controller's NAK**: a bulk descriptor not armed answers NAK; MSC never uses the `OverwriteRing`s.

### 3.3 SCSI command set (the minimum a PC needs; anything else: CHECK CONDITION, ILLEGAL REQUEST, INVALID COMMAND OPERATION CODE)

TEST UNIT READY, REQUEST SENSE, INQUIRY (vendor "Track3r", product "SD CARD"), READ CAPACITY(10), READ(10), WRITE(10), MODE SENSE(6) (write-protect bit, no caching page), PREVENT ALLOW MEDIUM REMOVAL, START STOP UNIT (LoEj = eject), SYNCHRONIZE CACHE(10) (accepted: there is no cache, section 6), READ FORMAT CAPACITIES (Windows asks), VERIFY(10) (as a no-op range check). Capacity from `BlockDevice::block_count()` (READ CAPACITY(10) reaches 2 TB; SDUC is already refused by the driver). No READ(16)/WRITE(16), no UNMAP. **[open]** whether macOS/Windows insist on MODE SENSE(10) or READ(16) for cards over 2 TB (not a case: the driver refuses SDUC).

### 3.4 The data path [new]

The interrupt only moves packets (as today): bulk OUT packets of a WRITE(10) block fill a 512-byte block buffer, bulk IN packets of a READ(10) block drain one. **The main loop** (`appimg::pass()`, which the USB interrupt itself wakes) runs the SCSI state machine and does the card I/O, one block (or a CMD18 run of at most 8 blocks) per pass, with two block buffers so the USB side fills one while the card takes the other.

**The ISR-to-main hand-off is U1c's design and has to be fixed before it is wired (review minor #1).** `msc::Engine` is single-context: `out_packet()`, `in_packet()`, `service()`, `clear_halt_*()` and the class requests all touch the same state (`ring_`, `moved_`, `phase_`, the halts), and `service()` blocks in the card's CMD24. So the USB interrupt must not call the engine while the main loop is inside `service()`. U1c picks one of two shapes and writes it down at the declaration: **(a)** a single-producer/single-consumer packet queue (a fixed ring of 64-byte OUT packets and a small IN descriptor queue, indices `volatile`, written by one side each) with every engine call made from the main loop, the ISR only moving packets between the controller and the queue; or **(b)** the engine's entry points called from the ISR inside a critical section that `service()` takes only around its state changes (never across the card I/O), with the block buffers owned by whichever side the phase says. (a) is the default: no engine change, bounded ISR work, the NAK is the queue being full. Either way the queue depth, the memory and the worst-case latency of a packet are stated and tested with a fake controller before U1c's interrupt code goes in.

**U1c design as chosen for (a) (coded: `usb/include/o3os/usb/msc_link.h`, `usb/src/msc_link.cpp`).** One `usb::MscLink` (single-writer fields; the index and event words are `std::atomic` with release/acquire), bound to `UsbDevice` with `bind_msc()` like `bind_audio()`; the main loop runs a `MscPump(link, engine)` once a pass. OUT: 8 slots of 64 bytes, zero copy (the ISR arms a free slot's buffer, at the token completion publishes `head` with the length), the pump feeds `Engine::out_packet()` when `can_accept_out()`. IN: 8 slots, the pump fills a free slot with `Engine::in_packet()` and publishes `head`; the ISR arms `tail+armed` (at most 2 descriptors) and advances `tail` only at the token completion, so a descriptor taken back by a CLEAR_FEATURE re-arms the same data. An IN stall is a MARKER slot in the same ring: the ISR sets EPSTALL (and `ControlPipe::mark_halt`, so GET_STATUS agrees) only when the marker is reached with nothing armed, which is the "after the last IN packet completes" rule. An OUT stall is a main-written sequence number the ISR applies (EPSTALL on EP 4 is immediate). Events (bus reset, SET_CONFIGURATION: `reset_all`; class request 0xFF: `bot_reset`; CLEAR_FEATURE on EP 5 / EP 4: `clear_halt_in/out`) are four 8-bit counters packed in ONE 32-bit word the ISR rewrites with a single store; the pump reads it once, runs the matching engine calls and keeps the snapshot. Stale data is dropped by an epoch (`all + bot` counters, mod 256): the pump stamps each IN slot with its snapshot's epoch and the ISR drops slots whose stamp differs from the live one; the ISR stamps each OUT packet and the pump drops older stamps and waits on newer ones. CLEAR_FEATURE alone never drops queued data (a host may clear a halt mid-transfer). Bulk-Only Reset leaves the descriptors armed until the mandatory clear-halt of the reset recovery takes them back (a host that skips the recovery could see up to two stale IN packets: hardware check). The ISR also runs the arm/stall service after the flag loop, and the pump pends the USB interrupt after publishing so an IN packet does not wait for the next SOF. GET MAX LUN (0xA1 0xFE, one byte 0) and Bulk-Only Reset (0x21 0xFF, no data) are `ControlPipe::class_request` cases for `layout::kIfMsc` in Disk mode (`Effect::MscReset`); `device.h` routes endpoints 4 and 5 by mode (`kAudioNumber` is 4 in Disk too). Tests with `usb_fake_controller.h`: queue full -> NAK, stall after the last packet, reset mid-write, clear-halt mid-read, a fake ISR racing a pump step.

**Amendments to the link design (review of U1c part 1, 2026-10-16; the code of part 2 follows these).**
1. **OUT stall and the packets already in the ring.** The ISR records `out_drop_to = out_head` (a word only the ISR writes) at the moment it applies an OUT stall. The pump drops every OUT slot below that mark, and drops every OUT packet while `Engine::out_stalled()` is set, so a packet the controller ACKed before the stall can never reach the engine after the clear-halt (it would trigger `go_dead()`). The mark is a free-running index: it is obsolete as soon as the pump's tail passes it.
2. **The stall is re-asserted after every clear.** The ISR clears EPSTALL at the CLEAR_FEATURE at once (the toggle and the descriptors must be reset in that interrupt), but the engine may still be halted (an invalid CBW stays dead until a Bulk-Only Reset). After handling a clear event the pump therefore forgets that a stall was posted, and posts it again as long as `in_stalled()` / `out_stalled()` is set (an IN marker through `in_packet()` returning Stall, an OUT request with a new sequence number). The host sees at most a few NAKs between the clear and the new stall, never NAK for ever. A clear also invalidates the IN markers not yet reached: a marker carries the clr_in counter of the pump's snapshot and the ISR applies it only while that is still the live one.
3. **The epoch never frees an armed slot.** The ISR skips (drops) only slots it has not armed. `in_tail` moves forward only at a descriptor's completion (to its slot + 1) or, with nothing armed, to the next slot to arm; a take-back (CLEAR_FEATURE, configuration) rewinds the arm index to `in_tail`, so the data of a descriptor taken back is armed again and a stale slot is skipped only afterwards.
4. **A card swap under Host** (the slot level changes while the computer has the card). **Superseded by amendment 8** (`present()` includes `opened_` and never saw a reinsert; the code watches the card-detect level through `MscBridge::follow()` instead). While `present()` is false the engine answers NOT READY, MEDIUM NOT PRESENT.
5. **Memory and latency.** The link is 2 x 8 x 64 = 1024 bytes of payload plus 80 bytes of indices and stamps (MscLink, 1,104 B), in `.bss` of SRAM_U: the DMA of the USB module reads and writes its slots, so it must stay in SRAM. The engine (`msc::Engine`, 1,172 B, both 512-byte block buffers) is **in the SDRAM slack window** (`O3OS_SDRAM_NOINIT`, memset then placement-new in `usb0::start()`): it is touched by the main loop alone (the pump, `disk_pass`, `disk_state`), never by the interrupt, the SDHC is polled (the CPU moves each block through the FIFO, no DMA) and the USB DMA only touches the link's slots, so nothing but the core reads or writes those bytes (the single-alias rule of `mem_map.h` holds trivially: only the plain 0x7000_0000 address is used). Reason: with the engine in SRAM_U the `SRAM_U free >= 32 KiB` link gate (`kSramUMinFree`) failed by 120 B (free 0x7F88), and the gate stays at 0x8000 (decision 2026-10-16). The measured deltas are in the commit message of U1c part 2b. A packet waits at most one ISR entry (every token, SOF or pump kick arms) plus one main-loop pass; the pump runs up to `kMaxRounds` (4) rounds of {OUT into the engine, `service()` (one block), IN out of the engine} while a round makes progress, so a 512-byte block crosses in one pass.
6. **Ordering.** The index words are `std::atomic` with release (publisher) / acquire (observer): the payload bytes are written before the release store of the index. OUT is never re-armed while halted (`ControlPipe::mark_halt` makes GET_STATUS agree for OUT as for IN).
7. **Boot disk checks.** `g_boot_disk` and the `poll_card` skip are platform code (no host test): the HIL row `USBDISK-BOOT` in the QA catalogue covers them (boot with the chord, insert and pull the card: no mount, no notification; the computer sees the disk).
8. **The slot under Host (review fold).** `MscBridge::follow(now_ms)` watches the card-detect level (`PinDebounce`, 250 ms), not `present()` (which includes `opened_` and would never see a reinsert): a settled pull lets the card go (`close()`), a settled insert starts it (`open()` logic), and the caller then calls `Engine::medium_changed()`. A card that is in and did not start is not tried again until it has been taken out and put back (a bad card must not block the main loop for 3 s every pass). Test: `mk66_usb_msc_bridge_test`.
9. **Stale OUT data at a clear.** The ISR also takes `out_mark_drop()` when it handles CLEAR_FEATURE on a stalled OUT endpoint (before the clear event is noted): a packet the controller ACKed just before EPSTALL is published after the stall's mark, and without the second mark a pump that handles the clear first would feed it to the engine (`go_dead()`, cases 9, 11, 13). A Bulk-Only Reset event also forgets the posted stalls in the pump (they are re-posted while the engine is halted). Tests in `usb_msc_link_test`.
10. **Cost notes for U1d.** `service_msc()` runs per token and at the end of every interrupt entry (bounded: at most two arms per direction); one pump pass does up to `kMaxRounds` (4) rounds, so a pass can do up to 4 blocking card blocks (single-block CMD17/CMD24, 1-3 ms each for a write): the main-loop stall of a pass is measured in U1d.

11. **A medium change ends the data stage in flight (the writable step).** `Engine::medium_changed()` aborts a READ or WRITE that is in its data stage (`abort_data(kNoMedium)`: the pipe halts if the host still has data to send, the CSW says Failed with the residue of the whole blocks the old medium took). A command is planned (LBAs, the capacity check) on the medium the host knew; before this fix a WRITE(10) whose host data was still arriving when the card was pulled would have gone on, block after block, onto the card put in meanwhile (the bridge answers NoMedium only while the slot is empty, and `follow()` starts the new card at a settled insert). Read-only that was a wrong read; writable it is a write to the wrong card. Tests: `msc: a medium change in the middle of a WRITE / READ` and the bridge case (a card pulled and put back in the middle of a WRITE: the second card gets none of the command's blocks; the case fails without the fix).
12. **The stall a write puts on the main loop (the writable step).** A WRITE(10) block is a blocking CMD24 on the main loop (F7); one pass of the pump does up to `kMaxRounds` (4) blocks. The SD driver's waits (the data CRC status, the card's busy, the CMD13 poll) are DWT deadlines, not `boot::delay_ms`, so the idle hook (`service_while_blocked`) does NOT run during them: bracketing a write with the hook would service nothing, and the display holds its last frame for the stall. What bounds it: unit numbers of v0.6.10-bench (one SD card, 2026-10-17): single-block write 1.15 ms on average and about 2.4 ms at most (`disk_wr1`, 432 KiB/s), a 32-block call up to 0.48 s (the card's own housekeeping), the driver's bound for one failing block 1280 ms (`DISK bound`); reads from a computer at 0.91 MiB/s over 25 s: the pass mean 98,445 cycles (547 us), max 657,174 cycles (3,651 us), histogram < 25 us / < 100 us / < 1 ms / < 5 ms / < 50 ms / >= 50 ms = 2225 / 8368 / 15903 / 7202 / 0 / 0; the USB interrupt 5.38 % of the core, 660 cycles a packet, worst entry 3,195 cycles (18 us). The write direction of the pass histogram is not measured yet (the disk was read-only): the writable copy's `DISK pass` max is the number the CMD25 record still needs. In the boot disk nothing renders, the watchdog is off (startup.cpp) and the display's swap timeout (500 ms) only fires for a swap the chip has not finished, which it finishes within a frame, so a stall of this size costs a frozen strip and a later key scan, nothing else. In the running mode (U2) the same stall is the F8 paired-run question: the render preempts the main loop, the UI frame and the MIDI-in timestamps do not.

**The EPSTALL timing (review minor #4).** The K66 driver applies `EPSTALL` of an IN endpoint only after the last IN packet already queued has completed (the controller finishes the transfer in flight first), so a stall requested by the engine (`in_stalled()`, case 5/7/9 and the failed-read abort) reaches the wire after the data it follows. The engine therefore never counts on the stall being visible at once, and U1c's driver glue clears and re-arms through `clear_halt_in()` / `clear_halt_out()` only after CLEAR_FEATURE(ENDPOINT_HALT) (the same note is in `usb/include/o3os/usb/msc.h`).

**F7: the write is blocking, and that is accepted for U1/U2 [default, to confirm].** A truly non-blocking write needs a split-phase SD driver (start CMD24, return, poll the busy and the CMD13 state across passes), which is a Level C change of the driver and its allowlist tests and is **not in this item**; it is recorded as a follow-up ("SD split-phase writes"). Until then a WRITE(10) block blocks the main loop for the card's programming time (typically 1-3 ms) and at worst for the driver's sum of bounds (**1.28 s** [code: `sd::policy::worst_write_block_us()` = 3 x 10 ms commands + 250 ms data + 500 ms busy + 500 ms CMD13 polls, printed by `bench disk` as `DISK bound`; for one block of a card that fails, once]); the display is serviced from the idle hook while it waits (as for the mount), and **the maximum main-loop stall is measured on the unit in U1d** and is a release criterion. The render is unaffected (it preempts the main loop). **[default]** CMD24 only at first; CMD25 + ACMD23 pre-erase for runs of 8 or more blocks only if the bench shows the single-block rate under 300 KB/s (an allowlist change in `sd_policy.h`: Level C of its own).

## 4. Exclusivity model

### 4.1 One owner, enforced at the bottom

The owner is `CardOwner` (`Tracker`, `Host`, `NoCard`). **Host means: FatFs has let go of the volume (`FatStorage::release()`: no handle, no cached sector, `generation()` incremented) and the SD card driver is used by the MSC state machine and by nothing else.** Every route to the card ends in one of three objects, and each checks the owner and **fails closed**: `FatStorage` (`mounted()` is false: every read answers `NotMounted`, already so after `release()`), `FatStorageWriter::gate()` (`NoCard` when not mounted; add `Host` as its own `WriteStatus` so the message differs), and the firmware store (`FatFirmwareStore`). `BlockDevice` is handed to the MSC bridge only while the owner is Host; while the owner is Tracker the bridge answers NOT READY, MEDIUM NOT PRESENT. A bug above cannot reach the card because there is no mount to reach it through. Never both sides: the owner changes only in the main loop, at the hand-over of 4.2.

**F1 (BLOCKER for U1): the owner is not enforced today.** `device::mount()` calls `CardSwap::reacquire()` (`storage/src/card_swap.cpp:33`, `device.cpp:31`) which mounts whatever the owner is; `poll_card` mounts on `Inserted` (`app_main.cpp:2151-2190`); the console `sd mount` mounts (`usb/src/console.cpp:584`) and the CDC console stays alive in Disk mode. Each would mount FatFs under the computer, in mode (b) as much as in (a). Required in U1b, before any MSC code is wired: **(i)** `reacquire()` returns `NotMounted` and mounts nothing while `owner_ == Host` (the Host-to-Tracker transition is a separate, explicit `take_back()` called only by the eject path); **(ii)** `poll_card` is skipped entirely in disk mode (b) and its mount branch refuses while the owner is Host; **(iii)** `sd mount` and `fw put|rm|update` answer `ERR card on host`; **(iv)** test: a counting `BlockDevice` proves zero FatFs I/O in (b) (boot with the chord: no `mount()` was ever called, no block read except by the MSC bridge) and that neither a card insert event nor `sd mount` mounts, in (a) and (b).

### 4.2 The hand-over (Tracker to Host)

**One predicate, `card_busy()` (F3).** Today `storage_in_use()` (`app_main.cpp:1712`) knows only a save job and a project-load phase; it misses `firmware_has_card()` (`app_main.cpp:1453`: FwPhase other than Idle/Done), a module load, a `preview_job` and a `dir_scan`/`dir_index` read in progress. `card_busy()` is the union of all of them (one function, one place each user registers a claim, like `SaveService::attach_claim` does for the firmware path), and it is what the hand-over, `sd mount` and `poll_card` ask. **A `fw arm` token survives a Host session today (valid 30 s, one use, `fw_service.h:24`); `release(Host)` revokes it** (`armed_ = false`), so a token armed before the disk went out cannot be used on a card the computer may have rewritten. One test for **each `FwPhase`** (Idle, Receiving, Discarding, Finalizing, Verifying, Arming, Rechecking, Handover, Done): busy or not, and the hand-over refused or allowed accordingly.

Preconditions (all, else refuse with the message): a card is mounted (`CardOwner::Tracker`); `card_busy()` is false; the save service holds no pending write (a settings/recent write that is due is done first: wait up to 2 s, else refuse "CARD BUSY: WAIT FOR THE SAVE").

**Order, with rollback (F4).** `request_layout()` can fail (descriptors that do not build fall back to STANDARD: `usb0.cpp:334-341`; `g_iso == nullptr` or a change already in phase refuses: `usb0.cpp:296-299`). The owner therefore flips **last**: (1) request the Disk layout; (2) wait for `attach()` to confirm `mode() == Disk` and the configuration to be set by the host side (a bounded wait, 8 s: past a host's 5 s control timeout, int.14); (3) only then `release(CardOwner::Host)`, the MSC bridge opens, the persistent strip comes up. If any step fails the unit stays Tracker (the layout is requested back to the previous mode) and the strip says `COULD NOT SHARE THE CARD`: **no state in which the owner is Host and the layout is not Disk** (a Host stranded without MSC would lock the user out of their card until a reboot). **Eject order:** MSC answers NOT READY, MEDIUM NOT PRESENT and stops accepting commands -> remount (6.3) -> request the previous layout. **Disk mode is never persisted**: it is a runtime state; `Settings/device.o3st` and the USB mode setting never store it (a test round-trips the settings file byte for byte through a Disk session, and `main.cpp:299`'s boot read never yields Disk).

## 6. Eject, remount, and cache invalidation

### 6.1 Eject

Three ways, all ending in the same remount: **(1)** the computer ejects (SCSI START STOP UNIT with LoEj, preceded by PREVENT ALLOW MEDIUM REMOVAL = allow) [Windows "Safely Remove", macOS eject, `udisksctl power-off`]; **(2)** the user on the unit: Config > USB, EJECT (F7, two presses: the first says `THE COMPUTER MAY STILL BE WRITING: F7 AGAIN`), which answers the computer's next command with UNIT ATTENTION, NOT READY TO READY CHANGE / MEDIUM NOT PRESENT; **a unit-side eject ignores PREVENT ALLOW MEDIUM REMOVAL by design (the user is at the unit), so once the disk is writable (U1c's writable step, done) the first F7 press shows a warning on screen, not only on the strip, and says that a copy in progress on the computer will be cut (review minor #7)**; in the boot disk (b), where the key is the unit's eject, the same rule is `DiskRestart` (`platform/mk66/include/o3os/platform/mk66/disk_restart.h`): a key or pad restarts at once when nothing can be lost (no computer has configured the disk, no card, the computer ejected it, the disk is read-only), otherwise the first press shows `THE COMPUTER MAY STILL BE WRITING: KEY AGAIN` (warning severity, 5 s window) and the second press restarts; the restart then waits for the SCSI command in flight, 3 s at most, so a WRITE(10) in the middle ends instead of being cut (a block is never cut: the reset comes from the loop that writes) **[default, the spec's own rule applied to (b); to confirm]**; **(3)** the computer is gone (bus reset to unconfigured, then no MSC traffic): **no automatic remount** by default (a host that only sleeps would resume on a card the unit has changed). **[default]**

### 6.2 What "no cache" means, and why it matters

The Tracker side holds **no write cache**: `BlockDevice::write` returns only after the card has taken and programmed the block (`block_device.h`), so SYNCHRONIZE CACHE is a no-op and the card is always as current as the last completed WRITE(10). The computer may have its own cache (Windows "Better performance" policy); a forced eject (2) cannot flush it. That is the PC-side data-loss risk and the reason for the confirmation press.

### 6.3 The remount [new, builds on OS-SDSWAP]

`device::mount()` (blocking, tens of ms, up to 3 s for a card that does not answer, display kept serviced) then the existing `CardEvent::Reading` -> `Ready`/`NotReadable` strip and listing re-read. Because the **computer may have changed anything**, everything the OS believes about the card is dropped, not only FatFs.

**F2 (BLOCKER for U2): the invalidation has no mechanism today, and the bug already exists for a plain swap.** `SaveService::known_` / `known_dir_` and `recent_loaded_` are keyed on `card_id()`, the volume serial (`fat_storage_writer.h:38`); `App::card_changed` (`app.cpp:1208`) touches neither them nor `SampleBank::card_version`. A same-serial remount (the same card, or the same card edited elsewhere) keeps every belief. This is fixed first, as its own change (**OS-BUG-REMOUNT**, branch `fix/OS-BUG-REMOUNT`, ahead of U2): one entry point called from `card_changed(Ready)` (which every remount reaches, swap or disk) that clears the save-known set, the recents cache and the bank's card versions; U2b only calls it. A test: a same-serial remount makes the next save write every sample and re-read the recents.

What the entry point (and the remount) drops:
- FatFs window and FAT caches: gone with `release()`; `generation()` increments (every save job pinned to the old mount ends with `NoCard`).
- The File/Sample listings and `dir_index`/`dir_scan` caches.
- `SampleBank::card_version` and `SaveService::known_*` ("the folder already holds that audio", `save_service.h:12-20`): cleared, so the next Save rewrites the samples instead of trusting folders the computer may have replaced.
- The recent list (`Settings/recent.o3rc`): re-read; entries whose folder is gone drop out.
- The project in the document is never touched; its "loaded from" path may no longer exist (Save As then).
- Module records on the card are re-scanned at the next bind; a `.tmod` the computer replaced does not affect the copy in RAM.
- Deferred settings/recent writes (4.3) are written now.
- **The listings filter** [F10]: dot-files and `System Volume Information` (which Windows creates) are never shown.
- **exFAT** [F10]: FatFs is built with `FF_FS_EXFAT` (the volume mounts) but the writer refuses it (`gate()`: FAT12/16/32 only); after a remount the unit shows `EXFAT CARD: READ ONLY` instead of a generic write failure.

**F5: the volume-dirty check is a warning only.** The earlier "refuse writes until reboot" is dropped (a dirty flag is routinely left set by hosts that never clear it; refusing would strand users). After a **Host session only** (not at every boot), the remount reads the flag and, if set, the strip says `CARD NOT EJECTED PROPERLY: CHECK IT ON THE COMPUTER`; everything else works. Which bits: FAT12/16: FAT[1] ClnShutBit (the top bit of the second FAT entry) and the boot sector's byte at 0x25 bit 0; FAT32: FAT[1] bit 27 (ClnShutBit) and the boot sector's byte at 0x41 bit 0; exFAT: VolumeFlags bit 1 (VolumeDirty) in the boot sector at 0x6A. Fixtures: images taken from Windows, macOS and Linux after a clean eject and after a pulled cable, pinned in the test (`[open]` until the fixtures exist: the bit's behaviour per OS is not verified here).

## 8. CPU, interrupt and memory cost

- **Interrupt:** the USB interrupt (prio 64) preempts the render (128). A bulk token with a 64-byte copy is 250-400 cycles [README, est]; full-speed bulk is at most about 19 packets per ms, so at saturation about 28 tokens per audio block (1.45 ms) x 400 = 11k cycles = **4.3 % of the 261k-cycle block**, 2-3 % at a realistic 0.6-0.9 MB/s [est]. The render has no way to wait for it. **[default]** a load throttle: while the render's load is above 85 %, the OUT/IN descriptors are left unarmed on alternate frames (NAK), halving the rate; the unit measurement decides the threshold.
- **Main loop:** SDHC reads at 22 MB/s need about 30 us per block including FIFO drain, so 1,600 blocks/s = about 5 % of the main loop; writes are bound by the card (1-3 ms a block): the non-blocking write state machine keeps the UI frame rate. The render is not affected by main-loop work (it preempts it); a render near its budget slows the UI and the transfer, never the audio.
- **Worst case:** a card that hangs costs one bounded wait (CMD13 500 ms) as a state-machine step, not a freeze.
- **RAM/flash:** the link (1,104 B) in SRAM_U `.bss` (counted in the `rings` row of `mem_map.h`, which keeps its 16 KiB: the link gate, not the plan row, is the limit); the engine with its two 512-byte block buffers (1,172 B) in the SDRAM slack window, main loop only (3.4 amendment 5); nothing in SRAM_L (the MSC state machine is flash code called once a pass). The measured FLASH/SRAM_U/SDRAM_STATIC deltas are in the commit message of U1c part 2b; flash about 4-6 KB [est] (BOT + SCSI + descriptors + UI). SRAM_L hot budget is not touched.
- **No `OverwriteRing` for MSC data; no allocation; no `double`.**

**F8: the real-time proof (per `docs/architecture/cpu-budget.md` section 5).** The estimates above prove nothing; the item is not done until paired runs on the unit show it. U1c records the **USB interrupt cost per packet** (`diag usb` last/worst entry in cycles, DWT) with a saturated copy in each direction. U1d/U2 run the paired protocol (same song, MSC idle against MSC saturated both ways, at least 10 minutes each, alternating windows, `bench stages` `render_total`): `diag usb` ISR max, `diag cpu` max and **underruns over 10 minutes**, the **OS-GOV sheds** (module instances dropped by the governor), the **UI frame time** (display pass max), and the **MIDI-in jitter** (the MIDI UART at priority 48 is above USB, but the timestamps through the engine are measured with a MIDI loop). Pass criteria are set from the paired baseline, not from the estimate: 0 underruns, render max within the OS-GOV threshold, no shed.

## 10. Safety rules this feature must not weaken

**F6: raw block writes.** `BlockDevice::write` is reached today only through FatFs's `disk_write` glue (`platform/mk66/storage/src/fat_storage.cpp`), under the writer's guard (`check_layers` rule 6 keeps FatFs write calls inside `fat_storage_writer.cpp`). The MSC bridge is a second caller of `write`, below the guard. So: **(i)** a new `check_layers` rule: only `disk_write` (FatFs glue) and the MSC bridge may call `BlockDevice::write`; **(ii)** the bridge writes only while `owner == Host` **and** READ ONLY is off (it reports the write-protect bit and answers DATA PROTECT otherwise); **(iii)** the bench of U1d never writes raw LBAs: it is gated on the Tracker owning the card (no marker, OS-ANYCARD) and writes only into a **pre-allocated scratch file** (`.o3-bench` made once through the normal writer path, then its clusters rewritten), never a computed LBA range; **(iv)** a test: with the owner Tracker the bridge's write returns an error and calls nothing.

- The OS's write guard (`save_guard.h`) constrains what **the OS** may create (until OS-ANYCARD, the test-card marker gate did too). A block-level disk bypasses the guard by definition: the computer can write any path, including `Firmware/`. Nothing here makes a file on the card an update: a firmware candidate still goes through `fw-gate-check` and the documented update path (CLAUDE.md). **[default]** the disk is writable; a **READ ONLY** row (same Config page) reports the write-protect bit to the computer for users who only want to copy off. **[decided 2026-10-16]** read-only first: U1c exports the card write-protected (the bridge answers DATA PROTECT to every write); the writable step follows after the read path is verified on the unit. **[done 2026-10-17, the writable step]** the boot disk is exported writable (`kBootDiskWritable`); the **READ ONLY row is the running mode's (U2a)**: it is a Config page row, and the boot disk mode reads no settings (nothing is mounted, the card is the computer's from the first instruction), so it has no way to hear one; the mechanism is built and tested (`MscBridge::set_writable(false)`: the WP bit of MODE SENSE and DATA PROTECT on every WRITE, zero blocks written) and U2a only has to call it from the row. A card that write-protects itself (the CSD bits) is exported protected whatever the policy. Nothing is persisted: no settings or file format changes.
- The hard rule on removable media for agents stands: a computer in a test session reaches only the unit's own removable disk (16d0:0e9f, removable, not mounted at `/`), identified by the HIL tool before any write; since OS-ANYCARD (maintainer, 2026-10-17) any SD card may be written and no marker file or volume serial is required (`--expect-volume` is an optional check). The disk mode makes that easier (no card swapping), it does not change the rule.

**The CMD25 decision record** (the facts the decision needs; the decision itself is the maintainer's, after the unit numbers). Question: does the writable MSC mode keep single-block CMD24, or add multi-block CMD25 (+ ACMD23 pre-erase)? Spec default F7 / Q10: CMD24 only; CMD25 only if the single-block rate is under 300 KB/s.

1. **What the code does now.** The SD allowlist (`storage/sd_protocol.h`) is the 16 commands CMD0, 2, 3, 6, 7, 8, 9, 12, 13, 16, 17, 18, 24, 55, ACMD6, ACMD41; CMD25 and CMD23/ACMD23 are not on it, and `mk66_storage_protocol_test` pins "exactly these 16" and `mk66_storage_card_test` that no other command is ever sent. `SdhcBus::write_data` takes `blocks == 1` only (BadArgument otherwise). `Card::write_blocks(lba, count, ..)` already accepts a run but loops `write_one` per block: a call of N blocks is N x (CMD24 + data + wait for the busy + CMD13 poll until READY_FOR_DATA in the transfer state). The MSC engine hands the store one block per `service()` (two 512-byte buffers), so even a WRITE(10) of 64 blocks reaches the card as 64 separate CMD24 calls. Reads already use CMD18 for `count > 1` (chunks of `kMaxBlocksPerCommand` = 32), but the MSC path never asks for more than one block.
2. **Where the single-block time goes.** Per block: command and CRC status (tens of microseconds at 22.5-45 MHz on 4 lines), then the card's programming busy (spec bound 250 ms for SDHC/SDXC, typically 1-3 ms [est], cards differ by an order of magnitude), then one or more CMD13 round trips. The busy dominates; the host-side overhead of CMD24 is small. So the write rate is the card's single-block program latency: 512 B per 1-3 ms is 170-500 KB/s [est], on both sides of the 300 KB/s trigger. **The unit decides; no estimate does.**
3. **What CMD25 would buy and cost.** Buys: one command and one busy per run, and with ACMD23 (pre-erase count) the card erases the run in advance, so a run of 8 or more blocks is typically an order of magnitude faster than 8 singles [est: SD physical-layer behaviour, to be measured]. Costs: (a) an allowlist change in `sd_protocol.h` (`Cmd::WriteMultipleBlock = 25`, `AcmdSetWrBlkEraseCount = kAppFlag | 23`, `known()`, `response_of()`, `writes_data()`) and the two pinning tests: **Level C of its own**; (b) `SdhcBus::write_data` for `blocks > 1`: BLKATTR with the count, the FIFO refill loop per block, the stop (CMD12 with its R1b busy, `kStopBusyUs`) and the error path (`recover_after_data_error`); (c) new bounds in `sd_policy.h` for a run (the data wait per block plus one stop busy; `worst_write_run_us(n)`) and the matching stall ceiling (a run of 32 blocks holds the main loop for the whole run, not 1 block: the display is serviced only between calls); (d) a gather buffer in the engine: today 2 x 512 B, a run of 8 needs 4 KiB, 32 blocks 16 KiB, in the SDRAM slack window (main loop only, no SRAM cost); (e) the engine's write path, the bridge (`MscBridge::write` already passes `count`) and `msc_bridge` tests; (f) power-cut behaviour: a cut inside a run leaves up to N blocks written and the rest not, the same class of damage as N singles interrupted, but the card's internal pre-erase can leave the unwritten blocks of the run erased (0x00 or 0xFF by card), so the fsck-clean property test (section 11, crash injection) must run at run granularity. Flash estimate about 1-1.5 KB [est], SRAM_U none.
4. **What the bench gives and what it cannot.** `disk_rd1` against `disk_rd32` measures the command overhead of single against multi-block on the read side (the same code paths minus the card's program latency). The write rate is measured by the write arm (`disk_wr1`, Q14 decided 2026-10-17); a CMD25-vs-CMD24 comparison arm is **not** built because the driver cannot send CMD25 (item 1): the arm reports what the driver does (`disk_wr driver` line) and `disk_wr8` / `disk_wr32` are runs of single-block programs through FatFs, so they separate the card's program latency from the per-call overhead, but not the gain of one CMD25 with ACMD23 (that gain stays an estimate until the CMD25 slice exists). **The decision therefore waits for (i) the single-block write rate on two card brands (`disk_wr1` on a card of each), (ii) the pass `max` of a writable copy.** If (ii) is 300 KB/s or more on both brands, CMD24 stays and CMD25 is recorded as a closed follow-up. If under on either, the CMD25 item is opened as its own Level C slice (allowlist, bus, policy, tests, engine buffer), with its own risk review. The split-phase write driver (F7, Q15) is a separate follow-up and solves the stall, not the rate.
4a. **Unit numbers (v0.6.10-bench, one SD card, 2026-10-17; the maintainer decides).** `disk_wr1` about 432 KiB/s (1.15 ms a block, max about 2.4 ms) is above the 300 KB/s trigger, so by the spec default CMD24 stays and this slice adds no CMD25; `disk_wr32` calls reach 0.48 s (the card's internal housekeeping); `DISK bound` write-block 1280 ms; reads rd1 1.8 MB/s, rd32 13.9 MB/s. One card brand only: the trigger asks for two brands and for (ii), the pass `max` of a writable copy (the boot disk is writable since the writable step, so `bench disk` after a `qa_usbdisk_rw` copy gives it). The CMD25 item is NOT opened by these numbers.
5. **Product view.** At 170-500 KB/s a 100 MB sample pack takes 3.5-10 minutes to copy in; at multi-block card speeds (class 10, several MB/s [est]) 10-30 s. The read direction is not affected (CMD17/18 rates in `disk_rd*`).

## 12. Hazards, ranked

1. **Two writers on one FAT** (corruption of the user's card). Sources: a card job started just before the hand-over (the 1.5 s settings timer, a recent-list write, an app export, an OG sample load, `fw put`, `sd mount`), a stale FatFs window after the PC changed the card, a path that reaches the card without going through `FatStorage`. Mitigation: one owner flag enforced in the three bottom objects (fail closed), hand-over only when idle and with the timer held, no mount to reach, a static rule that all users are accounted for, the exclusivity test of section 11.
2. **PC-side data loss and stale OS state after the PC changed the card** (unplug or force-eject with a PC write cache; samples/folders replaced under `card_version`, `dir_index`, recent list). Mitigation: no Tracker cache, a confirmed forced eject, full invalidation list (6.3), the FAT dirty-bit check with writes refused, deferred settings.
3. **Audio underruns from MSC**: the USB interrupt preempts the render (about 2-4 % of a block at full rate), the main loop can stall on a slow card or a mount. Mitigation: non-blocking card state machine, load throttle, measured with the paired-window protocol; budget stated in section 8.
4. **USB mode transitions**: AUDIO -> Disk -> AUDIO is two soft re-enumerations on three host OSes (driver binding by VID/PID/bcdDevice, composite splitting, a host that does not release the old device), no VBUS sensing (cannot tell cable-out from sleep), the K66's shared EPSTALL on EP 4. Mitigation: a distinct bcdDevice, the existing 700 ms detach, BOT reset recovery, a hw-session on each OS, composite fallback to single function.
5. **Card events while exported** (pulled, swapped, write-protected, unsupported or huge FS): the OS-SDSWAP poll goes quiet in Host, so the MSC layer must signal media change itself; slow single-block writes (throughput); a card the unit cannot mount is still exportable (good) but then it also cannot remount (stay in a `NOT READABLE` state with a clear strip).
6. **Boot mode (b) in the boot path** (Level C): a mis-read chord at power-up in the field, a code path that mounts the card by habit, recovery expectations (a broken firmware cannot offer the disk), **and anything that re-enumerates the port over the DISK set (v0.6.8: the app's USB AUDIO / USB RETURN sync saw the default settings, the file was never read, and took the unit to AUDIO 120 ms after the host's first reset; fixed: the syncs do nothing while DISK is presented or pending, and `usb0::request_layout` refuses any change from DISK, so the DISK set is final until a restart; the running mode's eject leaves DISK by its own call)**. Mitigation: the chord is explicit and rare, the mode builds on a minimal init (no audio, no FatFs), a reset is the only exit.
7. **Safety-gate bypass** (block-level writes ignore the guard; `Firmware/` is writable by the computer). Mitigation: documented in 10; updates still require `fw-gate-check`; a READ ONLY option.
8. **Same-serial remount trust** (F2): the OS keys what it knows about the card on the volume serial, so the same card edited by the computer is believed unchanged; a plain swap has the bug today (OS-BUG-REMOUNT fixes it first).
9. **Raw-write bypass** (F6): the MSC bridge writes below the guard; a second caller of `BlockDevice::write` that is not the bridge or `disk_write` would be a hole.
10. **Host stranded after a layout failure** (F4): the owner flipped before the Disk layout is confirmed locks the user out of their card.
11. **Disk persisted to settings** (F4): a Disk state in `device.o3st` would boot into a mode with no way out.
12. **Console or `poll_card` mounting in (b) and (a)** (F1): `sd mount` and the insert event mount under the computer.
13. **The eject path must raise `card_changed(Ready)`** (OS-BUG-REMOUNT): the OS's beliefs about the card (what the saves wrote into each project folder, what the loader read, the recents) are revalidated against the files by the event `App::card_changed` sends on every card change (Removed / Ready / NotReadable; not Reading); an eject that remounts the card without raising it leaves the beliefs unchecked, and a Save would then skip samples the computer replaced. The remount of 6.3 therefore ends with `card_changed(Ready)` (or `NotReadable`), never with a bare `mount()`; a test asserts it. The revalidation compares size and the FAT date/time (one lookup a sample), so it also needs the volume to keep timestamps: a computer that rewrites a file with the same size and timestamp is the residual risk.
14. **A card swapped in the middle of a write** (the writable step): the data stage in flight was planned on the old medium; `Engine::medium_changed()` ends it (3.4 amendment 11), the new card is a new medium (UNIT ATTENTION, capacity read again), and no block of the old command reaches it. A hot swap inside the 250 ms debounce is not seen by the slot logic at all; the card driver talks to the card it initialised, and an unselected card does not take a write.
15. **The unit's key cuts a copy** (the writable step): the restart is a reset; a block is never cut (the card access is synchronous on the loop that resets) but the rest of a multi-block command and the computer's write cache are. Mitigation: two presses while the computer may be writing, the strip says so, the restart lets the command in flight end (3 s at most); the PC side may still need its own repair (6.2).

## 16. U2 state for implementer (2026-10-19, written at the end of U2a-1)

**Built (U2a-1, host-tested, not in the image yet).** `DiskShare` (`platform/mk66/include/o3os/platform/mk66/disk_share.h`): the owner state machine of 4.2 and 6.1 over a `DiskShare::Port` (owner, claims, layout, bridge, remount, engine). Way out: `share(now, writable)` -> Quiesce (a due settings write is awaited, 2 s) -> Layout (the Disk layout requested, the previous one remembered) -> Configure (8 s for the computer; 3 s until int.14) -> **the flip** (`hand_to_host()`, which re-checks the claims; then `disk_open`) -> Out. The owner flips last; every failure before it asks the previous layout back (retried, bounded 4 s; `layout_stuck()` if it never takes) and ends Idle with a `Fail` and `fail_text()` ("CARD BUSY: WAIT FOR THE SAVE", "COULD NOT SHARE THE CARD", "NO CARD", "STOP THE EXPORT FIRST"). A card that does not start after the flip is given back at once (nothing was written). Way back: `eject()` (the unit) or the computer's START STOP UNIT -> Draining (the engine ends the transfer, 3 s bound) -> `disk_close` -> `take_back` -> Returning (previous mode and profile: Q6) -> Idle. The bus going away is no trigger (Q7). `poll_event()` is the one-shot for the app (Shared / Ejected / EjectedNotReadable / Failed); the remount owes `App::card_changed(Ready|NotReadable)` (hazard 13). Tests (`mk66_disk_share_test`, real `CardSwap`, `MscBridge`, `Engine` over a FAT32 image, simulated layout driver): the order of calls, READ ONLY policy, every refusal, the save wait, the three layout failures, a refused flip, a card that does not start, an unreachable previous layout, ten minutes Out with unplug/bus reset/claims (no take-back, no OS write or read), eject by the computer and by the unit (close < take_back < layout), eject in the middle of a WRITE (no block after it, the card mounts), the drain bound.

**U2a enumeration failure of int.13 (2026-10-19, fix + trace, to be proved on the unit).** `disk share` failed 3 times in 17 (host: `unable to read config index 0 descriptor/start: -71`); every failed EP0 trace ended with `stall set` and `stall sent` 0 us later, every good one with 24 us or more, and no SETUP followed. The SETUP buffers are NOT the cause: both receive descriptors are re-armed in the pass that takes their SETUP, before the stall, so one is always owned. Cause (a hypothesis that fits all the traces, not proved): the host's data-stage IN reaches the controller while the SETUP still freezes it (the interrupt entered late, under the audio interrupts), is answered when `on_token` ends the freeze, and a stalled data stage raises no TOKDNE, so nothing writes CTL again and the controller stays deaf (the same race exists at a cold start and in STANDARD and AUDIO, rarer: the host's IN is later there). Fix (`device.h` `stall_seen()`; its EPSTALL clear is superseded by int.14 below): the stall flag of endpoint 0's own stall clears EPSTALL, reads the receive descriptors (never rewrites them: a finished one holds an undelivered SETUP) and writes CTL last, unless a TOKDNE is pending. `usb ep0` has a `setup-armed` line after `stall sent` (descriptors owned, freeze released or kept, and TXSUSPENDTOKENBUSY read back from CTL after the write: `set` there means the stall handshake froze the controller again, the hypothesis' own signature). Review fold: the descriptor loads come before the ISTAT read so that nothing sits between it and the CTL write, and `stall_ep0()` drops a stale STALL flag (a bulk halt's, not yet looked at) before the EPSTALL write. **U2a EP0 protocol stall of int.14 (2026-10-20, fix + trace, to be proved on the unit).** usbmon of 10 `disk share` under load: 3 failed, and the failed device-qualifier URB had no completion until the unit's 3 s budget ended it (-71); 4 of about 12 AUDIO re-enumerations had the same URB hang 5.0 to 5.5 s (-2, the host's control timeout) and went on. A hang is the data-stage IN answered with NAK over and over: the STALL interrupt had cleared EPSTALL, so a retried IN found no stall and no armed descriptor.
Fix (`device.h`, design (f)): a first attempt held EPSTALL until the next SETUP, which rested on "the SIE ACKs a SETUP while EPSTALL is set", something nobody could confirm (if wrong, every enumeration dies at its next SETUP) while the usual Kinetis stacks clear EPSTALL at the first STALL interrupt. Kept: the CTL write that ends a token freeze, `setup-armed`. An OUT retried after the one-shot is still ACKed and dropped.
