## 0. Summary

The app host (ADR 0014, ABI 1.3–1.7) is solid *below* the page: capabilities, typed read/edit tables, undo groups, the audio tap, export writes, budgets and quarantine are built and host-tested. What was never designed is the **page itself**. ADR 0002 amendment 1 gave an app "the body of an OS page" and a raw event stream, and every app since then has invented its own key grammar, its own cursor, its own hint text and its own "exit" line, while the OS draws a key row that reads `-- -- -- -- -- -- EXIT EXIT`. The result is twelve apps that each behave differently from every native screen and from one another, that die when the user leaves the page, that cannot be heard unless they write into the pattern, and that are left with a two-finger chord as their only way out.

The decision keeps the ADR 0014 host and adds an **app UI contract** on top of it, additive, so every 1.2–1.8 app keeps running (the input list of point 3 is the one deliberate change to it):

1. **The OS draws the key row from labels the app declares** (F1–F7 and Shift+F1–F7), the same `ui::soft_keys` as every screen; F8 is BACK. OS-KEYROWDLG S5, ABI 1.9, which now also carries F8 BACK, so the row never reads EXIT EXIT between slices.
2. **One grammar, the app's own; no OS cursor.** The app draws and moves its own fields with the keys it receives, and every app answers the same keys alike: Up/Down the row, Left/Right the page, the encoder the value, Delete the default (S2; the shared helper is the standard, 3.2). The only cursor in the OS is the Pattern's.
3. **A narrow input list and one exit.** On an app page the app gets the arrows, Copy, Insert, Shift, Delete, the encoder, F1–F7, Shift+F1–F7, the pads and Rec. F8 is BACK and Play drives the transport (both withheld from the app, in OS-KEYROWDLG S5); the screen buttons leave the app from the 1.10 slice (S3), where they exit it; F7+F8 stays as the escape hatch for a hung app.
4. **Settings outlive the page, not the app.** Every exit is the same `exit()` (F8, the screen buttons, F7+F8); the app's settings are stored per project through `set_own_param` (S3, ABI 1.10), so nothing the user set is lost; only transient data (a VU history, a MIDI log) is. A relaunch from TOOLS starts fresh at the Pattern cursor. There is no suspend and no tick.
5. **The transport is visible** to the app (`get_transport`: playing, pattern, row, tempo, count-in), free in the io table (S3).
6. **The app can be heard**: `play_note` through the project's instruments on the live-note path (the same as a pad), governed like any voice (S3); MIDI out (C1, already designed) stays parked.
7. **Placement**: a tool app starts at the Pattern cursor, its target can be changed inside the app, and after an APPLY the Pattern cursor lands on the first written step with the block selected (S5).

Slices: S0, OS-KEYROWDLG S5 (with the old S1 folded in), S2, S3 (the whole 1.10 minor), S5 (section 4; S1 and S4 are retired numbers). Everything below the contract (the tap, the edit table, the groups) is untouched.

## 2. Diagnosis: why it feels shoddy

### 2.1 The soft keys and the Shift layer look unused — because the OS cannot label them

- The key row of every app reads `-- -- -- -- -- -- EXIT EXIT` (`modules_screen.h:12`). The apps *do* use F keys (Tap Calc F1 TAP / F2 APPLY `tapcalc.cpp:99-110`; Rhythm Gen F1 APPLY / F2 VARY `rhythmgen.cpp:322-325`; Chords F1 `chords.cpp:238`; Morph F1 / F3 `morph.cpp:175`; SMF Export F1 `smfexport.cpp:369`), but the OS has no way to know, so the row above the keys says nothing and each app writes its own hint line in the body (`chords.cpp:337`, `smfexport.cpp:480`, `midimon.cpp:315`, `loudness.cpp:346`, `scope.cpp:343`, `tuner.cpp:658`), in a different place and wording for each.
- Shift+F1–F8 reach the app (`app.cpp:297-301` withholds only Shift+arrows/Delete; the encoder under Shift at `:325`), so an app could use them; none does, and the OS never draws a Shift row on the app page (`screen.h:143-144`: a capturing screen "has no Shift bindings and draws no layer"). To the user that is sixteen dead keys on a screen whose only visible controls are two chord labels.
- On every native screen the key row is the truth about the keys (`docs/ui/ui-map.md` rule 7, "visible state"; OS-SHIFTROW). The app page is the one screen where it is not.

### 2.2 Leaving is bad — a chord as the only exit, on a dead-end screen

- F8 alone does nothing (`bindings.cpp:802-806`: only the chord, Shift+Up/Down, Shift+encoder, Shift+Delete). On every other screen F8 is UNDO on a document or BACK on an overlay (`ui-map.md` section 5 rule 3). The app page breaks that one rule a user has learned by then.
- The chord needs both presses inside 40 ms (`kGestureTimings.chord_ms`, ADR 0014 D.10). A hand test passed on 0.4.16, but OS-BUG-APPEXIT (`BACKLOG.md:106`) exists because exits were missed on the unit; the fallback (a 120 ms window) was never tried. The chord is also handed to the app as two presses (F7, F8) *before* the page closes (`o3module.h:264-265`), which is a trap for any app that binds F7 or F8.
- The screen buttons (Pattern, Song, …) are swallowed: the context captures (`screen.h:107-109`; `ui-map.md:43` calls it a dead end and "acceptable"). Nowhere else on the device does a screen button not change screen.
- Leaving **destroys** the app: `ModuleAppScreen::leave` → `app_exit()` → `exit()`, `shutdown()`, `release_host()` (`modules_screen.cpp:139-143`, `module_ui.cpp:1010-1028`). Values the app did not store in OS parameters are lost (Rhythm Gen, Chords, Humanize, Mutate, Morph keep their pages themselves and say so: ADR 0014 am. G.10(a), am. H.13). So the user cannot peek at the Pattern and come back.

### 2.3 You cannot hear what the app does

- An app has no sound path: no `render` (`o3module.h:88-90`), no note trigger, no MIDI out (C1 parked). Rhythm Gen's header says it plainly: "There is no preview: you hear it in Pattern" (`rhythmgen.cpp:12`). The user has to APPLY, leave (destroying the app), press Play, listen, go back to MODULES or F7, relaunch, undo. That is the loop the maintainer walked.
- The apps that *listen* (Loudness VU, Tuner, Scope) are fine in principle, but two of three failed on the unit: Tuner NO SIGNAL on a clean tone (OS-BUG-TUNER), Scope's spectrum quarantined under load (OS-BUG-SPECQ, `BACKLOG.md:108-109`). The 4 ms call budget plus SDRAM-resident state (about 28 cycles a load, ADR 0014 am. E.11) means a 1024-point FFT must be chunked by hand; the apps did it, and still got stopped at 55 % CPU. The budget is right (the main loop must not stall), the *visibility* is wrong: a stopped app is quarantined for the boot with no way back but a reboot (`modules_screen.cpp:175-179`).

### 2.4 No navigation model, and a cursor only on the Shift layer

- The OS cursor exists on the app page (`ModuleAppScreen::count / set_position`, `modules_screen.cpp:145-155`) but is reachable only through the **Shift layer**, and it only covers the 32 `o3m_param` rows with no pages (`ui-map.md` rule 2 gives a module ≤ 5 pages × 8 rows, the SDK's `O3M_PAGES_MAX` is 4, `o3module.h:134`; the app page has one column of up to 8 visible rows, `ParamView::kMaxRows`).
- Because that column is too small and Shift-only, six of the twelve apps declare **zero** parameters (Rhythm Gen, Humanize, Chords, Mutate, Morph, SMF Export; their `module.json`), and five of them draw their own rows, pages and cursor (`rhythmgen.cpp:51-52, :305-317`; `chords.cpp:229-235`; `apps/common/o3m_edit.h`), SMF Export a single PATTERN value on the encoder (`smfexport.cpp:360-368`) (amended 2026-10-18: it said five of thirteen). ADR 0014 am. G.10(a) records the trade: "its values are not remembered between launches and have no Learn". Tap Calc uses Up/Down for ±0.1 BPM and Left/Right for a page (`tapcalc.cpp:112-117`); Rhythm Gen uses Left/Right for lanes and Up/Down for rows; MIDI Monitor uses Insert and Delete (`midimon.cpp:139-141`). Three grammars for the same four arrows.
- What the shared helper does and does not share: `modules/apps/common/o3m_edit.h` holds text and number formatting, the seeded random, the launch-context target, the instrument-parameter reads and `draw_page` (rows with a cursor, a facts line, an answer line, two lines of key hints, `kMaxRows` = 8). It has **no input handling and no step logic**: each editing app repeats its own `input()` switch (`chords.cpp:217-240`, `humanize.cpp:142-160`, the same shape in Mutate and Morph) and none reads `mods`, so no app has a Shift+encoder step today (the OS withholds Shift+encoder from every app, `app.cpp:325`, and Shift+arrows, Shift+Delete with it, `:297-301`, even from an app with no parameters).
- The user therefore never knows, on an app page, whether the arrows move a cursor, change a value, turn a page or do nothing, and the only hint is a one-line text the app chose to draw. (Decision, Amendment 2: the OS does not take the cursor over; one grammar in the apps themselves, 3.2.)

### 2.5 The app's lifetime against play

- The app lives exactly as long as its page is in view (2.2). Nothing stops the transport while an app runs (Play is handed to the app raw and *also* is not bound in `moduleapp`, so Play from the app page does nothing unless the app forwards… it cannot: there is no transport entry). Verified: `bindings.cpp:800-806` binds no Play; `o3module.h` has no transport call; `O3M_BTN_PLAY` is delivered to the app (`o3module.h:254`) with nothing it can do with it.
- An app cannot see the transport (2.1 table). A rhythm generator cannot know the play row; a monitor cannot say "stopped"; a tuner cannot pause on silence.
- Edits during play are allowed (`o3module.h:507`), which is right, but only from `input()`: an app cannot do anything on a step boundary, so "running during play" can only mean "watching and reacting to keys".

### 2.6 Focus against the rest of the OS

- The app is a modal island: it captures, swallows the screen buttons, keeps its own cursor, and dies on exit. The OS's own navigation rules (OS-NAV3 Shift+Up/Down pages a list, OS-SHIFTROW Shift+F belongs to the screen, rule 3 F8 BACK/UNDO, rule 6 Delete = reset) all stop at its border.
- MODULES is itself reachable only from the Navigator (`ui-map.md:23`); Pattern F7 TOOLS reaches only tool apps. A listening app (Tuner, VU) is three gestures away and dies when you look at the Pattern.
- The app page shows no capability badges (ADR 0014 am. I.10), so the user does not know whether an app hears audio, edits or writes files until the first-launch confirm. (Amendment 3: accepted as it is; no badge is built.)

**Root cause, in one line:** ADR 0014 built the app's *hands* (read, edit, tap, export) and never built its *face*: the page contract was left at "raw events and a canvas" (ABI 1.1), so every app re-invents the UI and the OS cannot help it.

## 3. The design (decided)

Design rule: **additive; the input list is the one change to a legacy app**. New behaviour is chosen by the app (labels through `keys`; the grammar by using the helper), and a 1.2–1.9 app runs as today except for the OS-only changes of OS-KEYROWDLG S5 (F8, Play), S2 and S3, which are listed with their compatibility note (3.8). `o3m_ui` carries `struct_size` (`o3module.h:330`), so a new entry point could append to it; this spec adds none (1.10 is io-table entries only), and the module descriptor does **not** grow (no flags word: nothing needs one, 3.2, 3.8). Every new member gets an `O3M_ABI_ASSERT` and a literal-layout test (`tests/module_edit_test.cpp`), as 1.5–1.8 did.

### 3.1 App UI contract: the key row (ABI 1.9) — taken by OS-KEYROWDLG S5

- **Taken (Amendment 1), with the exit part folded in (Amendment 3 D).** OS-KEYROWDLG S5 (approved, after the alpha; `docs/specs/OS-KEYROWDLG.md` section 2.2 "App pages (C4)", section 5 S5; `BACKLOG.md:62`) implements this subsection as ABI 1.9 **and the exit part of this spec's old S1**: `o3m_ui.keys` is added at the end of `o3m_ui` through `struct_size` (the module descriptor does not grow, so `O3M_MODULE_SIZE(9)` stays 80 bytes); the F8 slot of the 16 labels is **reserved and ignored**; F8 is BACK, Play is withheld and F7+F8 stays the escape hatch (3.3); the 12 shipped apps declare their labels there (labels only); the lint rule for `modules/apps` is there. Q3 is settled by it (option A, a callback per frame). Where the text below and OS-KEYROWDLG S5 differ for 1.9, OS-KEYROWDLG S5 governs.
- `o3m_ui` grows one member: `const o3m_keys* (*keys)(void* state)` — called once a frame (before the page draws) and after every `input()`; returns a pointer to 16 labels (`const char* f[8]`, `const char* shift_f[8]`), each up to 7 characters (the key row's cell), NULL or `""` for a blank key. The OS copies them into the module host block (128 B, SDRAM, no SRAM), validates them (printable ASCII, cut to 7) and draws the row with `ui::soft_keys`, the Shift row while Shift is held, exactly as every screen (`key_row`, `follows_shift` gets an exception for an app that declares `keys`).
- **Reserved keys**: F8 is **BACK** (3.3) and the app may not label it; Shift+F8 is withheld too and stays blank. F7+F8 remains the escape hatch. OS-KEYROWDLG S5 ignores the app's F8 slot and draws BACK there; F7 shows the app's label or stays blank (it no longer reads EXIT). An app that labels F7 gets it (the chord still wins, as today).
- Key events keep their raw form (`O3M_EV_BUTTON`, `O3M_BTN_F1..F7`, `mods`): nothing changes for the app's `input()`; the OS only *shows* what the app says the keys do. A key the app labels blank is still delivered (the app decides), but the row says `-`.
- Cost [est]: flash +1.2–1.8 KB for the key row (copy, validation, the row path for an app, the test) and +0.2–0.4 KB for the exit part (3.3): **+1.4–2.2 KB for OS-KEYROWDLG S5 as amended**, SRAM 0 (128 B in the SDRAM host block), CPU: a 128-byte copy at 30 Hz, nil. Level C (ABI), S/M.

### 3.2 One grammar, owned by the app: no OS cursor (S2, no ABI)

**Decision (Q4).** The OS does not put a cursor over the app's fields. The only cursor in the OS is the Pattern's. The app draws its own rows and moves them with the keys it receives, and **every app uses the same grammar**. The user learns it once; the key row (3.1) names the F-keys; nothing on the OS side has to know what a row is.

| Key (plain layer) | Meaning on every app page | Note |
|---|---|---|
| Up / Down | the previous / next row of the page | stops at the ends, no wrap (what Chords, Humanize, Mutate, Morph and Rhythm Gen do today) |
| Left / Right | the previous / next page | an app with one page ignores them; at most 5 pages of 8 rows (`ui-map.md` rule 2, `kMaxRows` 8) |
| Encoder | the selected row's value | one step per detent |
| Shift + encoder | the selected row's value in **coarse** steps | [proposal, the one grammar detail not in the maintainer's list]. Today `o3m_edit.h` has no step logic and no app reads `mods`, so there is nothing to keep; the OS Params page uses `param.coarse` (`bindings.cpp:706`), and this mirrors it. A row without a coarse step ignores Shift |
| Delete | the selected row's default | an app whose Delete did something else (MIDI Monitor, Loudness VU) moves it to an F-key (3.10) |
| F1–F7, Shift+F1–F7 | actions, named by the key row (3.1) | APPLY, VARY, TAP, CLEAR … the app's own |
| Copy, Insert | free for the app | no grammar meaning; MIDI Monitor keeps Insert as PAUSE |
| F8 | BACK, the OS's | 3.3 |

- **The helper is the standard.** Today `modules/apps/common/o3m_edit.h` shares drawing and formatting but not input (2.4). S2 adds the grammar to it: a small row/page state, one function that takes an `o3m_ui_event` and answers which of {row, page, value (with its step), default} it was, and a `draw_page` that draws pages and the page name and drops the two bottom hint lines (the key row says it now). Header-only, integer, no libc, no allocation, no ABI: it is **source** the app compiles in, so a later change never breaks a shipped `.tmod`.
- **Where it lives (one recommendation, open for the maintainer's nod).** Split it: publish the grammar and the page drawing in **`module/sdk/`** (a new header, MIT like the SDK, named in the SDK README), and keep the app-specific rest (the seeded random, the launch-context target, the instrument-parameter reads) in `modules/apps/common`. Why: the grammar is the thing every app, including community apps, must share to feel alike, and an SDK header costs no ABI; keeping it in `apps/common` would leave third parties to copy it and drift. The cost is a documented surface that must stay backward compatible at the source level. Alternative: keep everything in `modules/apps/common` and document the grammar in the guide only.
- **A test per shipped app.** A shared test helper drives the app's `input()` with Up, Down, Left, Right, the encoder, Shift + encoder and Delete and checks that the row, the page and the value move as the table says, that Delete restores the default, and that no other key changes a value. Each of the 11 shipped apps' tests calls it (the six self-drawn apps in S2, the five that declare rows in S3); Pads, the legacy fixture (3.10), does not. The `modules/apps` lint of OS-KEYROWDLG S5 gains "uses the helper's input function".
- **No flags word, no ABI in S2.** Without an OS cursor nothing needs a flag: `O3M_UI_OS_CURSOR` and `O3M_UI_TAKES_PLAY` are gone, `O3M_UI_BG_TAP` was dropped with the tick, and `O3M_UI_FULL_BODY` has no candidate (3.10). The descriptor does not grow, and S2 needs no ABI minor. What reaches S3's 1.10 is storage (next bullet), not a flag.
- **Storage: `set_own_param(id, value)` (ABI 1.10, io table; Amendment 3).** Every app declares its rows as `o3m_param` and draws them itself in the grammar; when the user changes a value the app calls `set_own_param`. The call routes to the existing `ModuleUi::app_set_param` (`module_ui.cpp:931`), so the value lands in `app_values_` and is stored per project by `app_params_sync` (`project_state.cpp:245-266`, run at `:457`); the echo `set_param` back to the caller is suppressed. The launch order is init → `set_param` × n → `enter` (`module_ui.cpp:905-926`): the stored values are handed back before `enter`, so **apps must stop resetting declared values in `enter()`**. APPM 1.1, not readable by an older OS when more than 6 apps are stored (maintainer, 2026-10-19, option B); up to 6 apps it is still written as 1.0, byte for byte. This applies to the five apps that declare rows today and to the six that draw them without declaring (they start declaring), and it **fixes ADR 0014 am. G.10(a)** ("not remembered between launches"); MIDI Learn on these rows is not claimed. The 32-row cap holds (Rhythm Gen's 24 fit); the app draws its own pages, so its declared rows need no `pages` table.
- **No OS column for a 1.10 app [proposal].** An app built at 1.10 or later gets no OS parameter column and no Shift withhold: its declared rows are storage, it draws them itself, and it receives Shift + arrows, Shift + Delete and Shift + encoder. The OS recognises it by the file's minor, so no flag and no descriptor member are needed; the S3 engineer confirms that `ModuleUi` can read the minor. Until the app is rebuilt at 1.10, the five apps that declare rows keep the OS Shift column exactly as today.
- **What the OS still withholds for a legacy app.** A 1.2–1.9 app that declares `o3m_param` rows keeps the OS parameter column on the Shift layer, exactly as today (Shift + Up/Down row, Shift + encoder edit, Shift + Delete default). S2 makes that withhold **conditional**: Shift + arrows, Shift + Delete and Shift + encoder are kept by the OS only while the app declares at least one parameter, and reach `input()` otherwise (today they are withheld from every app, 2.4), so the grammar's Shift + encoder works on the six self-drawn apps in S2.
- **Accepted: transient data is lost on exit** (the VU history, the MIDI Monitor log, Tap Calc's taps); only settings persist (3.4).
- Moot, and removed: Rhythm Gen's 5-page cap and its dynamic lane rows (the app draws its own pages; five fit the helper), and the `[open]` items of the first 3.10 about rows a static descriptor cannot say (Chords' computed defaults, Mutate's GROUP list, Morph's SOURCE list).
- Cost [est]: firmware flash +0.1–0.3 KB for S2 (the conditional withhold, tests), SRAM 0, CPU nil on the render; each app's `.tmod` on the SD card grows by roughly 0.4–0.8 KB with the helper's input (SD, not flash). `set_own_param` is counted in S3 (3.4). Level B (OS, apps and helper), M for S2: six app files, the helper and six tests.

### 3.3 The input list, one exit, one back

- **The list (Q2, amended by Amendment 3 A).** On an app page the app gets the arrows, Copy, Insert, Shift, Delete, the encoder, F1–F7, Shift+F1–F7, **the pads and Rec**. **F8 (BACK) and Play are withheld from `input()`; from the 1.10 slice the screen buttons are withheld too.** The list applies to **every** app page, legacy apps included. Why only Play of the keys that Amendment 2 withheld: Play is a global binding (`bindings.cpp:333`, `kGlobal`), so withholding it lets the transport run; there is **no global pad binding** (`bindings.cpp:423-544` are all context-scoped) and plain Rec is per screen (only Shift+Rec is global, `:331`), so withholding them would leave them dead. Tap Calc therefore keeps its pad taps (`tapcalc.cpp:99`) and the Pads example keeps working.
- **F8 = BACK** on every app page, with or without `keys`, bound in `moduleapp` (`module.exit`), withheld from `input()`. No shipped app uses F8 (checked again on 777d84c: `grep O3M_BTN_F8 modules/apps` finds none; the F-keys in use are F1, F2 and F3, 3.10) and none uses Play or Rec. Decision Q1. **It ships in OS-KEYROWDLG S5's branch** (Amendment 3 D; formerly S1), so the row reads BACK from the first app-page change and never `EXIT EXIT` between slices: the legacy row is `-- -- -- -- -- -- -- BACK` (`modules_screen.h:12`), and an app with `keys` shows its F1–F7 labels (F7 blank unless labelled) and BACK in F8.
- **Play** drives the transport on an app page, as on every screen; the app does not see it. Today Play on an app page does nothing (2.5).
- **F7+F8 stays** (the hung-app escape hatch); it is no longer the documented way out. The two-presses-before-close trap (`o3module.h:264-265`) shrinks for **every** app: the OS withholds F8 from all of them, so before the page closes the app sees at most the F7 press. An app that labels F7 still acts on that press before the chord is recognised; the chord wins, as today.
- **The screen buttons leave the app from the 1.10 slice (S3).** The page stops capturing screen buttons (the rest of the capture stays) and the press does what F8 does: `exit()`, then the screen. They leave in the slice that brings the persistence, so no setting is lost; until then they stay swallowed, as today. A third-party app of 1.2–1.9 loses its transient state to a stray screen button; accepted.
- The return of F8 is one level, as today: Pattern when launched from TOOLS, else MODULES.
- **Behaviour changes for legacy apps** (documented in the guide and the SDK README, 3.8): F8 leaves; `O3M_BTN_PLAY` is never delivered; from S3 a screen button exits the app. `O3M_EV_PAD` and Rec are still delivered.
- Cost [est]: the exit part of OS-KEYROWDLG S5 (F8, the Play exception in `moduleapp`, the row text, tests) +0.2–0.4 KB, SRAM 0; the screen-button exit +0.1–0.2 KB in S3. Level C (it rides in OS-KEYROWDLG S5's slice; the input-routing change is a documented behaviour change of a published event stream, so the review checks the compatibility note).

### 3.4 One exit, and settings that stay (ABI 1.10; no suspend)

Today an app lives as long as its page. **Decided (Q5, amended by Amendment 3 B):** the maintainer chose suspend over the background tick (Amendment 2), then dropped suspend once persistence covered the need. There is no `SUSPENDED` state, no `suspend` / `resume`, no replace rule and no MODULES state text; `o3m_ui` does not grow in 1.10.

- **Every exit is the same `exit()`**: F8, the screen buttons (S3) and F7+F8 close the app as they do today (`exit`, `shutdown`, `release_host`, an open export aborted).
- **Settings survive** through `set_own_param` and the per-project storage (3.2). **Lost on exit is only transient data** (the VU history, the MIDI Monitor log, Tap Calc's taps, the last Scope or Tuner reading): **accepted** by the maintainer.
- **A relaunch from TOOLS starts fresh at the Pattern cursor** (P2, 3.7); from MODULES it starts at the stored settings and the default target. A project change resets the modules as today (`ModuleUi::reset`), and the stored settings are the project's.
- The tick (L-C), its budget, the `APP` strip badge and `O3M_UI_BG_TAP` stay dropped (Amendment 2); Q8 is moot.
- **Transport read** (`o3m_io_api.get_transport(o3m_transport* out)`: `{size, playing, pattern, order, row, ustep, tempo_x100, count_in, queued}`, a copy of `PlayPosition::Value` read once a pass by the main loop). **Decided (Q6): free in the io table, like `now_ms`**: it reveals no project content beyond `get_tempo`. With it an app can show the play row, pause on stop, align a tap tempo to the beat. It reads NULL below 1.10.
- **Diagnostics**: the `diag cpu app:` line is cut (it existed for the tick). OS-BUG-TUNER and OS-BUG-SPECQ can add it when they need it.
- Cost [est]: flash `get_transport` +0.3–0.5 KB, `set_own_param` +0.3–0.5 KB (routing, the echo suppress, the minor rule for the column, tests), screen-button exit +0.1–0.2 KB; with `play_note` (3.5) the 1.10 slice is +1.7–2.7 KB (3.8). CPU nil off-page. Level C (ABI), counted once in the merged slice S3.

### 3.5 Audio: hearing, and being heard

What an app can **hear** is built (the tap: INPUT or MASTER, mono). Two gaps the maintainer did not raise but the parked bugs show: a per-track tap point (what *this* track plays) and a stereo tap are not there; they are ADR 0014 am. E.9's "not in H2a" and stay out of this spec.

What an app can **output**:

| | Option | Audible as | CPU | Risk | Size |

| **A-1** | **`play_note(instrument, note, velocity)` / `stop_note(instrument)` (decided, Q7)**: io table (ABI 1.10), capability `play_notes` = bit 64, no confirm (it only makes sound), through the live-note path a pad uses (`audio/live_notes.h`, a new source `kLiveSourceApp = 3`, key = a slot 0..3), at most **4 held notes** and **8 triggers a frame** per app (Q14); all stopped on exit (every exit), quarantine and project change | the project's instruments, mixed and governed like a pad note; the Mixer's meter shows it | a voice costs what a voice costs; admission by the governor (`module_governor.h:64`, 90 %); nothing new on the render | low: the path exists for pads and MIDI in; the ring is the live-note ring | flash +1–1.5 KB |

The main-loop side is a ring push per trigger.

### 3.6 Transport and sequencer state visible to the app

Covered by `get_transport` (3.4). **Decided (Q10, amended by Amendment 3 E): no new read entries.** `song_info` is cut. `pattern_count` is not needed: `pattern_info` answers RANGE for a pattern that does not exist (`o3module.h:477-479, :494`), so an app counts the patterns by probing ids 1..255, one cheap copy-out each, from `enter()` or `input()` (checked against the header text; the S3 engineer confirms against the implementation, and the entry is added back only if the probe proves wrong). Rhythm Gen can still offer "next pattern" as a target; exporting the song is not offered.

### 3.7 Placement: "to put the cursor in it" (S5, P2 only)

The phrase admitted three readings. **Decided (Q9): P2 only.** P1 (a cursor inside the app) is the grammar of 3.2, owned by the app and not by the OS; P3 (a pinned live generator) is not pursued and no IDEA row is added (Q8).

- **P2.** A tool app **starts at the Pattern cursor**: pattern, track and start row (and the block, if one is selected) come from the launch context, as they do today for TOOLS (`o3edit::read_target`); the app's **target fields** (pattern, track, first row, rows, tracks) are ordinary rows on its first page, in the grammar, so the user can change the target **inside the app** without leaving. A relaunch from TOOLS starts fresh at the Pattern cursor (3.4).
- **After APPLY**, when the app returns, the OS moves the Pattern cursor to the group's **first written step** and **selects the written block** (one `ViewState` write in `apply_group`, no ABI).
- **Cut (Amendment 3 E):** "TOOLS no longer refused while the view follows the play line" is not built; TOOLS keeps refusing as today (am. G.9).
- Cost [est]: flash +0.3–0.6 KB (the cursor move, tests), SRAM 0; the target rows are app code. Level B (OS and apps).

### 3.8 Compatibility and the ABI story

- **Minor 1.9** (OS-KEYROWDLG S5, which now carries the exit part of the old S1): `o3m_ui.keys` only, added through `o3m_ui.struct_size`; the descriptor stays 80 bytes (`O3M_MODULE_SIZE(9)` = `O3M_MODULE_SIZE(8)`); the F8 slot reserved and ignored. A 1.9 file on a 1.8 OS is refused `NEEDS NEWER OS` by the minor rule.
- **Minor 1.10** (S3, one slice, one Level C review; Amendment 3 C): **io-table entries only**: `get_transport` (free), `set_own_param` (3.2), `play_note`, `stop_note` (bit 64 `O3M_CAP_PLAY_NOTES`). `o3m_ui` does not grow (no `suspend`, `resume` or `tick`), the descriptor does not grow, and there are no read-table entries. Bit 64 is the first bit above the six frozen ones; today it is "a reserved field" (`BadReserved`) in any file, so a 1.10 file on an older OS is refused with `NEEDS NEWER OS` by the minor rule before the bit is looked at: no new refusal path. The six frozen values do not move (C4). **There is no 1.11.**
- **S2 and S5 take no minor.** There is no flags word and no `O3M_MODULE_SIZE(10)`.
- **Behaviour changes for legacy apps** (OS-only): in OS-KEYROWDLG S5: F8 leaves (BACK, `exit()` as the chord does today) and Play is no longer delivered (it drives the transport). S2: Shift + arrows, Shift + Delete and Shift + encoder reach an app that declares no parameters (3.2). S3: a screen button exits the app (3.3). Pads and Rec stay delivered. All are documented in the guide and the SDK README. No shipped app depends on F8, Play, Rec or the swallowed screen buttons.
- **No major bump** is needed. A 2.0 would only be justified by *removing* raw F-key delivery in favour of named soft-key events; not proposed.
- Guide, SDK README, `docs/ui/ui-map.md` (the Module app row and rule 10's "dead end" note), `docs/qa/catalogue/modules.md` and the 12 apps' header comments are updated per slice; the apps that ship with the OS take their labels in OS-KEYROWDLG S5, their grammar in S2 (the six self-drawn) and S3 (the five that declare rows) (Q11). New QA rows name what proves them (`qa_cover`, OS-E2E-3: a sim snap, a HIL step, a host test, or `manual: <reason>`).

### 3.9 What this does not fix, and names

- OS-BUG-TUNER and OS-BUG-SPECQ are app DSP / budget bugs, not UI; they stay parked and are listed in the test battery (section 6). A `diag cpu app:` line is not built (3.4); they can add it when they need it.
- The simulator has no SD app, so no sim golden can cover an app page. **Decided (Q12): S0**, before S2: the sim's card gets the shipped apps built as host shared objects (the per-app tests already build them: `o3m_add_test`), so the key row, the grammar and the exit get sim scenarios and goldens; QA rows lose their `-`. Cost: build glue only, flash 0.
- **Capability badges on the app page are not built** (Amendment 3): the first-launch confirm already shows the capabilities (ADR 0014 am. I.10).

Reading the table:

- **Five apps already speak the grammar** (Rhythm Gen, Humanize, Chords, Mutate, Morph): for them S2 is a refactor onto the helper, a Shift+encoder step and a test. SMF Export gets the grammar on its one row. **Five change what their keys do, in S3**: Tap Calc (Up/Down were ±0.1 BPM, now the row), MIDI Monitor (Delete was CLEAR, now the default; CLEAR is F2) and Loudness VU (Delete was CLEAR, now the default; CLEAR is F1), plus Tuner and Scope, which gain an `input` and rows for the values the OS column used to hold. Pads is the legacy fixture and does not adopt it.
- **Every shipped app declares its rows and stores them per project** after S3, so the latent issue of the first reading (self-drawn values lost) is gone for them, and the five that declare rows lose nothing they had today.
- **`play_note`** is for the four generators (Rhythm Gen, Chords, Mutate, Morph); **the tap** is already used by Loudness VU, Tuner and Scope. There is no suspend and no tick, so MIDI Monitor and Loudness VU start empty on each launch; they keep their settings.
- No shipped app qualifies for a body-only layout (`O3M_UI_FULL_BODY` is not built).
