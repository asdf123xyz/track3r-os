## 2. Scope

**In (phase 2 and later)**
- **C1**: the standalone `.pti` (Shift + F5) and every `.pti` of C2 get their PCM resampled to 44,100 Hz when the instrument records another rate, and the instrument levels converted when the project plays at the 1.1.14 law. (This fixes a shipped latent defect, H1/H2, and is the shared building block.)
- **C2**: *Export to OG*: one folder holding a whole project in the OG layout, openable by the OS and (OQ, section 9) by official firmware 1.9.x.
- Lossy parts are counted by the existing `ExportDrops` plus the new counters of section 4, and shown to the user before and after (section 7).

**Out**: writing into an OG folder in place (the OS never writes into OG files); the native format (no change: no new chunk, no version bump); PASTE24's volume code; the CPU-optimisation files (`voices.cpp` LFO paths, `loop_player.cpp`); MOD/S3M/MED export; pattern names in the PAMD file (hardware gate, section 6 of og.md); 16-track patterns.

## 3. The rate rule (the check the row asked for first)

| Fact | Class | Evidence |
|---|---|---|
| An OG instrument (`.mti`, `.pti`) has **no sample-rate field**; the PCM is mono signed 16-bit little-endian | **VP** (the layout) | `docs/formats/og.md` section 5 (the field table lists every struct field: no rate); 93 of 93 fixture instrument files parse with no rate (`og_fixture_survey_test.cpp:103`) |
| The OG plays that PCM at **44,100 Hz** | **OQ** (parse-only evidence) | the fixtures show the files parse; they do not show what an official device does with them. Indirect evidence: the recorder writes 44,100 Hz (the rate of an OG folder's files, `app/src/record_actions.cpp`) and the OS's OG loader accepts 44,100 Hz only (`OS-RATEPITCH.md`). Until an official device plays an export (T9) nothing here is claimed as verified parity |
| So a native sample at another rate must be **resampled to 44,100 Hz** or its pitch changes on the OG | **NEW** (maintainer, OS-FILES row), resting on the OQ above | OS-RATEPITCH: a 22,050 Hz sample plays at its true pitch here; unresampled it would play an octave high from an OG file (S0 refuses that today) |
| The resampling ratio is `sample_rate / 44,100` exactly | **NEW** | the ratio uses the format's 44,100 Hz, not the engine's clock (44,100 Hz by default since v1.0.0, so the two agree; 44,117.647 Hz with `-DO3OS_RATE_44100=OFF`); whether the official firmware's clock differs from 44,100 Hz is an open research question (`docs/hw/tracker-hardware-notes.md`) |
| Points, loop and slices are 0..65535 fractions of the sample (`amiga_convert.h` "Points, loop and slices ..."), so they follow the new length unchanged | **VP** (field semantics: og.md section 5) | a loop whose length is not a whole number of the new frames has a seam of at most half a frame (**NEW**, accepted) |
| A wavetable instrument's pitch is its window's and takes no rate factor (`OS-RATEPITCH.md`); its `wavetable_window_size` is in samples | **NEW** (this OS's rule, OS-RATEPITCH; the field is in samples, og.md section 5) | so **a wavetable instrument is NOT resampled** (its frames are written as they are, the rate dropped, counted in `rate_ignored`): resampling would change the window length and the pitch. **default, to confirm by the maintainer** |
| Granular instruments: grain positions are fractions; the rate factor applies (`audio_granular_test` is in OS-RATEPITCH's list) | **OQ** | read the granular voice before phase 2 and write the answer here; default: resampled like a one-shot |
| Amiga-engine instruments (engine field, INST 1.2): the voice plays the data at Paula's rate, period 428 = 3,546,895 / 428 = **8,287.14 Hz** at the unity note (C-4, note 60), whatever `sample_rate` says (0 included), and adds the instrument's tune to the note (`amiga_convert.h`: the 16,574 Hz conversion is data at twice that rate with TUNE +12) | **NEW**, **BLOCKER of the review, answered here** | **the source rate of an Amiga instrument is 8,287.14 Hz, never its `sample_rate`**: the data is resampled by `step = 8,287.14 / 44,100` and **the instrument's tune is kept** (an Amiga note n plays the data at 8,287.14 x 2^((n + tune - 60)/12), a Modern note plays the resampled data at 44,100 x 2^((n + tune - 60)/12) in the new frames, the same pitch at every note: the +12 of a 16,574 conversion needs no special case and no guess about which part of a tune is the conversion's; the review's "strip the +12" would double-count it, T14 measures both at C-4 and C-5, for tunes -12, 0, +12 and +24). The Amiga engine itself, its 8-bit rounding and its period clamp (notes above B-4 reach period 113) are gone on the OG: counted in `amiga_engine`. **default, to confirm by the maintainer (Q5, BLOCKING)** |
| Resampled length above `kMaxPcmFrames` (5,898,240; `og.h:52`), possible from an 8,287 Hz sample (x5.32) | **NEW** | **default, to confirm by the maintainer**: that instrument is not written (no `.pti`), counted in `pcm_too_long`, and the user is told by name; never truncated silently |
| Quality: Kaiser beta 8, cutoff 0.45, DC exact (weights normalised), no dither (16 bits in, 16 bits out, round to nearest) | **NEW** | `amiga_convert.h` measurements; **default, to confirm by the maintainer** |
| Edges of the resampler: output frame m reads 32 source frames each side and outside the sample the source is silence (`amiga_convert.h`), so the first and last ~32 output frames fade | **NEW** (**MAJOR of the review**) | a one-shot keeps this (a fade of <1 ms at 44.1 kHz is inaudible, an impulse at frame 0 is not): the source is **edge-extended** (the first/last frame repeated) instead of silence; a looped instrument (play mode 1..3) reads **across its loop**: frames past the loop end come from the loop start (wrap), before the loop start from the loop end, so the loop point is seamless in the new rate (a half-frame seam at most remains, measured). **Known limit (review of C1b):** the resampler wraps at the loop's SOURCE frames (`floor(p x frames / 65535)`), while the file stores the points and a player reads them as `floor(p x frames_out / 65535)`; when the fraction is not exact the two differ by up to one output frame (1/44,100 s), so the seam can step about two normal steps (never a jump); aligning it would need a fractional wrap in the resampler, left out for its cost. Samples are saturated to 16 bits (counted in `clipped`: a full-scale square rings at the edges; the strip ends `DONE (CLIPPED)` when any was). Tests T13, `instrument_clip_test` |

## 5. Levels: the 1.1.14 law and the +24 dB hazard

OG instrument volume is a stored u8 whose gain is law-dependent (`audio/include/o3os/audio/smoothing.h` "THE LEVEL LAWS"): the 1.2+ law (**Og12**: 0 silent, 1 = -24 dB, then 0.48 dB x (level - 50), 50 = 0 dB, 100 = +24 dB) is the law this OS reads every file the writers produce through (project v16/v17, `.pti` v9); the release notes document it for 1.2+ firmware (PAR-023: documented, not verified), and the whole law is this OS's model (maintainer answer Q4 of OS-CLEANROOM, 2026-10-18). A project that plays at the 1.1.14 table (**Og1114**: 100 = 0 dB, 0.4 dB a step, also our model) keeps its levels unchanged today when exported: by the documented anchors **a level 100 would play +24 dB on a 1.2+ unit** (an open research question until an A/B on the unit; PASTE24 R3, candidate row OS-OGEXPORT-LAW). The law is runtime state of the document (`Project::volume_law()`, `docs/specs/OS-BUG-PASTE24.md` D1).

Rule (**NEW**, default, to confirm by the maintainer; **the conversion itself is INFERRED, not verified**): at export, when `volume_law() == 1`, each instrument level L (1..100) becomes `L' = 50 + round(0.4 x (L - 100) / 0.48)` (level 40 is -24 dB = level 1), under 40 it cannot be written (S0 and C1 refuse; the export counts `levels_clamped` and says so). Evidence class (**MAJOR of the review, folded**): both laws are this OS's model (`smoothing.h`; maintainer answer Q4 of OS-CLEANROOM); the 1.2+ law is documented only at its anchors (0, level 1 = -24 dB, 50 = 0 dB, 100 = +24 dB: PAR-023); **between the anchors it is INFERRED (smoothing.h says so: "confirms by A/B listening on the unit")**, so the conversion is **OQ**, and **T3 can only check arithmetic against the OS's own copy of the law (`level_gain_q16`), which proves nothing about an official device**: the proof is an A/B on the unit (T9b). The result line says what was done: `LEVELS WRITTEN AS PLAYED (1.1.14 -> 1.2+)` after a conversion, `LEVELS WRITTEN AS STORED` otherwise.

**The flow that cannot be fixed at export (tied to PASTE24 Q1, H2 stays OPEN)**: `volume_law` is runtime-only (never stored). An OG project below v7 that is saved **native** and loaded again has lost its law (the native file carries none: PASTE24 R2/D3), so it already plays +24 dB in the OS itself, and an export from that document writes the +24 dB levels as they are: **the export cannot know**. Until the maintainer answers PASTE24 Q1 (an additive `LAW` chunk, recommended) the export of any document that did not come from the OG in this session is "levels as stored", and the question for it (section 8) says so. With the chunk, `volume_law()` is exact after a native round trip, and the conversion above is applied to exactly the documents that need it. The same holds for the standalone `.pti` (C1).


## 6. The write path

Folder: `Export/<name> OG/`, `<name>` the project's folder name (the stems' rule: cut so the whole stem fits the guard's 31; "Untitled" with none), then ` OG`, `OG 2`.. when taken: never over an existing folder (**NEW**; **default, to confirm by the maintainer**: the user copies the folder to an official unit's `Projects/`, or it is opened by the OS from File as any OG project. A sibling of the stems' folder is chosen so that `Export/<project>/` stays flat WAVs and the guard keeps four components).

**Folder shape (guard)**: `Export/<name> OG` or `Export/<name> OG n`, **n in 2..99** (never more: the 100th export of a name says NO FREE NAME, as the `.pti` library does); `<name>` is cut so that `<name> OG 99` is at most 31 bytes and ends in neither a space nor a dot. Nothing else is accepted by the guard under `Export/<name>/` as an OG project.

Files, in this order (**NEW**; the order is the safety):

**File names (BLOCKER of the review, folded)**: `format_pti_name` (`og_common.cpp:297`) cuts to a buffer and replaces only `/ \ : " * ? < > |` and control characters; the card guard's `valid_name` (`hal/save_guard.h`) takes only letters, digits, space, `_`, `-`, `.`, at most 31 bytes in all, no trailing space or dot, and refuses reserved device names (`CON`...). A name such as `Kick (hard) & snare's` passes the first and fails the second, and `"NN "` + 31 characters is 34 bytes. So the `.pti` file name is built the way the library's is (`instrument_file_stem`, `app/src/save_service.cpp`: sanitised to the guard's alphabet, reserved names and empties replaced), **prefixed with the slot `NN ` and cut so the whole stem is at most 31 bytes (the instrument part at most 28), with no trailing space or dot after the cut**; the instrument's real name still goes in the file's 31-byte name field (counted when cut). Tests T11: `(`, `&`, `'`, UTF-8 bytes, `CON`, a trailing dot, a 31-character name, an empty name, two instruments with the same name (the `NN` prefix keeps them apart), all guard-valid and all read back by `classify_file_name` as the right slot.
1. `instruments/NN name.pti` for each sample instrument 1..48 that can be written (the resampler is the source stage of the file's PCM; `NN name` from `format_pti_name`; the instrument's name is only a name),
2. `patterns/pattern_NN.mtp` for every pattern id of the project,
3. `patterns/patternsMetadata`,
4. `project.mt` **last**. An OG project without `project.mt` is not a project (the OS's loader ends there with "NO PROJECT FILE", og_folder.h; and File's listing probes for the project file, `app/src/dir_scan.cpp:238-251`). So a cut at any point leaves a folder that can never be taken for a finished export.

Each file is one `AtomicSave` job in `Mode::NewOnly` (temp `_o3save.tmp` in its folder, read-back size and CRC, rename; `atomic_save.h:79` and the table of what a power cut leaves). A set is a plan like the stems' (`save_service.h`: one job at a time, `export_slot`): the first failure ends it and the files finished stay (as stems), the failing file's temp is removed.

**Snapshot (MAJOR of the review, folded)**: the plan takes the document's revision (the editor generation the writers' `unchanged()` already compares, plus the sample bank's per-slot versions and the instrument table's generations) **at the start and rechecks it before every file and before `project.mt`**; a difference ends the export with `Modified` (finished files stay, no `project.mt`). The counters and the loss question are computed from the snapshot; **the second F1 (the answer to the question) recomputes them** and asks again if they changed (as the NEW question does when the project changed under it). Tests T12: inject, between two files, a MIDI record (a take), an external-clock start, an undo, a sample edit, a pad-recorded sample; each must end the export or leave the files consistent with one revision, never a mix. **Refused at the start (MINOR, folded)**: a recording or a record take in progress, a sample-edit job or peak job running, a card claim (firmware update, `attach_claim`), a running stems/WAV export or save (`user_blocked()`), a load.
- **Card full** (`AtomicSave::Error::NoSpace`): the set stops, `EXPORT FAILED: CARD FULL (n OF m FILES)`; no final file is half written; the folder keeps the finished files and has no `project.mt`. The OS never removes a folder or a user file (guard: only temps and backups); cleanup is the user's (by hand, or the future OS-TRASHUI). There is **no free-space query** in `hal::storage` today: a 20 MB export fails at its end. Preflight is optional (OQ: add `Storage::free_bytes()`; **default: none**, the plan's byte total is shown in the question, section 7).
- **Power cut or pulled card (MAJOR, folded)**: `atomic_save.h` says what a cut leaves for one NewOnly file; an export is many of them, and FILES-B measured that a rename cut mid-way left two names sharing clusters in 9 of 42 cuts (`docs/specs/OS-FILES-B.md`; `tests/save_fatfs_test.cpp`). So: (a) a cut during the rename `_o3save.tmp` -> final can leave the temp and the final name on one chain (the data is whole; the next write refuses to remove either: "card needs a check") in **any** of the folders, **including `project.mt`**: that is accepted for the data (both names are the complete new file) and T6 holds it to exactly that, never to a final name with partial content; (b) **stale `_o3save.tmp` files stay in `patterns/` and `instruments/`** (and the root): the folder is abandoned after a failure, so nothing ever cleans them; they never match an OG file name (`classify_file_name` ignores them: `files_ignored` in `og_folder.h`; whether an official device ignores them is OQ), and the user can delete the folder by hand; (c) **card write reordering**: an SD card may complete writes in another order than issued; the existing guard is `sync + read-back before rename` (atomic_save steps 4-5), which this plan keeps for every file, and `project.mt` is renamed **last**, after the read-back of every earlier file already passed; the residual (a card that lies to the read-back) is the same as the native save's and is not made worse. T6 uses the two-entry fault of `save_fatfs_test.cpp` (the directory entry of the temp and of the final name in different sectors) at every cut of every file, including `project.mt`.
- **Read-back mismatch / source changes**: the job fails; the bank's per-slot version is watched as the `.pti` save does (`watch_ok`): a sample edited, replaced or swapped during the export ends the export (`Modified`).
- **The document changing**: the progress overlay captures every key (as the WAV export: `OverlayId::ExportProgress`), MIDI-learn CCs do nothing (existing rule), the transport stops first; the writers' own `unchanged()` guard (`og.h` `WriterBase`) ends the export if the model changes anyway.

**Guard additions (Level C, `hal/save_guard.h`, walked by `tests/save_guard_test.cpp`; MAJOR of the review, folded)**: only the **exact forms**, each with the folder shape above as its second component: `Export/<name> OG[ n]` (folder, make_dir); `Export/<name> OG[ n]/patterns` and `.../instruments` (folders); Targets, NewOnly, never replaced, no Backup form: `.../project.mt` (3 components), `.../patterns/pattern_NN.mtp` (NN 1..255, at least two digits as the fixture folders name them: checked against the fixture folder listing before C2a), `.../patterns/patternsMetadata`, `.../instruments/<NN name>.pti` (the stem of the names rule); **Temps (`_o3save.tmp`) only in the OG folder itself, `patterns/` and `instruments/`**, never in `Export/<name>` (the stems' flat folder) or anywhere deeper. At most four components, so `Export/<name> OG/patterns/pattern_NN.mtp` is the limit. No rename into another folder, no removal other than temps. The longest path is `Export/` + 31 + `/instruments/` + 31 + `.pti` = 88 bytes, inside `kPathCap` 96. T7 lists the near-misses (below).

Memory and code: the resampler's 8 KB kernel lives in SDRAM and is built in slices (never in flash: the project rule); output goes through a chunk buffer of a few KB; the source PCM is read in place from the sample bank (read-only). Flash: the orchestration job and guard rows, estimated 3-4 KB (to be measured by `tools/ci.sh mk66`, flash is at 71.7%); SRAM_L untouched (never in the audio path). Cost: about 5 us a frame at ratio 1 to 25 us at ratio 5.3 (amiga_convert.h): a 7.6 MB project is a few seconds to under a minute on the main loop in slices, with the screen running; nothing runs in the render or an ISR.

## 7. Versioning

Written: project **v16** (2,320 B, firmware field 1.9.0.255) by default, v17 when the target is 1.9.2; pattern **v5** (12 tracks); `.pti` **v9**; PAMD **v1**. Why: v16, v5, v9 and PAMD v1 are the highest versions with fixture evidence (`og.h` `kProjectVerified` etc.: **VP**); v17 is observed only, no file seen (og.md section 2: open research question), and what an official device of the other generation does with the project name is unknown (og.md section 3 table: **OQ**). So **default, to confirm by the maintainer**: target 1.9.0, with the 1.9.2 target offered as a second value of the EXPORT row. No format changes anywhere: no native chunk, no version bump (the rule for persistent formats is met by writing only existing OG versions).

**Evidence classes (MAJOR of the review, folded)**: v16, pattern v5, `.pti` v9 and PAMD v1 are **VP** as formats (fixtures read and write back byte for byte). That an official device **opens** them is **OQ** until T9. **v17 / target 1.9.2 is OQ** (observed only, no file: og.md section 2): **slice 1 (C2a and C2b) targets 1.9.0 only**, with no target choice in the UI; 1.9.2 comes with a second slice after a real v17 file has been seen. The `pattern_NN.mtp` padding and reserved bytes the writer emits (zeros) are checked against the fixtures before C2a: `og_fixture_survey_test.cpp` has 103 8-track patterns and **one** 12-track pattern, so the 12-track block (tracks 9-12, the unused tail of each 769-byte row) is compared byte by byte against that one file and the result is written here (**OQ** until done).

## 8. The user flow

File > F7 EXPORT page, which has four rows (SONG, PATTERN, SONG STEMS, PATT STEMS: `app/include/o3os/app/export_view.h` `kRows`). Part C adds a fifth row **OG PROJECT** (NEW; **default, to confirm by the maintainer**). On it (slice 1 targets 1.9.0 only, so the encoder does nothing yet; the 1.9.2 value comes later, section 7): the card line shows the folder that F1 would make (`Export/<NAME> OG`) and the size (`about 7.6 MB, 29 FILES`); F1 starts.
1. **Question** (only when something is lost or converted, i.e. `any_lost()` or any new counter): the strip says `3 MODULES, 14 FX, 2 LEVELS CLAMPED NOT KEPT: F1 AGAIN`, the same two-press guard as NEW/OPEN (taken back by any other key, a move or 4 s; `file_question_sync`). A project with no loss exports at once.
2. **Progress**: the existing modal overlay (`FILE n OF m`, the part, the bar; F8 CANCEL ends the set, finished files stay), transport stopped first.
3. **Result strip**: `SAVED OG PROJECT <NAME> OG (29 FILES)` and, with losses, `... 3 MODULES NOT KEPT`; failures say why (`CARD FULL`, `CANCELLED: n OF m FILES`, `EXPORT FAILED: <why>`). A longer report (the counters by name, the instruments not written) goes to the diagnostics log (`log`) and to the screen's info pane; a report file is **not** written (**default, to confirm by the maintainer**: the guard grows by one more kind otherwise).
4. The label **EXPERIMENTAL / NOT YET OPENED ON AN OFFICIAL UNIT** stays on the row until the hardware check of section 10 closes (**default, to confirm by the maintainer**).
The standalone `.pti` flow (Shift + F5) does not change; its PCM is resampled behind the scenes and a one-line notice says `RESAMPLED 22050 -> 44100 HZ` (NEW).
