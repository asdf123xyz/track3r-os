# OS-FINALQA: the final test batch and the feature catalogue

Maintainer direction, 2026-10-14: finish the whole work queue, then run one good batch of final tests. In that final check: take screenshots, verify that the whole GUI is correct and easy to use, and build a reproducible catalogue of tests and features and how each maps to the UI. It will later feed the documentation of how the whole system works.

Level B (docs, test scenarios, host tooling). No firmware behaviour changes here; fixes found by the batch go through their own items.

## 0. What exists (verified 2026-10-14)

- **Simulator:** `o3sim` replays scripted input (`sim/scenarios/*.txt`: `tap`, `press`, `pad`, `encoder`, `action`, `document`, `midicc`, `playhead`, `snap`), writes PNGs, checks SHA-256 goldens (`sim/goldens.txt`), and has a gallery mode covering every screen, state and theme (`sim/README.md`).
- **Unit:** the HIL runner takes JSON scenarios (`platform/mk66/tools/hil/*.json`, generated by `gen_hil.py`) with keys, encoder, state asserts, console commands, and `shot` steps. A shot can be compared against a simulator snapshot by region and tolerance. the tester runs it through o3console.
- **Known gap (OS-SIMKEY, in the queue):** the key-cap bar renders 0.56× darker on the unit than in the simulator, and `--shot-format 8888` returns a white PNG.

## 1. Deliverables

1. **Feature catalogue**: `docs/qa/catalogue/<screen>.md`, one file per screen in `docs/ui/ui-map.md` §1, plus `global.md` for global keys, transport, MIDI, USB and storage. Every row is one user-visible function, in one fixed table:

   | ID | Function | How (gesture) | Expected | Sim | Unit | Spec | Status |
   |---|---|---|---|---|---|---|---|
   | QA-PAT-012 | Select a block | Shift + arrows in Edit free | the block is highlighted; F2 COPY copies it | `qa/qa_pattern.txt` › `qa_pat_012` | `qa_pattern.json` › `qa_pat_012` | OS-RECSWAP | sim PASS 0.5.x · unit PASS 0.5.x |

   - IDs are `QA-<SCREEN>-NNN` and are never reused.
   - "How" writes keys exactly as the keycaps read: `Shift + F4`, `Rec`, `pad 13`, `encoder +2`.
   - Status carries the build id or version of the last run.
   - `docs/qa/catalogue/README.md` holds the index and the counts: functions, sim PASS, unit PASS, open.
2. **Simulator scenarios**: `sim/scenarios/qa/qa_<screen>.txt` (the `qa_` prefix keeps test names and golden prefixes apart from the other scenarios), one `snap qa_<id>` for each row that has a visible result. Their goldens go in `goldens.txt`, so the batch is reproducible with one command.
3. **Unit scenarios**: `platform/mk66/tools/hil/qa_<screen>.json`, for every row where the hardware matters: audio, MIDI, USB, storage, CPU, LEDs and pads. Each has a `shot` of the screen and, where the screen is the same, a soft `compare` against the simulator snapshot.
4. **Screenshot set**: the gallery (every screen × state × theme) from the simulator, plus one unit shot per screen and main state. A contact sheet the screenshot contact sheet links each picture to its catalogue rows. The PNGs stay out of git when they are large; the scenarios regenerate them.
5. **Usability review**: the usability notes. Every screen is checked against:
   - the UI budget rules in `docs/ui/ui-map.md` §5;
   - every Shift + F has a label (the OS-UIFIX test);
   - the header names the screen and page;
   - a common action takes three presses or fewer from the screen's home;
   - an F key never changes meaning without a visible label;
   - no hidden mode;
   - readable at arm's length, in all three themes.

   Every finding has a screenshot, a severity (blocker, confusing, cosmetic) and a proposed fix. The review is done once per screen set from the PNGs with a short brief, and checked by the maintainer.
6. **CPU**: the heavy-song run of `docs/architecture/cpu-budget.md` §5 on the final image, plus the budget table filled with measured values.
7. **Final report**: `docs/qa/final-report-<date>.md`. It gives the build id, image hash, simulator and unit pass counts, the CPU table, usability findings by severity, and what is still open.

## 2. Incremental rule (from now on)

So that the final batch is a run, not a writing marathon, **every item merged from the queue adds its catalogue rows and its simulator `snap` lines** in the same branch, plus a HIL step when it touches hardware. The reviewer checks that they are present. Items merged before this rule get their rows during the final batch.

## 3. Order of the final batch (when the queue is empty)

1. The catalogue is drafted for all screens from `ui-map.md` and the specs, marking rows still without a scenario.
2. An implementer fills the missing simulator scenarios and goldens, and runs `o3sim --gallery` and every `qa/*.txt` with `--check --twice`.
3. the tester runs every `qa_*.json` and the existing battery on the final image, takes the unit shots, and runs the CPU protocol.
4. The screenshots are reviewed for usability (section 1, item 5). Small fixes (labels, alignment, text) go to the implementer as one batch; larger ones are recorded for the maintainer.
5. A second pass after the fixes; then the final report.

## 4. Acceptance

- Every screen in `ui-map.md` §1 has a catalogue file, and every function on its F-key and Shift rows has a row.
- `o3sim` runs every QA scenario with `--check --twice` and exits 0.
- The unit battery reports PASS or a recorded finding for every unit row.
- No usability blocker is left open without a maintainer decision.
- The final report exists, and the catalogue counts match it.

## 5. Later (not here)

User documentation is generated from the catalogue: one page per screen, with its gestures, expected results and screenshots.
