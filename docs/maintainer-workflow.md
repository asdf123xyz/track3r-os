# How the maintainer works (the agent set-up behind this repository)

This page is the maintainer's own way of running the project with Claude Code: roles, lanes, agents, skills and the build machines. It is one working set-up, not a rule of the project. The project's rules are in `CLAUDE.md` (hard rules, layout, standards, branches); you can follow them with any tool, or with none. To use this set-up on your own machine, or to drop it, read `docs/agent-setup.md`: what to change is listed there.

The root `CLAUDE.md` imports this page at its end, so a Claude Code session in this repository loads it. Delete that one import line to work without it.

## The maintainer's machines

- **Never max out the machine:** `nice -n 10 taskset -c 2-19` (cores 0-1 always stay free for the system), 18 jobs in total at most. A lane build outside the CI lock stays at `-j4`. Whoever holds `flock "$(git rev-parse --git-common-dir)/../.claude/worktrees/.ci.lock"` (a full `tools/ci.sh` run, or an `mk66`/`qemu` run) uses `O3OS_CI_JOBS=10`, which sets build and ctest parallelism; direct `ctest` calls outside the lock use `-j2`.
- **Remote build machine first.** Every agent sends its `tools/ci.sh` runs (scoped or full `host`, `e2e`, `qemu`, `mk66`) to the remote build machine with `tools/remote_ci.sh` (16 threads in four turns of 4, so four runs go at once; the full log back in `build-remote/`); so does the edit-compile loop (maintainer, 2026-10-22: locally only the cmake configure for the LSP and the hooks); image builds and image gates stay local. It is named by `O3OS_REMOTE_CI`, set locally only; exit 3 or 255 (no remote) means the local rules above. Details: `docs/toolchain.md`.

## How work is organised

- **Sessions by role** (names change after a restart; use ListAgents). Two sessions run standing: the **orchestrator** (Opus) runs the backlog (specs → worktree → engineer → review → merge → image) in **three lanes** by default (maintainer, 2026-10-21: one M/L item, one S batch and one bug batch of the fast lane in `fw-feature`, whose files do not overlap; the maintainer's latest count wins; reviewers, verifiers and doc agents are not lanes), keeps a recurring keep-alive ping every 30 min so its context never goes an hour idle, and only moves the queue (routine in the `fw-feature` skill); the **tester** (Sonnet) installs gated images on the unit and runs the HIL scenarios when the orchestrator asks, and the orchestrator pings it when it shows idle. Other sessions run only when the maintainer opens them: a **spec session** writes specs and ADR amendments and takes delegated product/UX decisions; a backlog session may own `BACKLOG.md` and relay the maintainer's decisions.
- **Subagents** (`.claude/agents/`): `firmware-engineer` (Sonnet) implements one scoped change; `firmware-reviewer` (Sonnet, read-only) reviews; `build-verifier` (Haiku) does the mechanical build/test/budget gate; `doc-keeper` (Haiku) updates status docs; `radar-researcher` (Sonnet) researches ideas; built-in `Explore` for searches and `Plan` for designs. The project agents take their model from their frontmatter; pass `model` explicitly to built-in agents, which otherwise inherit the orchestrator's model. Keep token spend low: brief agents with a short packet (not CLAUDE.md or whole specs), fold through the same engineer, cap agent reports.
- **Skills** (`.claude/skills/`): `fw-feature`, `decide`, `rt-optimize`, `tmod-perf`, `dsp-port`, `fw-build`, `fw-gate-check`, `hw-session`, `sd-module`, `radar`, `handoff`.
- **Backlog states** (`docs/roadmap/BACKLOG.md`): IDEA → APPROVED → QUEUED → IN PROGRESS → DONE, plus PARKED and DROPPED. At most 3 in progress and 6 queued; keep one large (M/L) task, one small (S) batch and one bug batch running (a batch of one lane counts as one).
- **QA catalogue** (`docs/qa/catalogue/<screen>.md`): every merged item adds its rows (function, gesture, expected result, sim scenario, unit scenario, spec). It feeds the test battery and the user manual (`docs/manual/`).
- **CI break:** a trivial, isolated CI break (one obvious edit, one test proves it) is fixed by the orchestrator itself on a `fix/` branch, merged with `git merge --no-ff`; it opens no lane and spawns no agent.
- **Agent reuse:** an engineer is reused only for related items and below about 200k tokens; otherwise a fresh agent is briefed with a short written state (a "state for implementer" section in the spec).
